# Vise — Canonical Architecture (Ideal)

This document describes the IDEAL architecture Vise is working toward. It points well ahead of
the current scaffold and is the reference to keep in mind as the project scales. It is not a
changelog; progress lives in the git log.

## Definitions (core terms & invariants)

- **Vise**: a pnpm-workspaces monorepo pairing a Node HTTP backend with a browser SPA frontend, both in vanilla TypeScript (no runtime frameworks).
- **Backend**: an `http` server exposing a JSON-only API under `/api/*`. Runs on `:3001`.
- **Frontend**: a Vite + vanilla-TS SPA. Runs on `:5173`; talks to the backend via a dev proxy (`/api -> :3001`).
- **LLM proxy**: a local llama.cpp server (OpenAI-compatible API) at `:8080`. It is external to Vise: it is *not* part of the `/api/*` surface and has no backend route. The browser reaches it only through the Vite dev proxy (`/llm -> :8080`, prefix stripped), because the proxy's CORS allows the LAN origin.
- **Route**: a mapping of `(method, pattern) -> handler`. Patterns support `:param` segments and a trailing `*` wildcard, which captures the remaining path segments into `params.rest`.
- **AppContext**: the per-process dependency container (currently `now`, `rootPath`). Handlers should obtain shared services through the context, not globals. `rootPath` is the root the filesystem API is scoped to.
- **Invariant — JSON in, JSON out, with one streaming exception**: every `/api/*` response is JSON with a stable shape (`{ status }`, `{ message }`, `{ error, message }`). The single exception is `GET /api/watch`, a Server-Sent-Events stream (`text/event-stream`) used for live filesystem reflection. The dispatch loop must treat a streaming route as one that *owns* the response (skips the JSON body read and the `toResponse` mapping) rather than papering over the exception by luck (an empty SSE GET happens to parse as a `null` body today, which is fragile). A streaming route is the only place allowed to write to `res` directly.
- **Invariant — no circular imports**: modules are layered so dependency edges point one way (see Structure). Splitting a file must never require a back-edge.
- **Invariant — structured, actionable errors**: an error response answers what/where/why/how (see Potential Problems).
- **Invariant — exception-safe dispatch**: the entire per-request path (matching + body + handler) runs under a single catch. Malformed client input — e.g. a bad percent-encoding in the URL — yields a structured 400/404, never an unhandled exception. The process must never crash from client input.
- **Invariant — long-lived resources are owned by the app lifecycle, not by a module**: any app-scoped resource that outlives a single request (the shared filesystem watcher, the server) is created and torn down through `createApp`/`close`, never parked in a module-level `let`. `close()` must release *every* resource the app opened, so that `createApp` + `close` in a test exits cleanly and the process has no dangling handles. Adding a new long-lived resource means wiring its teardown into `close()` and the `index.ts` signal path, not introducing a new singleton.
- **WatchEvent / live reflection**: a debounced filesystem change under the root, emitted to the browser over `/api/watch`. The path is *relative to the root, forward-slash separated*, and is server-derived (never client input), so it carries no traversal surface — the `..`/out-of-root guard in `watch.ts` is a belt-and-suspenders check, not the load-bearing defense.
- **Invariant — filesystem is root-scoped and symlink-safe**: any path served by the filesystem API is resolved against `rootPath`, and its *realpath* must remain within the *realpath* of `rootPath`. This defeats both `..` traversal **and** symlink escape (a link inside root that points outside must be rejected). The guard lives in a single shared module (`fs.ts`), not inlined per route.
- **Invariant — file reads and writes are bounded and text-safe**: a file is only read *or written* when (a) its size is ≤ the size cap, and (b) the bytes are decodable as UTF-8 text. Binary files and over-cap files are rejected with a structured 400 — never read as mojibake, and never overwritten. Writes go through the same root-scoped, symlink-safe guard as reads (`fs.ts`), so a write cannot escape the root any more than a read can. The guard and the binary/size checks live in one shared place (not per route), so read and write stay consistent.
- **Invariant — LLM API keys are not source code.** No secret is committed to the repo. The llama.cpp key is provided at build time via a gitignored `.env` (or `.env.local`) file consumed through Vite's `import.meta.env.VITE_*` variables, with an explicit "proxy unreachable / key missing" empty state in the UI when it is absent.
- **Invariant — LLM tools reach the filesystem only through the sandboxed API.** The model's file tools (`list_directory`, `find_files`, `read_file`, `edit_file`, `create_directory`, `create_file`, and the destructive `delete_file`/`delete_directory`) are executed **on the backend** (`routes/llm.ts`); every file-tool handler reaches the filesystem only through the sandboxed resolvers in `fs.ts` (`resolveWithinRoot`), so a tool inherits the root-scoped, symlink-safe guard and adds no new filesystem attack surface. (`find_files` is the read-only exception: it shells out to `git ls-files` to list git-tracked/ignored names and returns git-relative paths, so it does not touch the sandboxed `fs` — safe because it only *reads* names, never contents, and never writes.) The browser panel only forwards the model's calls to `POST /api/llm/tool` and renders the returned string — it never joins paths or reads files itself. Adding a tool = one name in `@vise/shared`'s `LLM_TOOL_NAMES` + one definition in `llm/tools.ts` + one handler in `routes/llm.ts`, and a file tool must keep routing through `fs.ts`. `create_subagent` is the one declared exception to "executed on the backend" — see the invariant below.
- **Invariant — `create_subagent` is the sole client-executed LLM tool, and a subagent cannot itself spawn subagents.** Every other tool call goes `panel -> POST /api/llm/tool -> backend handler`. `create_subagent` cannot, because fulfilling it means running another chat-completion loop, and only the browser panel holds the LLM proxy connection — so `runTurn`'s tool dispatch (`resolveToolCall` in `llm.ts`) intercepts it before the network hop and runs `runSubagent` locally: a bounded (`SUBAGENT_MAX_TOOL_TURNS = 5`) loop with its own message history (just the task text — never the parent conversation) and the parent's tool set minus `create_subagent` itself (nesting stops at one level) and minus whatever the parent has disabled. The backend's `tools` record still carries a `create_subagent` entry — a stub that throws — purely so `Record<LlmToolName, LlmToolHandler>` stays exhaustive; it existing and being reachable would itself signal the client-side interception was bypassed. Nothing about a subagent run is persisted (`ConversationStore` only ever sees the ordinary `tool_calls`/`tool` message pair the parent's call produces); the live session renders the run as a collapsed block via `MessageView.appendSubagentResult` so its internal trace is inspectable without being saved.
- **Invariant — command execution is bounded and human-confirmed.** `run_command` is the one tool that reaches the OS shell rather than the sandboxed fs, so it must stay a *bounded, confirmable* capability, not an unrestricted shell. Its ideal shape: (a) a hard timeout that kills the *whole process tree* (a spawned `pnpm`/`node` must not outlive the timeout); (b) a bounded, capped output (≤ 1 MB) so a chatty command cannot flood the model's context; (c) a **vetted-command allowlist** (e.g. only `pnpm`, `git`, `node` with checked sub-args) so the model cannot run arbitrary PowerShell; and (d) a **UI confirmation gate** in the panel before the command is dispatched, since a single model turn (or prompt-injection via a file it reads) can otherwise trigger destructive/exfiltrating commands. (a), (b), and the process-tree kill + single-flight guard are implemented (the tree kill is Windows-only: `taskkill /T /F`); (c)+(d) remain, and until the confirm gate is in place this tool is the app's largest attack surface — tolerable only as a single-user, local-only, trusted-model setting.
- **Invariant — file edits preserve every byte outside the replaced range.** A line-range edit rewrites only the replaced lines; everything else — line endings, trailing newline, untouched lines — must stay byte-identical. In particular an edit to a CRLF file must not re-encode the whole file to LF (and vice versa), because a single-line change showing up as a whole-file line-ending diff is surprising and destroys information the user did not ask to change.
- **Invariant — the UI fills the viewport and scrolls internally**: the SPA spans the full viewport (100dvh) with no page-level scroll; the three panels (tree, viewer, LLM chat) stretch to fill the remaining height and their *content* scrolls within its own region (`overflow: auto` + `flex: 1 1 0; min-height: 0` down the flex chain). Resizing (including narrow/mobile widths, where the grid stacks to one column) must never introduce a horizontal page scrollbar.
- **Invariant — LLM history is append-only; compaction bypasses, never deletes.** The persisted transcript (`localStorage`) grows only: a compaction event appends a summary *marker* message (`role: "user"`, `compaction: true`) and every pre-marker turn stays in the array and on disk. Prompt construction (the panel's `buildMessages`) sends the system prompt + the **latest** marker's content + the turns after it, so pre-marker turns are bypassed in the outgoing prompt while remaining fully recoverable for the UI and future re-summaries. Consequences that must survive any refactor: (a) markers are appended **only at turn boundaries** (before the turn's user message), so a marker can never split an assistant `tool_calls` message from its `tool` results — the `user` role is what keeps the post-cut sequence protocol-valid and must not change; (b) the UI render of a marker (a subtle divider) must agree with the prompt cut: markers *before* the latest marker render as nothing; (c) the summarization call must prompt with the *already-compacted* prefix (`buildMessages` output), never the full history, or it overflows the same window it is meant to rescue (see Potential Problems).

## Structure (module layout & dependency direction)

Dependency direction flows strictly inward; a layer may only import layers to its left.
`packages/shared` is the outermost contract layer: the apps depend on it, and it depends on nothing.

```
packages/shared/src/
  index.ts      # CONTRACTS (type-only): every cross-app shape the apps must agree on,
                #   expressed as types (e.g. the LLM tool-name union). It exports NO
                #   runtime values, so it is erased at emit in both the Vite bundle and
                #   the compiled backend — the backend's zero-runtime-deps invariant holds.

apps/backend/src/
  index.ts        # bootstrap: reads env, wires ctx, starts server (entry only)
  app.ts          # app factory: assembles router + server, request dispatch
  router.ts       # ROUTER: Route type, matchRoute, matchPattern (pure, no I/O)
  json.ts         # BODY: readJsonBody (inbound body parsing)
  http.ts         # RESPONSE: sendJson (the only *JSON* outbound serializer)
  watch.ts        # FS WATCH: createFileWatcher -> { start, close, subscribe }. Owns the
                  #   shared FSWatcher (root, recursive where supported) and a debounce
                  #   (100ms) that coalesces per-path change/rename into WatchEvent
                  #   { path, event }. Path is root-relative, forward-slash, server-derived.
  fs.ts           # FS CORE: root-scoped path resolution (realpath-contained) + vetting
                  #   (validatePath) + existence guard (assertDoesNotExist) + createDir/createFile
                  #   primitives — the single place every fs mutation passes through
  routes/         # HANDLERS: one file per resource/endpoint group
    health.ts     #   GET /api/health
    hello.ts      #   GET /api/hello/:name
    echo.ts       #   POST /api/echo
    ls.ts         #   GET /api/ls/*  (root-scoped directory listing, "rest" wildcard)
    file.ts       #   GET /api/file/* (root-scoped content, size-capped, text-only)
                  #   PUT /api/file/* (root-scoped write, size-capped, text-only)
                  #   DELETE /api/file/* (root-scoped unlink, files only; 404 for dirs/missing)
    create.ts     #   POST /api/file, POST /api/dir (root-scoped creation via the
                  #   fs.ts createDir/createFile cores; HTTP semantics only)
    llm.ts        #   POST /api/llm/tool (LLM tool execution: a `tools` name→handler
                  #   registry — list_directory, find_files, read_file, edit_file,
                  #   create_directory, create_file, delete_file (unlink),
                  #   delete_directory (rm recursive) — reaching fs only via fs.ts
                  #   (find_files excepted: it shells to `git ls-files` and returns
                  #   git-relative names, a read-only OS escape); plus the two OS tools:
                  #   run_command (the shell via node:child_process, spawn + taskkill
                  #   /T /F — timeout, process-tree kill, single-flight guard, 1MB cap)
                  #   and find_files (git via execSync, 10MB buffer, 500-match cap).
                  #   create_subagent's entry is a throwing stub (only exists for the
                  #   Record<LlmToolName, ...> exhaustiveness check) — the frontend
                  #   intercepts and runs it itself, never reaching this route.
                  #   Errors resolve to 200 + "Error: …" so the model adapts)
    watch.ts      #   GET /api/watch (SSE: subscribes the shared watcher, streams WatchEvent
                  #   frames, unsubscribes on res close). The one non-JSON route; owns res.
  errors.ts       # error model: AppError type/enum, toResponse mapping
  context.ts      # AppContext definition + createContext (shared deps)

apps/frontend/src/
  main.ts         # bootstrap: mounts render into #app (entry only)
  render.ts       # THIN composition: sets the full page HTML template, runs the health()
                  #   check, then delegates each panel to components/ — await setupFileViewer(root)
                  #   (tree + editor) and setupLlm(root) (chat). Owns no panel logic itself.
  dom.ts          # shared DOM helpers (makeButton, ...)
  highlight.ts    # SYNTAX HIGHLIGHT: pure line tokenizer + thin DOM appender (see invariant below)
  api/
    client.ts     # fetch wrapper: typed calls, base path, error normalization. Also hosts
                  #   subscribeToChanges(onEvent), the single place that opens the /api/watch
                  #   EventSource and hands parsed WatchEvent objects up (returns a close fn).
  components/     # self-contained views/widgets, one file each
    contextMenu.ts  #   reusable context menu (makeContextMenu / showMenu / hideMenu)
    createDialog.ts #   new-file / new-directory modal (showCreateForm)
    fileTree.ts     #   file tree + viewer/editor panel: a thin DOM controller exposed as
                    #   setupFileViewer(root). Renders the listing (renderListing/renderEntry)
                    #   and the always-edit overlay editor (renderEditor: transparent textarea
                    #   over a live-highlighted backdrop + line-number gutter). Reached via
                    #   listDir/getFile/putFile/apiDelete in api/client.ts. Live reflection:
                    #   tracks expandedDirs and, on a debounced (80ms) WatchEvent, re-fetches
                    #   the root + each expanded dir (depth-ordered) and re-renders; reloads the
                    #   open file when it changed on disk, or marks it "(out of date)" if dirty.
    fileState.ts    #   DOM-free editor/file-state store (target): owns the open file's
                    #   content/rel, the dirty flag, the save timer, and the save lifecycle
                    #   (schedule/flush/save + the "abort navigation on a failed flush" rule).
                    #   Mirrors conversations.ts so the auto-save data-safety invariant is
                    #   unit-testable without a DOM; fileTree.ts then only paints and forwards
                    #   user actions, keeping the controller under the 500-line cap.
    llm.ts          #   LLM chat panel: a thin DOM controller over the conversation store.
                    #   Queries elements, builds the store, wires render fns + events. Runs a
                    #   bounded tool-call loop (list_directory, read_file, edit_file,
                    #   create_directory, create_file, run_command — which must surface a
                    #   confirm-before-run gate) and forwards each model call to the backend
                    #   /api/llm/tool route. Holds the turn loop (runTurn), prompt builder
                    #   (buildMessages), and compaction (summarizeConversation). It owns only
                    #   the turn loop and store wiring — the transcript's rendering is delegated
                    #   to messageView.ts so the controller stays lean. `resolveToolCall`
                    #   dispatches each model call: disabled tools short-circuit locally,
                    #   create_subagent runs its own nested loop (runSubagent — its own
                    #   message history, the parent's tools minus create_subagent itself,
                    #   capped at SUBAGENT_MAX_TOOL_TURNS), everything else forwards to the
                    #   backend as before.
    messageView.ts  #   VIRTUALIZED LLM transcript view (DOM, no store knowledge): renders the
                    #   active conversation's messages as a bounded, windowed list. A general
                    #   `VirtualList` keeps a spacer as tall as the whole conversation and
                    #   positions only the viewport-visible blocks (+ a buffer) absolutely
                    #   inside it, measuring real heights over a couple of rAF passes as they
                    #   settle; it re-lays-out on scroll (rAF-throttled) and on `refresh()`
                    #   (window resize / content change). Exposes append/set/clear methods the
                    #   panel calls in place of raw DOM appends, so a long chat never
                    #   materializes unbounded DOM (see Performance). It is a pure view over
                    #   `ChatMessage[]` — it reads no store and writes no state, mirroring how
                    #   fileTree.ts paints over fileState.ts. `appendSubagentResult` is the one
                    #   exception to "pure view over ChatMessage[]": a subagent's run is never
                    #   persisted, so its collapsed <details> block (task + tool trace + result)
                    #   is pushed straight from llm.ts's live call, not derived from history.
    conversations.ts #   DOM-free conversation store: owns convs, activeId, per-conversation
                    #   promptTokens, and per-model contextWindow. Persists a list of
                    #   {id,title,model,messages} to vise:llm:conversations (+ vise:llm:active);
                    #   exposes getActive/new/switch/delete/persist + title derivation. The store
                    #   always keeps >=1 conversation (deleteConversation reseeds a fresh empty one
                    #   when the last is removed, and reassigns activeId to the first remaining).
                    #   Legacy single-conversation keys (vise:llm:history/model) migrate once.
                    #   Context compaction: when the last call's prompt tokens reached 80% of
                    #   the model's n_ctx (from the proxy's model list), one extra tool-free
                    #   call summarizes the conversation and the summary is appended as a
                    #   compaction marker; buildMessages() then bypasses the pre-marker history
                    #   in every outgoing prompt of the turn (see append-only invariant)
  styles/         # CSS: design tokens + theme (present as a single src/styles.css; split into a styles/ dir as it grows)
```

Target invariants (implemented in the backend):
- `router.ts` is pure (Route type + matching) and imports no I/O — trivially unit-testable.
- Each `routes/*.ts` is a self-contained resource module: `(ctx) => Route[]`. Adding an endpoint = adding a file, no edits to `app.ts`.
- `app.ts` is thin: register route groups, wrap the server, wire body parsing + error handling. It contains no handler bodies or matching logic.
- `context.ts` owns `AppContext`; the context is constructed once (in `index.ts`) and passed into `createApp` — no module-level singleton. The live-reflection `fileWatcher` is a context member, created inert in `createContext`, `start()`ed in `createApp`, and closed in `close()` — the "app lifecycle owns long-lived resources" invariant now holds. Residual: `close()` tears the watcher down only after `server.close()` drains, and a live SSE stream never drains on its own, so `closeAllConnections()` is needed (see Potential Problems).
- Frontend `api/client.ts` is the single place that knows the base URL and normalizes network/HTTP errors, so views never call `fetch` directly. Every endpoint is wrapped (`listDir`, `getFile`, `putFile`, `deleteFile`, `createEntry`, `health`); the `fail(res)` helper centralizes the "parse body → read `message` → throw `Error`" normalization.
- **Invariant — file content is rendered as text, never as HTML.** `highlight.ts` tokenizes one line into runs and `render.ts` inserts every run via `textContent`/`createTextNode`. File content must never reach the DOM through `innerHTML`/`insertAdjacentHTML`, so arbitrary (attacker- or binary-) file bytes cannot inject markup/scripts. Keep the tokenizer pure (a line in, `Token[]` out) so it stays trivially testable and split-free, and keep the DOM-appending as a thin separate function.
- **Invariant — the always-edit overlay keeps both text layers on identical font metrics.** Every file opens in the editor: a transparent-text `<textarea>` (`color: transparent`, `white-space: pre`, no wrap) absolutely positioned over a live re-highlighted `<pre>` backdrop, with a sticky line-number gutter. The two layers only align pixel-perfectly if `font-family`/`font-size`/`line-height`/`tab-size`/`padding`/`margin` are identical on both. Because a `<pre>`'s UA stylesheet forces `font-family: monospace` (overriding inheritance), the backdrop must set the exact mono stack explicitly — relying on inheritance re-introduces ghosted/doubled text. The overlay container (`.editor-scroll`) is the sole scroller; `#viewer-body` is `overflow: hidden` so exactly one scrollbar shows.
- **Invariant — auto-save lifecycle is loss-free on navigation.** The editor debounces saves (`AUTOSAVE_MS`). `viewer.dirty` is the single source of truth for "unsaved work exists"; the `.save-status` span reflects it (`unsaved`/`saving`/`saved`/`error`). Before switching files (`viewFile`) and on `beforeunload`, `flushSave` clears any pending timer and persists a dirty buffer. If that flush **fails**, navigation must be aborted (no re-render) so the in-memory edit is never discarded — the current edit stays in the textarea and `dirty` remains true.
- **Invariant — disabling an LLM tool never changes the tool `definitions` array (KV-cache preserving).** A per-conversation `disabledTools: string[]` (in `conversations.ts`, back-compat via `?? []` on load) drives the disable state. The `llmToolDefinitions` array is always sent **unchanged** to `sendLlmMessage`, so the request prefix (and the server's KV cache) is stable. Disabling a tool only (a) **appends** a note to `SYSTEM_PROMPT` (`systemPrompt(disabled)` — byte-identical to `SYSTEM_PROMPT` when nothing is disabled) and (b) **short-circuits** the client-side execution of a disabled tool with a model-readable result (`disabledToolResult`), so no backend call is made. Do **not** filter the definitions array to drop disabled tools — that is the exact thing the feature is designed to avoid.

**Why the layering matters (recursion):** router (pure), response (I/O), and routes (handlers) are separated so dependency edges point one direction. This keeps the code splittable: any future split of a file cannot introduce a circular import, because the pure core never imports the I/O or handler layers.

## Potential Problems (risks, limits, failure modes)

- **LLM traffic has no production path.** The `/llm` route exists only in `vite.config.ts` (dev server). The built SPA (`pnpm build`) calls `/llm/...` with no route behind it — the panel 404s in any production deployment. Decide the production story when it is needed: a same-origin reverse-proxy rule, or a backend route that forwards to `:8080` (keeps the key off the browser *and* gives the API a single host). Until then the panel is dev-only and that is acceptable for a local tool.
- **The LLM key is hardcoded in `client.ts` (dev-only, to be removed).** It is committed to the repo and baked into the bundle. Fine for a single-user local tool, but it violates the key invariant: move it to a gitignored `.env` consumed via `import.meta.env.VITE_LLM_API_KEY` and surface a clean empty state when absent.
- **No focus trap in dialogs (UI).** The create dialog is `role="dialog" aria-modal="true"` and dismissible via Escape/overlay-click, but Tab cycles through the whole page (buttons, tree toggles) rather than staying inside the dialog. Keyboard users can tab "out" of the modal; add a lightweight focus trap (cycle between the input and the Cancel/Create buttons) when the dialog component is extracted.
- **Create path: check-then-write race and leaf-not-realpathed (acceptable now, watch it).** The create cores in `fs.ts` run `assertDoesNotExist` (stat) *before* `writeFile`/`mkdir`, so there is a TOCTOU window, and `resolveForCreate` realpaths the *parent* only — the new leaf is trusted via name vetting, not re-checked with realpath after creation. For a single-user, root-scoped tool this is fine (and `O_EXCL`/`mkdir` semantics make the practical race a clean 400), but if the server ever becomes multi-user or is pointed at a shared/mutable volume, convert the create to `open(..., O_CREAT | O_EXCL)` for files and rely on `mkdir`'s `EEXIST` for dirs, and re-verify the final realpath is inside the root.
- **Writes have no freshness / conflict guard (now more live with auto-save).** `PUT /api/file/*` overwrites unconditionally. There is no `ETag`/`If-Match` (or content-hash) check, so a save made from a stale read silently clobbers any change made to the file between the `GET` and the `PUT`. Auto-save raises the write frequency, so this is worth doing sooner: add an `ETag` (content hash) to the `GET` response and require `If-Match` on `PUT` (return 409 on mismatch) so concurrent edits surface as a conflict instead of a silent overwrite.
- **Writes are not atomic.** `writeFile` truncates-then-writes in place; a crash mid-write leaves a truncated file. Write to a temp file in the same directory and `rename` it over the target for atomicity once the write path gains real usage.
- **Unbounded directory listings (DoS surface).** `readdir` has no cap on entry count and the response is fully buffered/serialized in memory. A directory with millions of entries (e.g. a large `node_modules`) is listed, sorted, and serialized whole. No pagination, no max-entry limit, no depth guard. Client-side expansion is user-driven (one dir per click) so the blast radius is a single request, but it can still stall a worker.
- **`matchPattern` is a linear scan per request** and re-parses patterns on every call. Fine at this scale; at scale, precompile routes at startup (see Performance). The trailing `*` wildcard is correct for the `rest` capture, but it only matches when `*` is the *last* segment — non-trailing wildcards return `null` (documented behavior; keep it that way).
- **No request-size / timeout guards** on `readJsonBody`; a huge or slow body is buffered unbounded.
- **Frontend: touch targets are just under the comfortable minimum.** The expand/collapse toggle (`.toggle`) is 22×22px (20×20 content + 1px border) — under the ~24px comfortable floor, and the file rows rely on the whole `.row` for the click area. Keyboard focus *is* visible (the UA focus outline is not suppressed and `aria-expanded` is set), so the earlier "no focus ring" gap is gone; only the small hit area remains. Bump `.toggle` to ≥24×24 (or pad the clickable region) when the tree component is extracted.
- **Error messages are terse.** The `AppError` model exists and 500s no longer leak raw `String(err)`, but the generic messages (`resource not found`, `internal server error`) don't fully answer what/where/why/how. The `ls` handler also leaks the resolved absolute `path` and raw `fs` error text into the JSON body — fine internally, but keep the response shape stable.
- **Shutdown does not terminate in-flight SSE connections (top issue).** The watcher now has a real lifecycle owner (context member, `start()` in `createApp`, closed in `close()`), so the module-singleton and "no owner" concerns are gone. But `close()` runs `server.close(cb)` and calls `ctx.fileWatcher.close()` only *inside* `cb`, and `server.close()` does not fire `cb` until every existing connection drains — an open `/api/watch` stream never drains on its own. So while a browser tab has the live-reflection stream open (the normal state), Ctrl-C / SIGTERM hangs: the watcher never closes and the `process.exit(0)` in `index.ts` is gated *after* `app.close()`, so it is a no-op, not a safety net. Fix: call `server.closeAllConnections()` (Node ≥18.02) inside `close()` before/alongside `server.close()`, so open SSE connections terminate and the close callback — and with it the watcher teardown and the exit — actually run.
- **The SSE route is one, and it coexists with the JSON-only request loop by accident.** The dispatch loop in `app.ts` reads a JSON body on *every* request and funnels errors through `toResponse`. `GET /api/watch` (the one `text/event-stream` route) works only because an empty GET body parses to `null` and the handler writes to `res` directly, bypassing both. That is fragile: a streaming route must be explicitly recognized (skip body read + `toResponse`, let it own `res`) or the invariant is being papered over. Today there is exactly one; the dispatch loop has no notion of a "streaming" route kind.
- **`/api/watch` emits no heartbeat and the fallback is silent.** After the `:ok` prime there is no periodic keep-alive comment, so a proxy/LB that drops idle connections sees a silent stream (the browser `EventSource` auto-reconnects, healing it — acceptable for a local tool, but a `:ping` every ~15s is cheap insurance). Separately, `watch.ts` falls back to a *non-recursive* root-only watch when `recursive` is unsupported (Linux without inotify-recursion): nested changes are silently missed and the UI goes stale with no indication. Surface the degraded mode (a `degraded: true` field or a one-time log) so a stale tree is explainable.
- **Live-reflection debounce drops intermediate events and can re-locate dead nodes.** The frontend debounce (80ms) keeps only the *last* event's `path`, so a create+delete inside one window nets to nothing and no refresh fires for that file — a benign edge for a human-paced tool, but worth noting. `liveRefresh` re-locates each expanded dir's `<li>` by walking the DOM and matching `.name` text; if a dir was removed on disk, `findDirLi` returns `null` and it is skipped, so a stale `expandedDirs` entry leaks until the next collapse/expand. Harmless (a `Set` of strings) but unbounded in principle; clear it on a root refresh.
- **Multi-conversation titles: empty conversations are now distinguishable (fixed).** `deriveTitle(messages, idSuffix?)` falls back to `"New conversation"` for any conversation with no user message, but when `idSuffix` is supplied it returns `"New conversation · <suffix>"`. Both empty-conversation creation sites (the first-run seed and `newConversation`) pass the new id's first 4 chars, so several empty conversations stay tell-apart in the `#llm-conversation` select. Titles derived from a user message carry no suffix (they are already unique-ish). Consider making titles *editable* so a conversation is always addressable by a label the user chose — that is the remaining, optional refinement.
- **Compaction: the summarizer call can overflow the window it is rescuing (fixed: it now prompts with the compacted prefix).** The 80% trigger fires when the *last* prompt was already ≥ 80% of `n_ctx`; `summarizeConversation` previously sent the **full, un-compacted** history (system + everything) — strictly larger than the prompt that just measured ≥80% — so on llama.cpp the rescue call would 500/degrade past `n_ctx`, fail like the turn it saves, and drop the user's just-sent message (rollback to `preLength`). It now sends `buildMessages(history)` (the already-cut prefix) per the append-only invariant, so the rescue prompt is never larger than the one that triggered it. Residuals to watch: (a) an empty summary produces no marker and silently retries every turn — acceptable, but a "compaction failed, context near limit" hint would surface it; (b) token measurements are per-model: after a model switch, `lastPromptTokens` (measured under the old model) is compared against the new model's `n_ctx` — reset `lastPromptTokens = undefined` on model change to make the metric honest again.
- **`run_command`'s process-tree kill is Windows-only, and there is no UI confirm gate.** The timeout now kills the tree via `taskkill /T /F` (Windows) and the single-flight guard bounds concurrency, but on a non-Windows host `taskkill` does not exist so the kill degrades to `child.kill()` on the top-level shell only — descendants (`pnpm`/`node`/`git`) survive the timeout. The confirm gate (invariant above) is also not implemented: the panel dispatches a model-requested command with no human approval, so a single turn (or a prompt-injected file) can run it unattended. (The arbitrary-PowerShell tradeoff itself is *accepted* for this single-user, local-only tool; do not re-architect toward a full sandbox.)
- **The sandbox guard blocks escape; destructive tools additionally reject the root itself (fixed).** `resolveWithinRoot` returns the root unchanged when `realTarget === realRoot`, so a root alias (`"."`, `""`, an absolute-in-root path) *would* pass `isDirectory()` and let `rm(realRoot, { recursive: true })` wipe the whole workspace in one model call. The guard is now in place: both `delete_file` and `delete_directory` reject `realTarget === realRoot` (`badRequest("cannot delete the workspace root")`), so the root cannot be a delete target even though it is a valid in-root path. `delete_file` is *additionally* safe on the kind check (a root is a directory, so `isFile()` fails), but the explicit root guard is the load-bearing defense — do not rely on the kind check alone.

- Make the write path as safe as the read path: add a conflict guard (`ETag`/`If-Match`, 409 on a stale save), and make writes atomic (temp file + `rename`). (Unsaved-edit guarding — dirty flag, "unsaved" indicator, confirm + `beforeunload` — is now implemented.)
- Bound filesystem listing: cap entry count (and/or paginate), so a huge directory cannot stall a worker or balloon memory.
- Add a focus trap to the create dialog (and any future modal): Tab should cycle within the dialog, not the whole page.

## Performance (obvious concerns only — profile before optimizing)

- Live reflection adds two costs to watch: (a) the backend `fs.watch` is recursive over the whole root, so a large tree (e.g. `node_modules`) produces a high event rate that the 100ms debounce coalesces by *path* — cheap per flush, but the watcher itself tracks every file; consider an ignore list for `node_modules`/`.git` if the root is large. (b) Each debounced `liveRefresh` re-fetches the root plus every expanded directory (N+1 requests per burst); fine for a few expanded dirs, but cap or batch if the tree grows. The SSE stream holds one open connection per browser tab — unbounded subscriber count is not guarded (a per-subscriber cap is cheap insurance).

- Route matching is a per-request linear scan with per-call pattern splitting; precompile the route table at startup (regex/radix) when endpoint count grows.
- Body buffering is unbounded; bound it and stream once payloads get large.
- Directory listings are fully read, sorted, and serialized in memory; cap/paginate once directory sizes are large.
- The dev proxy adds one hop in development only; it is absent in a same-origin production deployment.
- Frontend: lazy per-directory fetch on expand (no preloading). When the tree grows, consider caching expanded state so collapse/re-expand is free, and avoid re-fetching an already-loaded listing.
- The viewer materializes one DOM node pair (`.line` + line number + text) per line. A ~1 MB file (the preview cap) is thousands of lines → tens of thousands of nodes in a single scroll region. Fine for small files; profile before assuming, and reach for virtualization only if a real file makes the scroll region lag. (The LLM transcript no longer has this problem — `messageView.ts`/`VirtualList` window-renders only the visible blocks, so its DOM stays bounded regardless of conversation length; the file viewer is the one remaining unbounded-DOM surface.)
- Real tuning should be driven by a profiler (Node perf / browser devtools), not by the above guesses.
