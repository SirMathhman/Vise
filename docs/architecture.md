# Vise — Canonical Architecture (Ideal)

This document describes the IDEAL architecture Vise is working toward. It points well ahead of
the current scaffold and is the reference to keep in mind as the project scales. It is not a
changelog; progress lives in the git log.

## Definitions (core terms & invariants)

- **Vise**: a pnpm-workspaces monorepo pairing a Node HTTP backend with a browser SPA frontend, both in vanilla TypeScript (no runtime frameworks).
- **Backend**: an `http` server exposing a JSON-only API under `/api/*`. Runs on `:3001`.
- **Frontend**: a Vite + vanilla-TS SPA. Runs on `:5173`; talks to the backend via a dev proxy (`/api -> :3001`).
- **LLM proxy**: a local llama.cpp server (OpenAI-compatible API) at `:8080`. It is external to Vise: it is _not_ part of the `/api/*` surface and has no backend route. The browser reaches it only through the Vite dev proxy (`/llm -> :8080`, prefix stripped), because the proxy's CORS allows the LAN origin.
- **Route**: a mapping of `(method, pattern) -> handler`. Patterns support `:param` segments and a trailing `*` wildcard, which captures the remaining path segments into `params.rest`.
- **AppContext**: the per-process dependency container (currently `now`, `rootPath`). Handlers should obtain shared services through the context, not globals. `rootPath` is the root the filesystem API is scoped to.
- **Invariant — JSON in, JSON out, with one streaming exception**: every `/api/*` response is JSON with a stable shape (`{ status }`, `{ message }`, `{ error, message }`). The single exception is `GET /api/watch`, a Server-Sent-Events stream (`text/event-stream`) used for live filesystem reflection. The dispatch loop must treat a streaming route as one that _owns_ the response (skips the JSON body read and the `toResponse` mapping) rather than papering over the exception by luck (an empty SSE GET happens to parse as a `null` body today, which is fragile). A streaming route is the only place allowed to write to `res` directly.
- **Invariant — no circular imports**: modules are layered so dependency edges point one way (see Structure). Splitting a file must never require a back-edge.
- **Invariant — structured, actionable errors**: an error response answers what/where/why/how (see Potential Problems).
- **Invariant — exception-safe dispatch**: the entire per-request path (matching + body + handler) runs under a single catch. Malformed client input — e.g. a bad percent-encoding in the URL — yields a structured 400/404, never an unhandled exception. The process must never crash from client input.
- **Invariant — long-lived resources are owned by the app lifecycle, not by a module**: any app-scoped resource that outlives a single request (the shared filesystem watcher, the server) is created and torn down through `createApp`/`close`, never parked in a module-level `let`. `close()` must release _every_ resource the app opened, so that `createApp` + `close` in a test exits cleanly and the process has no dangling handles. Adding a new long-lived resource means wiring its teardown into `close()` and the `index.ts` signal path, not introducing a new singleton.
- **WatchEvent / live reflection**: a debounced filesystem change under the root, emitted to the browser over `/api/watch`. The path is _relative to the root, forward-slash separated_, and is server-derived (never client input), so it carries no traversal surface — the `..`/out-of-root guard in `watch.ts` is a belt-and-suspenders check, not the load-bearing defense.
- **Invariant — filesystem is root-scoped and symlink-safe**: any path served by the filesystem API is resolved against `rootPath`, and its _realpath_ must remain within the _realpath_ of `rootPath`. This defeats both `..` traversal **and** symlink escape (a link inside root that points outside must be rejected). The guard lives in a single shared module (`fs.ts`), not inlined per route.
- **Invariant — file reads and writes are bounded and text-safe**: a file is only read _or written_ when (a) its size is ≤ the size cap, and (b) the bytes are decodable as UTF-8 text. Binary files and over-cap files are rejected with a structured 400 — never read as mojibake, and never overwritten. Writes go through the same root-scoped, symlink-safe guard as reads (`fs.ts`), so a write cannot escape the root any more than a read can. The guard and the binary/size checks live in one shared place (not per route), so read and write stay consistent.
- **Invariant — LLM API keys are not source code.** No secret is committed to the repo. The llama.cpp key is provided at build time via a gitignored `.env` (or `.env.local`) file consumed through Vite's `import.meta.env.VITE_*` variables, with an explicit "proxy unreachable / key missing" empty state in the UI when it is absent.
- **Invariant — LLM tools reach the filesystem only through the sandboxed API.** The model's file tools (`list_directory`, `find_files`, `search_files`, `read_file`, `edit_file`, `create_directory`, `create_file`, and the destructive `delete_file`/`delete_directory`) are executed **on the backend** (`routes/llm.ts`); every file-tool handler reaches the filesystem only through the sandboxed resolvers in `fs.ts` (`resolveWithinRoot`), so a tool inherits the root-scoped, symlink-safe guard and adds no new filesystem attack surface. (`find_files` and `search_files` share a `listWorkspaceFiles` helper that shells out to `git ls-files` to list git-tracked/untracked-and-not-ignored names and returns git-relative paths, so _that listing step_ does not touch the sandboxed `fs` — safe because it only _reads_ names, never contents, and never writes; `find_files` matches names against that list alone, while `search_files` goes on to read each candidate's content, and does so through the normal `resolveWithinRoot`/`fs.ts` path like any other read, so the content-reading half of the tool is fully sandboxed.) The browser panel only forwards the model's calls to `POST /api/llm/tool` and renders the returned string — it never joins paths or reads files itself. Adding a tool = one name in `@vise/shared`'s `LLM_TOOL_NAMES` + one definition in `llm/tools.ts` + one handler in `routes/llm.ts`, and a file tool must keep routing through `fs.ts`. `create_subagent` is the one declared exception to "executed on the backend" — see the invariant below. `browser_run_code` runs model-written JavaScript, so it is **not** run in the backend process: `routes/browser/codeRunner.ts` runs each snippet in a short-lived child Node process under `--permission` (no file reads outside Playwright's package, writes only to a fresh empty scratch dir, no child processes or workers), which reaches the page by attaching to the same Chrome over CDP (a localhost-only debugging port the gate opens), and is killed after 30s — so a spinning snippet can neither freeze the backend nor touch the filesystem outside `fs.ts`'s sandbox.
- **Invariant — the client-executed tools are `create_subagent`, `ask_questions`, and `use_skill`, and all three are intercepted before the network hop.** Every other tool call goes `panel -> POST /api/llm/tool -> backend handler`. `create_subagent` cannot, because fulfilling it means running another chat-completion loop, and only the browser panel holds the LLM proxy connection — so `runTurn`'s tool dispatch (`resolveToolCall` in `llm.ts`) intercepts it before the network hop and runs `runSubagent` locally: a bounded (the profile's `maxToolTurns`, default 100) loop with its own message history (just the task text — never the parent conversation), under the named Profile the model passed as the call's required `profile` argument (its own system prompt, allowed tools, and hooks — see profiles.ts); a missing or unrecognized `profile` is a model-readable error (listing the available profile names) rather than a fallback (nesting stops at one level regardless of what a named profile's own `allowedTools` lists — `subagentToolDefs` excludes `create_subagent` unconditionally). `ask_questions` cannot either, because fulfilling it means rendering an interactive card and _pausing the turn_ until the user answers — a UI concern only the panel can own; `resolveToolCall` intercepts it and awaits `askQuestions`, which renders the card (`askQuestionsCard.ts`) into the transcript and resolves with the model-readable answer string. `use_skill` cannot either, because fulfilling it means looking up a named skill's full content in the browser's skill store — a panel concern the headless subagent loop doesn't own — so `resolveToolCall` intercepts it and returns the skill's `content` verbatim (a missing name is a model-readable error listing the available skill names). The model sees each skill's `name` and one-line `summary` in the system prompt's available-skills list (appended by `systemPrompt` when any skill has a non-empty summary) and calls `use_skill` with the skill's `name` — the name is the model-facing identifier and is the store's uniqueness key (no internal id). `subagentToolDefs` excludes `use_skill` unconditionally, alongside `create_subagent` and `ask_questions`. The backend's `tools` record still carries a throwing stub for each — purely so `Record<LlmToolName, LlmToolHandler>` stays exhaustive; reaching one would itself signal the client-side interception was bypassed. Nothing about a subagent run or a question card is persisted (`ConversationStore` only ever sees the ordinary `tool_calls`/`tool` message pair the parent's call produces); the live session renders the subagent run as a collapsed block via `MessageView.appendSubagentResult` and the question as an ephemeral card, so their traces are inspectable without being saved.
- **Invariant — command execution is bounded and human-confirmed.** `run_command` is the one tool that reaches the OS shell rather than the sandboxed fs, so it must stay a _bounded, confirmable_ capability, not an unrestricted shell. Its ideal shape: (a) a hard timeout that kills the _whole process tree_ (a spawned `pnpm`/`node` must not outlive the timeout); (b) a bounded, capped output (≤ 1 MB) so a chatty command cannot flood the model's context; (c) a **vetted-command allowlist** (e.g. only `pnpm`, `git`, `node` with checked sub-args) so the model cannot run arbitrary PowerShell; and (d) a **UI confirmation gate** in the panel before the command is dispatched, since a single model turn (or prompt-injection via a file it reads) can otherwise trigger destructive/exfiltrating commands. (a), (b), and the process-tree kill + single-flight guard are implemented (the tree kill is Windows-only: `taskkill /T /F`); (c)+(d) remain, and until the confirm gate is in place this tool is the app's largest attack surface — tolerable only as a single-user, local-only, trusted-model setting.
- **Invariant — file edits preserve every byte outside the replaced range.** A line-range edit rewrites only the replaced lines; everything else — line endings, trailing newline, untouched lines — must stay byte-identical. In particular an edit to a CRLF file must not re-encode the whole file to LF (and vice versa), because a single-line change showing up as a whole-file line-ending diff is surprising and destroys information the user did not ask to change.
- **Invariant — the UI fills the viewport and scrolls internally, never the page, and never with two nested scrollbars.** `html`/`body` are hard-pinned to `100vw`/`100vh` with `overflow: hidden` (`base.css`) — the page itself can never scroll, in either axis. `#app section` (each of the three panels: tree, viewer, LLM chat) is `overflow: hidden` too — a panel is _never itself_ a scroll region; it is a backstop against its own static chrome (headers, controls, inputs) somehow outgrowing it on an extreme viewport, not a scroll boundary for legitimately unbounded content. Exactly _one_ designated inner region per panel owns that content and scrolls (`#ls-items`, `#viewer-body`, `#llm-response`), via `overflow: auto` + `flex: 1 1 0; min-height: 0` down the flex chain, so a panel never shows two live scrollbars at once. Content that can't live inside that one flex-managed region — the LLM panel's Profiles editor, which can grow arbitrarily tall (a long system prompt, the full tool list, three hook inputs) and has no natural "shrink to fit" behavior the way a virtualized transcript does — is pulled out into its own overlay (`.llm-profiles-overlay` / `.llm-profiles-modal`, fixed-positioned, its own single `overflow-y: auto`) instead of living inline in the panel's flow; this was a deliberate redesign after an inline version first grew the whole document past `100vh` (leaking past the panel with no overflow rule) and then, once the panel itself was given `overflow-y: auto` as a quick fix, produced a _visibly nested_ scrollbar (the panel's own, plus `.llm-tools-list`'s separate `max-height: 160px` cap) — both symptoms of the same root cause: unbounded form content living inside a panel's normal flow. Verified at 1000×500 (with the Profiles modal open and overflowing its own box), 1914×951, and 390×844 (mobile, where the grid stacks to one column): `document.documentElement.scrollHeight`/`scrollWidth` equal the viewport exactly in every case, and never more than one scrollbar is visible at a time.
- **Invariant — LLM history is append-only; compaction bypasses, never deletes.** The persisted transcript (`localStorage`) grows only: a compaction event appends a summary _marker_ message (`role: "user"`, `compaction: true`) and every pre-marker turn stays in the array and on disk. Prompt construction (the panel's `buildMessages`) sends the system prompt + the **latest** marker's content + the turns after it, so pre-marker turns are bypassed in the outgoing prompt while remaining fully recoverable for the UI and future re-summaries. Consequences that must survive any refactor: (a) markers are appended **only at turn boundaries** (before the turn's user message), so a marker can never split an assistant `tool_calls` message from its `tool` results — the `user` role is what keeps the post-cut sequence protocol-valid and must not change; (b) the UI render of a marker (a subtle divider) must agree with the prompt cut: markers _before_ the latest marker render as nothing; (c) the summarization call must prompt with the _already-compacted_ prefix (`buildMessages` output), never the full history, or it overflows the same window it is meant to rescue (see Potential Problems).
- **Invariant — persisted display-only fields are stripped at the wire boundary, exactly once.** A `ChatMessage` carries fields that exist for the UI alone and are meaningless or harmful to the model: `reasoning` (the model's chain-of-thought, which the proxy streams in a separate `reasoning_content` delta rather than inline in `content`). History is append-only on disk, so the field persists with the message; the outgoing prompt is built by exactly **one** converter (`toWireMessage` in `llm.ts`, applied per message by `toWireMessages`, which `buildMessages` uses and therefore by `summarizeConversation` too) that destructures the display-only fields away. Three consequences follow. (a) The strip must stay a **single chokepoint**: echoing the model's own reasoning back on the next request is both wasteful and actively misleading (the model would treat its prior thoughts as observed fact), so any new call site that builds a prompt must route through `buildMessages`/`toWireMessage` rather than passing `ChatMessage[]` straight to `sendLlmMessage`. (b) The strip must be **explicit and field-by-field** — today a destructure of the named display-only field — rather than a whitelist of wire keys: a new wire field (e.g. OpenAI's `name` or `refusal`) added to `ChatMessage` would be silently dropped by a whitelist, so the deny-list must be revisited whenever the wire shape grows. (c) The other UI bookkeeping flags (`compaction`, `endHook`) are **not** stripped — they ride along as unknown properties and are ignored by the proxy, which is harmless because they are booleans rather than content, but they are the reason a `ChatMessage` can never be `JSON.stringify`d straight into a request body without a deliberate decision. `images` is a second display-only field, on `tool` messages: images a tool returned (a browser screenshot). It is **never persisted** (a JSON replacer in `conversations.ts` drops it — base64 images would blow the localStorage quota) and **never sent as-is**: `toWireMessage` strips it, and `toWireMessages` instead delivers only the most recent images as a synthetic `user` message with `image_url` parts placed after the last tool message of the group (a `tool` message's content must stay text, and nothing may split an assistant's tool calls from their results). Note the deliberate asymmetry: `reasoning` is **persisted** (unlike a subagent trace or a subagent/end-hook display, which stay ephemeral) because it belongs to the reply it accompanied and must survive a reload, collapsed, next to that reply.

## Structure (module layout & dependency direction)

Dependency direction flows strictly inward; a layer may only import layers to its left.
`packages/shared` is the outermost contract layer: the apps depend on it, and it depends on nothing.

```
packages/shared/src/
  index.ts      # CONTRACTS (type-only): every cross-app shape the apps must agree on,
                #   expressed as types (e.g. the LLM tool-name union). It exports NO
                #   runtime values, so it is erased at emit in both the Vite bundle and
                #   the compiled backend — the backend's zero-runtime-deps invariant holds.

apps/backend/src/
  index.ts        # bootstrap: reads env, wires ctx, starts server (entry only)
  app.ts          # app factory: assembles router + server, request dispatch
  router.ts       # ROUTER: Route type, matchRoute, matchPattern (pure, no I/O)
  json.ts         # BODY: readJsonBody (inbound body parsing)
  http.ts         # RESPONSE: sendJson (the only *JSON* outbound serializer)
  watch.ts        # FS WATCH: createFileWatcher -> { start, close, subscribe }. Owns the
                  #   shared FSWatcher (root, recursive where supported) and a debounce
                  #   (1000ms) that coalesces per-path change/rename into WatchEvent
                  #   { path, event }. Path is root-relative, forward-slash, server-derived.
  fs.ts           # FS CORE: root-scoped path resolution (realpath-contained) + vetting
                  #   (validatePath) + existence guard (assertDoesNotExist) + createDir/createFile
                  #   primitives — the single place every fs mutation passes through
  routes/         # HANDLERS: one file per resource/endpoint group
    health.ts     #   GET /api/health
    hello.ts      #   GET /api/hello/:name
    echo.ts       #   POST /api/echo
    ls.ts         #   GET /api/ls/*  (root-scoped directory listing, "rest" wildcard)
    file.ts       #   GET /api/file/* (root-scoped content, size-capped, text-only)
                  #   PUT /api/file/* (root-scoped write, size-capped, text-only)
                  #   DELETE /api/file/* (root-scoped unlink, files only; 404 for dirs/missing)
    create.ts     #   POST /api/file, POST /api/dir (root-scoped creation via the
                  #   fs.ts createDir/createFile cores; HTTP semantics only)
    llm.ts        #   THIN REGISTRY + routing only (split out of a single file once it
                  #   crossed the 500-line cap — see llmCommand.ts/llmFs.ts/llmSearch.ts
                  #   below): isLlmToolName, the create_subagent/ask_questions throwing
                  #   stubs (they exist only for the Record<LlmToolName, ...>
                  #   exhaustiveness check — the frontend intercepts and fulfills both
                  #   itself, a nested loop / an interactive question card, never
                  #   reaching this route), the `tools` name→handler registry built from
                  #   the three sibling modules' exports, and the two HTTP routes:
                  #   POST /api/llm/tool (dispatches into `tools`; errors resolve to 200
                  #   + "Error: …" so the model adapts) and POST /api/llm/hook-command (a
                  #   second, non-tool route: runs a command through llmCommand.ts's
                  #   runShellCommand core — the same one run_command uses — but returns
    browser/      #   BROWSER SESSION: the app-owned Playwright session the eleven
                  #   browser tools (open, snapshot, click, type, drag, hover, navigate,
                  #   read, run_code, screenshot, dialog) drive, owned by
                  #   AppContext (ctx.browserSession) and closed in close() — see the
                  #   "long-lived resources" invariant above. Every action re-collects a
                  #   numbered snapshot of interactive elements before acting so the
                  #   model's element indices stay live. Split by dependency direction:
                  #     elements.ts  - PURE: INTERACTIVE_SELECTOR, ElementKind, kindOf,
                  #                    labelOf, RawElement/SnapshotEntry (no Playwright
                  #                    import, unit-testable in Node)
                  #     snapshot.ts  - collectTargets (one page.evaluate, capped at
                  #                    MAX_SNAPSHOT_ELEMENTS) + snapshotText
                  #     targets.ts   - the single element-number validator: parses numeric
                  #                    args (n / from / to) and range-checks them against
                  #                    the same capped list the snapshot printed, returning
                  #                    Targets or a badRequest; click/type/drag never
                  #                    re-implement it
                  #     actions.ts   - one small function per page-acting tool (click, type, drag,
                  #                    hover, navigate, read, run_code), collected in the `pageActions` record
                  #                    taking (page, args); drag releases the mouse in a
                  #                    finally so a failed move never leaves it held down
                  #     dialogs.ts   - holds JS dialogs open (no Playwright auto-dismiss):
                  #                    guard() reports a dialog an action opened and
                  #                    refuses new actions until browser_dialog answers it;
                  #                    clears a stale dialog on navigation/page close
                  #                    plus screenshot(), the one tool returning an
                  #                    image (LlmToolResult {text, images})
                  #     codeRunner.ts - runs browser_run_code snippets in a `node --permission`
                  #                    child attached over CDP; killed on timeout
                  #     gate.ts      - createPageGate: owns Chrome (launched with a localhost
                  #                    debugging port for codeRunner) + the single page
                  #                    (ensurePage, close) and the gate (a promise chain)
                  #                    that runs every tool and the panel's navigate one
                  #                    at a time
                  #     session.ts   - createBrowserSession: wiring only; the four
                  #                    page-acting tools share one act(tool, args)
                  #     screencast.ts / view.ts - the panel-facing stream and input
                  #   Dependency direction: session -> actions -> targets -> snapshot ->
                  #   elements; nothing imports back up.
                  #   {stdout, stderr, truncated, timedOut} structured JSON instead of one
                  #   formatted string, since the panel's end-of-turn hook must tell
                  #   stdout from stderr apart. Errors are thrown AppErrors like every
                  #   other JSON route, not caught into a 200 — unlike /api/llm/tool this
                  #   isn't model-facing).
    llmToolTypes.ts #  The one shared type (LlmToolHandler) all four llm* modules need,
                  #   in its own type-only file so none of them has to import another's
                  #   internals just to name it — erased at compile time, no runtime cost.
    llmCommand.ts #   OS command execution: run_command (the shell via
                  #   node:child_process, spawn + taskkill /T /F — timeout,
                  #   process-tree kill, single-flight guard, 1MB output cap) and the
                  #   exported runShellCommand core both llm.ts's hook-command route and
                  #   run_command itself call.
    llmFs.ts      #   The filesystem CRUD tools — list_directory, read_file, edit_file,
                  #   create_directory, create_file, delete_file (unlink),
                  #   delete_directory (rm recursive) — reaching fs only via fs.ts.
    llmSearch.ts  #   find_files and search_files, sharing a `listWorkspaceFiles` helper
                  #   (shells to `git ls-files`, returns git-relative names, a read-only
                  #   OS escape) and a `requirePattern` regex-validation helper.
                  #   find_files matches names against that list alone (git via execSync,
                  #   10MB buffer, 500-match cap); search_files goes on to read each
                  #   candidate's content through the normal resolveWithinRoot/fs.ts path
                  #   (so its content-reading half is fully sandboxed) and matches its
                  #   regex per line, skipping binary/oversized files, capped at 200
                  #   matches total and 50 per file — a file that hits the per-file cap is
                  #   named in the result's closing note even when the total cap is never
                  #   reached, so a truncated file's matches are never silently implied
                  #   complete.
    watch.ts      #   GET /api/watch (SSE: subscribes the shared watcher, streams WatchEvent
                  #   frames, unsubscribes on res close). The one non-JSON route; owns res.
  errors.ts       # error model: AppError type/enum, toResponse mapping
  context.ts      # AppContext definition + createContext (shared deps)

apps/frontend/src/
  main.ts         # bootstrap: mounts render into #app (entry only)
  render.ts       # THIN composition: sets the full page HTML template, runs the health()
                  #   check, then delegates each panel to components/ — await setupFileViewer(root)
                  #   (tree + editor; captures its returned FileViewerHandle) and
                  #   setupLlm(root, fileViewer) (chat). Owns no panel logic itself.
  dom.ts          # shared DOM helpers (makeButton, ...)
  highlight.ts    # SYNTAX HIGHLIGHT: pure line tokenizer + thin DOM appender (see invariant below)
  diff.ts         # DOM-free line-diff math for the live edit_file preview: buildDiffRows
                  #   (single-hunk unified diff — context/removed/added rows, dual old/new
                  #   line numbers) + clampEditRange (mirrors the backend's end_line clamp).
  api/
    client.ts     # fetch wrapper: typed calls, base path, error normalization. Also hosts
                  #   subscribeToChanges(onEvent), the single place that opens the /api/watch
                  #   EventSource and hands parsed WatchEvent objects up (returns a close fn).
  llm/
    partialJson.ts  # DOM-free: extractPartialJsonString/extractPartialJsonNumber pull a
                    #   field's value out of a tool call's still-streaming, possibly-invalid
                    #   JSON arguments text — see the LLM panel section.
  components/     # self-contained views/widgets, one file each
    contextMenu.ts  #   reusable context menu (makeContextMenu / showMenu / hideMenu)
    createDialog.ts #   new-file / new-directory modal (showCreateForm)
    fileTree.ts     #   file tree + viewer/editor panel: a thin DOM controller exposed as
                    #   setupFileViewer(root), returning a FileViewerHandle (beginEditDiff/
                    #   updateEditDiffNew/endEditDiff) the LLM panel uses to preview an
                    #   in-flight edit_file call live, in this panel, as an inline diff — see
                    #   the LLM panel section. Renders the listing (renderListing/renderEntry)
                    #   and the always-edit overlay editor (renderEditor: transparent textarea
                    #   over a live-highlighted backdrop + line-number gutter) — renderEditor
                    #   is also the one place that resets activeDiff to null, since normal
                    #   navigation always supersedes a live preview. Reached via
                    #   listDir/getFile/putFile/apiDelete in api/client.ts. Live reflection:
                    #   tracks expandedDirs and, on a debounced (80ms) WatchEvent, re-fetches
                    #   the root + each expanded dir (depth-ordered) and re-renders; reloads the
                    #   open file when it changed on disk, or marks it "(out of date)" if dirty.
    fileState.ts    #   DOM-free editor/file-state store (target): owns the open file's
                    #   content/rel, the dirty flag, the save timer, and the save lifecycle
                    #   (schedule/flush/save + the "abort navigation on a failed flush" rule).
                    #   Mirrors conversations.ts so the auto-save data-safety invariant is
                    #   unit-testable without a DOM; fileTree.ts then only paints and forwards
                    #   user actions (note: the multi-tab feature has since pushed that
                    #   controller well past the 500-line cap — see Future Work).
    tabs.ts         #   DOM-free viewer tab store: owns the ordered list of open tabs
                    #   (each a Tab = {id, rel, kind?}, where rel is a workspace-relative
                    #   path or a URL and kind is "file" | "url"; kind is optional and
                    #   defaulted to "file" for rows persisted before URL tabs existed)
                    #   and which tab is active. Persists to vise:viewer:tabs (+
                    #   vise:viewer:active) with structured validation (isValidTab),
                    #   mirroring conversations.ts/profiles.ts/skills.ts so it runs under
                    #   Jest in Node (tabs.test.ts). API: activeId/getActive/getTabs,
                    #   open(rel, kind?) (activates an existing tab for the same rel rather
                    #   than duplicating; kind defaults to "file"), close(id) (closing the
                    #   active tab promotes the first remaining; closing the last leaves the
                    #   store empty), and activate(id). It deliberately does NOT own the
                    #   per-tab FileStateStore buffers: those need the network `persist`
                    #   callback and the DOM save-status span, both controller concerns, so
                    #   fileTree.ts keeps one FileStateStore per file tab plus a per-tab text
                    #   map and consults this store only for the open set and the active id
                    #   (URL tabs own no buffer — fileTree.openUrl renders an <iframe>).
    llm.ts          #   LLM chat panel: a thin DOM controller over the conversation AND
                    #   profile stores. Queries elements, builds both stores, wires render
                    #   fns + events (including the Profiles modal: profile create/rename/
                    #   delete, its allowed-tools checklist via renderProfileToolList, and
                    #   its three hook inputs — opened via a "Profiles" button next to the
                    #   conversation's profile <select>, closed via its own Close button,
                    #   Escape, or a backdrop click, mirroring createDialog.ts's overlay
                    #   pattern; kept out of the panel's normal flow specifically so its
                    #   unbounded content never needs a second scrollbar nested inside the
                    #   panel's — see the viewport invariant). Runs a bounded
                    #   tool-call loop (list_directory, read_file, edit_file,
                    #   create_directory, create_file, run_command — which must surface a
                    #   confirm-before-run gate) and forwards each model call to the backend
                    #   /api/llm/tool route. Holds the turn loop (runTurn), prompt builder
```

Target invariants (implemented in the backend):

- `router.ts` is pure (Route type + matching) and imports no I/O — trivially unit-testable.
- Each `routes/*.ts` is a self-contained resource module: `(ctx) => Route[]`. Adding an endpoint = adding a file, no edits to `app.ts`.
- `app.ts` is thin: register route groups, wrap the server, wire body parsing + error handling. It contains no handler bodies or matching logic.
- `context.ts` owns `AppContext`; the context is constructed once (in `index.ts`) and passed into `createApp` — no module-level singleton. The app's long-lived resources are all context members, created inert in `createContext` and torn down in `close()`: the live-reflection `fileWatcher` (`start()`ed in `createApp`, closed in `close()`) and the model-driven `browserSession` (a Playwright session lazily opened on first `browser_open` and closed in `close()`). Both obey the "app lifecycle owns long-lived resources" invariant — the browser session's state (the Chrome `Browser`/`Page` handles) lives inside the `BrowserSession` object the context owns, not in a module-level singleton, so the app's resource lifetime is visible in one place. Residual: `close()` tears the watcher down only after `server.close()` drains, and a live SSE stream never drains on its own, so `closeAllConnections()` is needed (see Potential Problems).
- Frontend `api/client.ts` is the single place that knows the base URL and normalizes network/HTTP errors, so views never call `fetch` directly. Every endpoint is wrapped (`listDir`, `getFile`, `putFile`, `deleteFile`, `createEntry`, `health`); the `fail(res)` helper centralizes the "parse body → read `message` → throw `Error`" normalization.
- **Invariant — file content is rendered as text, never as HTML.** `highlight.ts` tokenizes one line into runs and `render.ts` inserts every run via `textContent`/`createTextNode`. File content must never reach the DOM through `innerHTML`/`insertAdjacentHTML`, so arbitrary (attacker- or binary-) file bytes cannot inject markup/scripts. Keep the tokenizer pure (a line in, `Token[]` out) so it stays trivially testable and split-free, and keep the DOM-appending as a thin separate function.
- **Invariant — the always-edit overlay keeps both text layers on identical font metrics.** Every file opens in the editor: a transparent-text `<textarea>` (`color: transparent`, `white-space: pre`, no wrap) absolutely positioned over a live re-highlighted `<pre>` backdrop, with a sticky line-number gutter. The two layers only align pixel-perfectly if `font-family`/`font-size`/`line-height`/`tab-size`/`padding`/`margin` are identical on both. Because a `<pre>`'s UA stylesheet forces `font-family: monospace` (overriding inheritance), the backdrop must set the exact mono stack explicitly — relying on inheritance re-introduces ghosted/doubled text. The overlay container (`.editor-scroll`) is the sole scroller; `#viewer-body` is `overflow: hidden` so exactly one scrollbar shows.
- **Invariant — auto-save lifecycle is loss-free on navigation.** The editor debounces saves (`AUTOSAVE_MS`). `viewer.dirty` is the single source of truth for "unsaved work exists"; the `.save-status` span reflects it (`unsaved`/`saving`/`saved`/`error`). Before switching files (`viewFile`) and on `beforeunload`, `flushSave` clears any pending timer and persists a dirty buffer. If that flush **fails**, navigation must be aborted (no re-render) so the in-memory edit is never discarded — the current edit stays in the textarea and `dirty` remains true.
- **Invariant — a profile's tool allowlist never changes the _main conversation's_ tool `definitions` array (KV-cache preserving).** Each Profile (`profiles.ts`) carries `allowedTools: string[]` — an allowlist, not the old per-conversation `disabledTools` denylist it replaced, but the mechanism is unchanged: `llmToolDefinitions` is always sent **unchanged** to `sendLlmMessage` for the main loop, so the request prefix (and the server's KV cache) is stable. `disabledFromAllowed(profile.allowedTools)` derives the complement once per turn; disallowing a tool only (a) **appends** a note to the profile's own system prompt (`systemPrompt(ctx)` — byte-identical to `ctx.base` when nothing is disallowed) and (b) **short-circuits** the client-side execution of a disallowed tool with a model-readable result (`disabledToolResult`), so no backend call is made. Do **not** filter the definitions array in the main loop to drop disallowed tools — that is the exact thing the feature is designed to avoid. A **subagent's** offered tool list is the one deliberate exception: it _is_ filtered to `profile.allowedTools` (`subagentToolDefs`), because it already excluded `create_subagent` before profiles existed — each subagent run is a fresh, single-shot conversation with the model anyway, so there is no ongoing per-conversation KV cache to preserve across turns the way there is for the main loop.

**Why the layering matters (recursion):** router (pure), response (I/O), and routes (handlers) are separated so dependency edges point one direction. This keeps the code splittable: any future split of a file cannot introduce a circular import, because the pure core never imports the I/O or handler layers.

## Potential Problems (risks, limits, failure modes)

- **LLM traffic has no production path.** The `/llm` route exists only in `vite.config.ts` (dev server). The built SPA (`pnpm build`) calls `/llm/...` with no route behind it — the panel 404s in any production deployment. Decide the production story when it is needed: a same-origin reverse-proxy rule, or a backend route that forwards to `:8080` (keeps the key off the browser _and_ gives the API a single host). Until then the panel is dev-only and that is acceptable for a local tool.
- **The virtual list does not know when an inline `<details>` toggles (top UI issue).** `VirtualList` measures each block's height on `layout()` and only re-runs on scroll (rAF-throttled) or an explicit `refresh()`. A `<details>` block (the reasoning block; already true of the subagent block) can change its own height on user click without the list noticing, so the recorded heights — and therefore the spacer height and every subsequent block's `top` — go stale: the following block overlaps the expanded one (measured ~14–32px) and the conversation loses that much scroll height. Scrolling heals it only because scroll triggers `layout()`; a user who merely clicks and reads sees the collision. Fix: have the view listen for the `toggle` event on any `<details>` it renders and call `refresh()`, or (better) give `VirtualList` a `ResizeObserver` on the live nodes so any height change re-lays-out without depending on scroll. Documentation-only `<details>` are safe to avoid until then.
- **A conversation switch no longer strands the streaming turn (fixed) — but Stop and the `ask_questions` pause don't know about each other.** `setupLlm` now holds one `AbortController` per turn (`activeTurn`), threaded as `signal` through `submitTurn` → `runTurn` → `streamLlmMessage`, and `doNew`/`doDelete`/`switchConversation` all call `activeTurn?.abort()` — so `fetch` itself is cancelled at the source instead of an abandoned stream being filtered after the fact. `#llm-send` reuses the same controller as a Stop button (`send.dataset.mode`), and `runTurn` checks `signal.aborted` right after `streamLlmMessage` returns to finalize early with whatever text streamed so far. That much is solid and browser-verified (Stop mid-stream persists the partial reply; New/Delete/switch mid-stream cleanly abort the fetch and roll back). The gap: **`ask_questions` is a separate pause mechanism** (`pendingAsk`, a plain `Promise` parked in `resolveToolCall` → `askQuestions`, resolved only by the card's Answer button or by `resolvePendingAsk()`) that the `AbortController` knows nothing about. `doNew`/`doDelete`/`switchConversation` happen to work anyway because they call `resolvePendingAsk()` _and_ `activeTurn?.abort()` together — the resolve unblocks the parked `await`, and the loop then finds the signal already aborted (or the conversation switched) on its next step. The Stop click handler was not given the same pairing: it calls only `activeTurn?.abort()`. Verified live: sending a prompt that triggers `ask_questions`, then clicking Stop while the card is showing, does **nothing visible** — `send` stays stuck on `data-mode="stop"`/"Stop" with no feedback, because there is no in-flight `fetch` for the abort to cancel and nothing wakes the parked `askQuestions` promise. The abort only takes effect later, when the user finally answers the card: the tool result is recorded, the loop advances, calls `streamLlmMessage` with the now-already-aborted signal (an immediate no-op fetch), and `runTurn`'s `if (signal.aborted)` branch fires — discarding the model's turn entirely and appending the generic `"(Stopped before the model replied.)"` placeholder right after the user's answer, which reads as a non sequitur. Fix: have the Stop click handler call `resolvePendingAsk()` alongside `activeTurn?.abort()`, exactly like the other three call sites.
- **The LLM key is hardcoded in `client.ts` (dev-only, to be removed).** It is committed to the repo and baked into the bundle. Fine for a single-user local tool, but it violates the key invariant: move it to a gitignored `.env` consumed via `import.meta.env.VITE_LLM_API_KEY` and surface a clean empty state when absent.
- **No focus trap in dialogs (UI).** The create dialog is `role="dialog" aria-modal="true"` and dismissible via Escape/overlay-click, but Tab cycles through the whole page (buttons, tree toggles) rather than staying inside the dialog. Keyboard users can tab "out" of the modal; add a lightweight focus trap (cycle between the input and the Cancel/Create buttons) when the dialog component is extracted.
- **Create path: check-then-write race and leaf-not-realpathed (acceptable now, watch it).** The create cores in `fs.ts` run `assertDoesNotExist` (stat) _before_ `writeFile`/`mkdir`, so there is a TOCTOU window, and `resolveForCreate` realpaths the _parent_ only — the new leaf is trusted via name vetting, not re-checked with realpath after creation. For a single-user, root-scoped tool this is fine (and `O_EXCL`/`mkdir` semantics make the practical race a clean 400), but if the server ever becomes multi-user or is pointed at a shared/mutable volume, convert the create to `open(..., O_CREAT | O_EXCL)` for files and rely on `mkdir`'s `EEXIST` for dirs, and re-verify the final realpath is inside the root.
- **Writes have no freshness / conflict guard (now more live with auto-save).** `PUT /api/file/*` overwrites unconditionally. There is no `ETag`/`If-Match` (or content-hash) check, so a save made from a stale read silently clobbers any change made to the file between the `GET` and the `PUT`. Auto-save raises the write frequency, so this is worth doing sooner: add an `ETag` (content hash) to the `GET` response and require `If-Match` on `PUT` (return 409 on mismatch) so concurrent edits surface as a conflict instead of a silent overwrite.
- **Writes are not atomic.** `writeFile` truncates-then-writes in place; a crash mid-write leaves a truncated file. Write to a temp file in the same directory and `rename` it over the target for atomicity once the write path gains real usage.
- **Unbounded directory listings (DoS surface).** `readdir` has no cap on entry count and the response is fully buffered/serialized in memory. A directory with millions of entries (e.g. a large `node_modules`) is listed, sorted, and serialized whole. No pagination, no max-entry limit, no depth guard. Client-side expansion is user-driven (one dir per click) so the blast radius is a single request, but it can still stall a worker.
- **`matchPattern` is a linear scan per request** and re-parses patterns on every call. Fine at this scale; at scale, precompile routes at startup (see Performance). The trailing `*` wildcard is correct for the `rest` capture, but it only matches when `*` is the _last_ segment — non-trailing wildcards return `null` (documented behavior; keep it that way).
- **No request-size / timeout guards** on `readJsonBody`; a huge or slow body is buffered unbounded.
- **Frontend: touch targets are just under the comfortable minimum.** The expand/collapse toggle (`.toggle`) is 22×22px (20×20 content + 1px border) — under the ~24px comfortable floor, and the file rows rely on the whole `.row` for the click area. Keyboard focus _is_ visible (the UA focus outline is not suppressed and `aria-expanded` is set), so the earlier "no focus ring" gap is gone; only the small hit area remains. Bump `.toggle` to ≥24×24 (or pad the clickable region) when the tree component is extracted.
- **The transcript's follow pill overlaps message text instead of reserving space for itself.** `.llm-follow` is `position: sticky; bottom: 10px` as a plain flow child of `#llm-response` — it has no gutter of its own, so it floats over whatever content is scrolled underneath it. Verified live (60-message seeded conversation): with follow off and the view scrolled mid-history, a wrapped message block's last line rendered behind the opaque pill (block bottom at 881.6px vs. the pill's top at 851px, in the same viewport). It only avoids this at the exact bottom because `scrollToBottom()` happens to leave a few px of clearance there; anywhere else in the (now common, since scrolling away from the bottom to read history while follow auto-disables is the feature's whole point) mid-history scroll range, a line can be obscured. Fix by reserving room for the pill rather than overlaying it — e.g. `scroll-padding-bottom`/extra bottom padding on `#llm-response` sized to the pill's height, or moving the pill outside the scrolling element (an absolutely-positioned overlay on a non-scrolling wrapper around `#llm-response`) instead of `sticky` inside it.
- **Error messages are terse.** The `AppError` model exists and 500s no longer leak raw `String(err)`, but the generic messages (`resource not found`, `internal server error`) don't fully answer what/where/why/how. The `ls` handler also leaks the resolved absolute `path` and raw `fs` error text into the JSON body — fine internally, but keep the response shape stable.
- **Shutdown does not terminate in-flight SSE connections (top issue).** The watcher now has a real lifecycle owner (context member, `start()` in `createApp`, closed in `close()`), so the module-singleton and "no owner" concerns are gone. But `close()` runs `server.close(cb)` and calls `ctx.fileWatcher.close()` only _inside_ `cb`, and `server.close()` does not fire `cb` until every existing connection drains — an open `/api/watch` stream never drains on its own. So while a browser tab has the live-reflection stream open (the normal state), Ctrl-C / SIGTERM hangs: the watcher never closes and the `process.exit(0)` in `index.ts` is gated _after_ `app.close()`, so it is a no-op, not a safety net. Fix: call `server.closeAllConnections()` (Node ≥18.02) inside `close()` before/alongside `server.close()`, so open SSE connections terminate and the close callback — and with it the watcher teardown and the exit — actually run.
- **The SSE route is one, and it coexists with the JSON-only request loop by accident.** The dispatch loop in `app.ts` reads a JSON body on _every_ request and funnels errors through `toResponse`. `GET /api/watch` (the one `text/event-stream` route) works only because an empty GET body parses to `null` and the handler writes to `res` directly, bypassing both. That is fragile: a streaming route must be explicitly recognized (skip body read + `toResponse`, let it own `res`) or the invariant is being papered over. Today there is exactly one; the dispatch loop has no notion of a "streaming" route kind.
- **`/api/watch` emits no heartbeat and the fallback is silent.** After the `:ok` prime there is no periodic keep-alive comment, so a proxy/LB that drops idle connections sees a silent stream (the browser `EventSource` auto-reconnects, healing it — acceptable for a local tool, but a `:ping` every ~15s is cheap insurance). Separately, `watch.ts` falls back to a _non-recursive_ root-only watch when `recursive` is unsupported (Linux without inotify-recursion): nested changes are silently missed and the UI goes stale with no indication. Surface the degraded mode (a `degraded: true` field or a one-time log) so a stale tree is explainable.
- **Live-reflection debounce drops intermediate events and can re-locate dead nodes.** The frontend debounce (80ms) keeps only the _last_ event's `path`, so a create+delete inside one window nets to nothing and no refresh fires for that file — a benign edge for a human-paced tool, but worth noting. `liveRefresh` re-locates each expanded dir's `<li>` by walking the DOM and matching `.name` text; if a dir was removed on disk, `findDirLi` returns `null` and it is skipped, so a stale `expandedDirs` entry leaks until the next collapse/expand. Harmless (a `Set` of strings) but unbounded in principle; clear it on a root refresh.
- **Multi-conversation titles: empty conversations are now distinguishable (fixed).** `deriveTitle(messages, idSuffix?)` falls back to `"New conversation"` for any conversation with no user message, but when `idSuffix` is supplied it returns `"New conversation · <suffix>"`. Both empty-conversation creation sites (the first-run seed and `newConversation`) pass the new id's first 4 chars, so several empty conversations stay tell-apart in the `#llm-conversation` select. Titles derived from a user message carry no suffix (they are already unique-ish). Consider making titles _editable_ so a conversation is always addressable by a label the user chose — that is the remaining, optional refinement.
- **Compaction: the summarizer call can overflow the window it is rescuing (fixed: it now prompts with the compacted prefix).** The 80% trigger fires when the _last_ prompt was already ≥ 80% of `n_ctx`; `summarizeConversation` previously sent the **full, un-compacted** history (system + everything) — strictly larger than the prompt that just measured ≥80% — so on llama.cpp the rescue call would 500/degrade past `n_ctx`, fail like the turn it saves, and drop the user's just-sent message (rollback to `preLength`). It now sends `buildMessages(history)` (the already-cut prefix) per the append-only invariant, so the rescue prompt is never larger than the one that triggered it. Residuals to watch: (a) an empty summary produces no marker and silently retries every turn — acceptable, but a "compaction failed, context near limit" hint would surface it; (b) token measurements are per-model: after a model switch, `lastPromptTokens` (measured under the old model) is compared against the new model's `n_ctx` — reset `lastPromptTokens = undefined` on model change to make the metric honest again.
- **`run_command`'s process-tree kill is Windows-only, and there is no UI confirm gate.** The timeout now kills the tree via `taskkill /T /F` (Windows) and the single-flight guard bounds concurrency, but on a non-Windows host `taskkill` does not exist so the kill degrades to `child.kill()` on the top-level shell only — descendants (`pnpm`/`node`/`git`) survive the timeout. The confirm gate (invariant above) is also not implemented: the panel dispatches a model-requested command with no human approval, so a single turn (or a prompt-injected file) can run it unattended. (The arbitrary-PowerShell tradeoff itself is _accepted_ for this single-user, local-only tool; do not re-architect toward a full sandbox.)
- **The sandbox guard blocks escape; destructive tools additionally reject the root itself (fixed).** `resolveWithinRoot` returns the root unchanged when `realTarget === realRoot`, so a root alias (`"."`, `""`, an absolute-in-root path) _would_ pass `isDirectory()` and let `rm(realRoot, { recursive: true })` wipe the whole workspace in one model call. The guard is now in place: both `delete_file` and `delete_directory` reject `realTarget === realRoot` (`badRequest("cannot delete the workspace root")`), so the root cannot be a delete target even though it is a valid in-root path. `delete_file` is _additionally_ safe on the kind check (a root is a directory, so `isFile()` fails), but the explicit root guard is the load-bearing defense — do not rely on the kind check alone.

- **The end hook's own execution failure could discard an entire turn's persisted history (fixed).** The startup and turn hooks run through `executeLlmTool` (`POST /api/llm/tool`), which the backend deliberately resolves every failure into a `200` + `"Error: …"` string, so a broken hook command degrades to visible text and never throws. The end hook instead calls `runShellCommand` (`POST /api/llm/hook-command`), which by design throws a normal `AppError` on a spawn failure or on the shared `commandInFlight` single-flight collision (reachable in practice from two browser tabs/conversations each dispatching a hook or `run_command` against the same backend at once, since the guard is a single module-level flag, not per-conversation). `runTurn`'s end-hook branch previously let that rejection fall through to the turn's outer `catch`, which calls `store.rollbackTo(preLength)` — discarding the user's message and every tool call/result and assistant reply from that turn, even though any file-mutating tool calls in it already ran and were _not_ rolled back on disk, with the user seeing only a generic "Request failed" and no indication the workspace was actually changed. The end-hook branch now wraps `runShellCommand` in its own local try/catch: a thrown failure is shown via `appendEndHookResult` and fed back to the model as a blocking retry turn (`endHook: true`, same as a non-empty-stderr rejection) instead of propagating to the whole-turn rollback.
- **A passing end-hook check renders identically to a blocking one (verified live).** `renderItemDom`'s `"end-hook"` case and `.llm-end-hook` in `llm.css` apply one unconditional danger-red left border/background to every `appendEndHookResult` block, regardless of whether `formatEndHookOutput`'s embedded status line reads `ok` or `stderr present` — confirmed by rendering both side by side, both computed to the same `rgb(194, 91, 78)` border. Since this ephemeral block is the _only_ UI signal a passing check ever leaves (a pass is never persisted), color is doing real communicative work here; a clean turn currently looks identical to a rejected one. Add a passed/blocked modifier class (or distinct styling) so the two are visually distinguishable at a glance.
- **The live `edit_file` diff preview (`fileTree.ts`'s `beginEditDiff`/`updateEditDiffNew`/`endEditDiff`/`cancelEditDiff`, driven by `llm.ts`'s `handleEditAnimChunk`/`resyncEditDiff`) had three correctness gaps; two are fixed, one remains open.** All three were preview-only — the file the backend actually writes has always been correct, since `editFileRange` (`llmFs.ts`) computes its own range independently — but a wrong live preview is still visibly wrong to the user watching it stream, which is the feature's entire point. **(1, open) The supersede-guard is a null-check, not an identity-check, so two `edit_file` calls in one streaming round can corrupt each other's preview.** `Viewer.activeDiff`'s own doc comment states "its identity — is the guard," but `updateEditDiffNew`/`endEditDiff`/`cancelEditDiff` in `fileTree.ts` only test `viewer.activeDiff !== null`; they never confirm the `ActiveDiff` object they are about to touch is the one their caller actually opened. `beginEditDiff` is async (it awaits `store.flush()` then `getFile`), and `handleEditAnimChunk`/`resyncEditDiff` call it as soon as a call's `path`/`start_line` resolve — so if a streaming round contains two `edit_file` calls, each gets its own in-flight `beginEditDiff` promise, and whichever happens to _resolve_ last wins `viewer.activeDiff`, regardless of which call is chronologically later in the model's own token stream. A slow first call resolving after a fast second call silently tears out the second file's live diff DOM and replaces it with the first's; the first call's still-queued `EditAnimTrack.active.then(...)` chunk updates (in `llm.ts`) then keep writing into whatever `addedContainer` is current, which may now belong to the wrong call. Fix: have `beginEditDiff` hand back an opaque per-call token (or the `ActiveDiff` object itself) that `updateEditDiffNew`/`endEditDiff`/`cancelEditDiff` must be passed and compare by identity, instead of reading the shared `viewer.activeDiff` unconditionally. **(2, fixed) `clampEditRange` (`diff.ts`) now clamps `start_line` the same way it already clamped `end_line`.** `editFileRange` (`llmFs.ts`) never rejects a `start_line` beyond the file's length — `lines.slice(0, startLine - 1)` on a too-large index just returns the whole array via `Array.prototype.slice`'s own clamping, so any `start_line > lines.length` behaves identically to `start_line = lines.length + 1` ("append at end"); `clampEditRange` mirrors that now too (`Math.min(startLine, lineCount + 1)`), so `buildDiffRows`'s leading-context loop no longer renders dozens of bogus blank "context" rows for a wildly out-of-range `start_line`. Covered by `diff.test.ts`. **(3, fixed — and this one didn't stay theoretical) The `end_line`-omission heuristic assumed a field order the same function's own comment says isn't reliable, and was caught live within minutes of shipping.** `handleEditAnimChunk` treats a missing `end_line` as genuinely omitted (defaulting to `start_line`, a pure insert) once `'"content"'` appears in the accumulated arguments text, reasoning that `content`'s appearance proves the object won't grow further before `end_line` would — but a real local model was observed emitting `end_line` _after_ `content` (a live reproduction of the exact same field-order risk the `start_line`-before-`content` case already documented), which made the heuristic lock in a wrong "insert" shape for what was actually a 3-line replace, visibly, in the settled diff. Rather than trying to out-guess field order with a smarter heuristic (an unbounded game against whatever a given model happens to do), the fix is a self-healing resync: once a round's `reply.tool_calls` is fully known (valid, complete JSON, no more ambiguity), `resyncEditDiff` re-parses the call's real `path`/`start_line`/`end_line`/`content` and calls `beginEditDiff` again against the correct range — _before_ `resolveToolCall` executes the edit and the pre-edit "old" snapshot is lost — so whatever the live mid-stream portion guessed, the version the user actually reads once it settles (`endEditDiff`'s "Edited"/OK button state) is always correct. The live-only heuristic itself is untouched and can still flicker to a momentarily wrong shape while streaming; only the settled result is guaranteed.
- **The `edit_file` diff preview's settled state now waits for an explicit dismiss (OK button) instead of auto-reloading.** `endEditDiff(ok)` stops the live cursor, shows "Edited"/"Edit failed" plus an **OK** button in `#viewer-actions`, and leaves the full red/green diff up — clicking OK is what reloads the file from disk into the normal (non-diff) editable view, which still reflects the edit's real result; only the diff coloring goes away, not the content. A turn abandoned before the call ran (Stop, or a conversation switch/rollback) uses the separate `cancelEditDiff()` instead, which reloads immediately with no dismiss step, since there's no real outcome to show or wait on.
- **The OK button's "leave it up until dismissed" promise being silently defeated by the live-refresh watcher (fixed).** `liveRefresh` (`fileTree.ts`) used to reload the open file with no regard for `viewer.activeDiff`, and since `beginEditDiff` never touches `viewer.store`'s `rel` (only `viewFile`/`loadIntoViewer` call `store.beginLoad`), `openRel` was whatever file was last explicitly opened in the plain editor — exactly the edited file itself in the mainline "I have this file open, please fix it" flow. The edit's own write is a real `fs.writeFile` the backend's `fs.watch` cannot help but see (1000ms debounce, `watch.ts`), pushed over `/api/watch` and re-debounced 80ms client-side, so `liveRefresh` fired roughly 150-300ms after `resolveToolCall` resolved — almost always before a human reacts and clicks OK — silently collapsing the diff back to the plain view via `loadIntoViewer` → `renderEditor` (which unconditionally nulls `activeDiff`). Because the resulting DOM was indistinguishable from what clicking OK would have produced, this was easy to miss even while deliberately testing the button. Fixed: `liveRefresh` now returns early, before touching `viewer.store` at all, when `viewer.activeDiff?.rel` matches the changed path — leaving the diff exactly as `endEditDiff` left it; a background change to a file with no diff showing still refreshes normally (verified live: re-ran the same scenario with the file open manually beforehand, confirmed the diff and its OK button survived 800ms past the edit landing on disk, that clicking OK still correctly dismissed it, and that an unrelated external change to the same file still auto-refreshed normally with no diff active).

## Performance (obvious concerns only — profile before optimizing)

- Live reflection adds two costs to watch: (a) the backend `fs.watch` is recursive over the whole root, so a large tree (e.g. `node_modules`) produces a high event rate that the 1000ms debounce coalesces by _path_ — cheap per flush, but the watcher itself tracks every file; consider an ignore list for `node_modules`/`.git` if the root is large. (b) Each debounced `liveRefresh` re-fetches the root plus every expanded directory (N+1 requests per burst); fine for a few expanded dirs, but cap or batch if the tree grows. The SSE stream holds one open connection per browser tab — unbounded subscriber count is not guarded (a per-subscriber cap is cheap insurance).

- Route matching is a per-request linear scan with per-call pattern splitting; precompile the route table at startup (regex/radix) when endpoint count grows.
- Body buffering is unbounded; bound it and stream once payloads get large.
- Directory listings are fully read, sorted, and serialized in memory; cap/paginate once directory sizes are large.
- The dev proxy adds one hop in development only; it is absent in a same-origin production deployment.
- Frontend: lazy per-directory fetch on expand (no preloading). When the tree grows, consider caching expanded state so collapse/re-expand is free, and avoid re-fetching an already-loaded listing.
- The viewer materializes one DOM node pair (`.line` + line number + text) per line. A ~1 MB file (the preview cap) is thousands of lines → tens of thousands of nodes in a single scroll region. Fine for small files; profile before assuming, and reach for virtualization only if a real file makes the scroll region lag. (The LLM transcript no longer has this problem — `messageView.ts`/`VirtualList` window-renders only the visible blocks, so its DOM stays bounded regardless of conversation length; the file viewer is the one remaining unbounded-DOM surface.)
- Streaming rewrites the _whole_ accumulated reply into `streamTextEl.textContent` (and the whole reasoning into the reasoning body) on **every** delta, and each such write calls `scrollToBottom()`, which re-measures and re-targets in a bounded loop. That is O(n) DOM text per chunk and O(passes) layout per chunk — imperceptible for the token rates a local llama.cpp server produces, but it is the obvious first thing to throttle (coalesce deltas to one rAF) if a faster backend ever makes typing feel heavy. It is also why the streaming block is one node outside the virtual list rather than a `VisualItem`: re-rendering a virtual item on every chunk would re-key the windowed list on every token.
- Streaming rewrites the _whole_ accumulated reply into `streamTextEl.textContent` (and the whole reasoning into the reasoning body) on **every** delta, and each such write ends in a `scrollToBottom()` that re-measures and re-targets in a bounded loop — O(n) text per chunk plus a layout pass per chunk.
