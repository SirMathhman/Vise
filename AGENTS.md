# Vise — Agent Instructions

A pnpm-workspaces monorepo: a **vanilla TypeScript backend** (raw Node `http`, no framework) and a **vanilla TypeScript frontend** (Vite, no framework). It's a local file browser/editor with an LLM panel that gives a model live, sandboxed read/write/shell access to the workspace. See [README](README.md) for setup and layout, and [architecture doc](./docs/architecture.md) for the ideal architecture, design invariants, known risks, and future work.

## Commands (run from repo root)

| Task                                           | Command                                                        |
| ---------------------------------------------- | -------------------------------------------------------------- |
| Install                                        | `pnpm install`                                                 |
| Dev (backend :3001 + frontend :5173, parallel) | `pnpm dev`                                                     |
| Build (all packages)                           | `pnpm build`                                                   |
| Typecheck (all packages)                       | `pnpm typecheck`                                               |
| Test                                           | `pnpm test` (frontend only — Jest; backend has no test script) |
| Lint                                           | `pnpm lint` (Biome: `biome check .`)                           |
| Format                                         | `pnpm format` (Biome: `biome format --write .`)                |

Run these automatically before/after changes; a change is not done until `pnpm typecheck` and `pnpm lint` pass (and `pnpm test` for anything touching `apps/frontend/src/components/{conversations,fileState,profiles}.ts`).

To run a single frontend test file or a name pattern: `pnpm --filter @vise/frontend exec jest src/components/conversations.test.ts` or `... jest -t "some test name"`.

## Architecture

### Backend (`apps/backend`) — layered, no framework

- `router.ts` — pure path matching (`:param`, trailing `*` → `params.rest`). No side effects.
- `http.ts` — `sendJson` (the only response writer).
- `errors.ts` — `AppError` + factories (`notFound`, `badRequest`, `forbidden`, `internal`) and `toResponse`.
- `context.ts` — `AppContext` (deps: `now`, `rootPath`, `fileWatcher`) injected into route factories.
- `fs.ts` — the single place all filesystem access passes through: `resolveWithinRoot` (must exist, follows symlinks, rejects escapes), `resolveForCreate` (parent must exist), `validatePath` (name vetting), `assertDoesNotExist`, `createDir`/`createFile` (create cores), `looksBinary` (NUL-byte sniff, first 8 KB), `mapFsError` (raw `fs` → `AppError`: ENOENT/ENOTDIR→404, EACCES/EPERM→403, EISDIR→400).
- `watch.ts` — `createFileWatcher(rootPath)`: a dependency-free recursive `fs.watch`-based watcher that debounces (1000ms) bursty raw events into one `WatchEvent` per changed path and exposes `start`/`close`/`subscribe`. Falls back to a non-recursive root watch where recursive `fs.watch` isn't supported (Linux); Windows/macOS get the real recursive watch.
- `json.ts` — `readJsonBody`.
- `routes/*.ts` — one resource file per endpoint group; each exports a **named** factory (`healthRoutes`, `helloRoutes`, `echoRoutes`, `lsRoutes`, `fileRoutes`, `createRoutes`, `llmToolRoutes`, `watchRoutes`) returning `Route[]`.
- `app.ts` — composes `routeGroups` (the 8 factories), starts the file watcher, mounts the request loop (guards `/api/` prefix, body parsing, error → `toResponse`). `close()` calls `server.closeAllConnections()` before `server.close()` — an open `/api/watch` SSE stream is a long-lived connection that would otherwise keep the server (and the watcher teardown) from ever completing.
- `index.ts` — entry point; reads `PORT` (default 3001) and `ROOT_DIR`. `SIGINT`/`SIGTERM` trigger a clean `app.close()` so the watcher doesn't keep the event loop alive.

To add an endpoint: create/extend a `routes/*.ts` factory returning `Route[]`, then register it in `routeGroups` in `app.ts`. Do not bypass `sendJson` or hand-write `res` — throw `AppError`s and let `app.ts` map them.

### Frontend (`apps/frontend`) — vanilla TS + Vite

- `main.ts` — mounts `render` into `#app`.
- `render.ts` — builds the static shell (template string + DOM), then calls `setupFileViewer` (capturing its returned `FileViewerHandle`) and `setupLlm(root, fileViewer)`.
- `api/client.ts` — **the only place that calls `fetch`/`EventSource`**. Typed wrappers (`health`, `listDir`, `getFile`, `putFile`, `deleteFile`, `createEntry`, `subscribeToChanges`, plus the LLM helpers `listLlmModels`, `sendLlmMessage`, `streamLlmMessage`, `executeLlmTool`); each returns parsed data or throws a normalized `Error`. Holds the hardcoded `LLM_API_KEY` bearer token (dev-only, `127.0.0.1` proxy only).
- `dom.ts` — small DOM helpers (e.g. `makeButton`).
- `highlight.ts` — dependency-free, single-line syntax highlighter (no cross-line state, no language detection).
- `diff.ts` — DOM-free line-diff math for the live edit_file preview (see below): `buildDiffRows` (a single-hunk unified diff: context/removed/added rows with dual old/new line numbers) and `clampEditRange` (mirrors the backend's own end_line clamp). Unit-tested in `diff.test.ts`.
- `llm/partialJson.ts` — DOM-free helpers for reading a field's value out of a tool call's arguments while they're still streaming in as partial, possibly-invalid JSON text: `extractPartialJsonString` (stops at the first unescaped closing quote; handles `\n`/`\t`/`\"`/`\\`/`\uXXXX`, holding back an incomplete trailing escape) and `extractPartialJsonNumber` (only returns a value once a trailing `,`/`}` proves the digit run is complete, so a still-streaming number is never read as a truncated one). Unit-tested in `partialJson.test.ts`.
- `components/fileTree.ts` — the thin DOM controller for the tree/listing and the file viewer/editor: renders the listing, wires the context menu (new/delete via `contextMenu.ts` + `createDialog.ts`), owns expand/collapse state, the `beforeunload` dirty guard, and live-refresh from the watch SSE stream (see below). Delegates the editor's buffer/dirty/autosave logic to `fileState.ts`. `setupFileViewer` returns a `FileViewerHandle` (`beginEditDiff`/`updateEditDiffNew`/`endEditDiff`) so the LLM panel can preview an in-flight `edit_file` tool call live in this same panel — see the LLM panel section.
- `components/fileState.ts` — a DOM-free store for the editor's autosave lifecycle (buffer, `dirty` flag, debounced save timer, `flush`/`save`). Kept free of the DOM and of `api/client.ts` (the persist function is injected) so it's unit-testable in Node; see `fileState.test.ts`.
- `components/conversations.ts` — a DOM-free `ConversationStore`: owns the list of chat conversations (each with its own message history, model choice, and `profileId`), persists them to `localStorage`, and migrates the old single-conversation format. Unit-tested in `conversations.test.ts`.
- `components/profiles.ts` — a DOM-free `ProfileStore`: owns the list of profiles (each a system prompt, allowed-tools list, and three hook commands — see the LLM panel section), always keeps the undeletable `Default` profile present, and persists to `localStorage`. Unit-tested in `profiles.test.ts`.
- `components/profileLists.ts` — renders a profile's allowed-tools checklist into a container (`renderProfileToolList`); checking a box calls `onChange` with the full new allowed-tools list. Used by the Profiles modal in `llm.ts`.
- `components/skills.ts` — a DOM-free `SkillStore`: owns the list of named skills (each a `name`, one-line `summary`, and full `content`), keyed by `name` (the model-facing id, fixed after creation), persists to `vise:llm:skills`. Backs the `use_skill` tool — the panel's `resolveToolCall` intercepts `use_skill` and looks up the skill's `content` here. Unit-tested in `skills.test.ts`.
- `components/messageView.ts` — `MessageView`, a virtualized renderer for the chat log: only the blocks in/near the viewport are live DOM nodes (absolutely positioned inside a full-height spacer), so scrolling a long conversation stays smooth.
- `components/askQuestionsCard.ts` — the `ask_questions` tool's interactive card: renders one question block per item (radio/checkbox options when provided, plus a free-text input), an Answer button that enables once any answer is non-empty, and the `formatAskQuestionsResult`/`notAnsweredResult` helpers that shape the answers into the model-readable `tool` message. Ephemeral — appended directly to the transcript scroll container, not the `ChatMessage[]` store.
- `components/llm.ts` — the LLM panel's DOM controller: wires the conversation/model/profile dropdowns, the Profiles editor panel, the send loop, and context-usage display, using the stores/view above.
- `components/contextMenu.ts`, `components/createDialog.ts` — shared right-click menu and "create file/dir" modal.
- `llm/tools.ts` — OpenAI-style tool **definitions** (`llmToolDefinitions`) sent with each chat request.
- `styles.css` imports per-area CSS in `styles/`.

Views call functions from `api/client.ts` — never `fetch`/`EventSource` directly.

The Vite dev server proxies `/api` → `localhost:3001` and `/llm` → `localhost:8080` (see `vite.config.ts`).

### Live file-tree updates (`GET /api/watch` + `subscribeToChanges`)

`routes/watch.ts` exposes the app-owned `fileWatcher` as an SSE stream (`text/event-stream`, one `data: <WatchEvent JSON>\n\n` per debounced change). The frontend's `subscribeToChanges` wraps it in an `EventSource` (auto-reconnecting) and `fileTree.ts` uses it to: refresh the root and every expanded directory, and reload the open file _only if its buffer is clean_ (an in-progress edit is never clobbered — if the open file changed on disk while dirty, the title is annotated "(out of date)" instead). Refreshes are debounced an additional 80ms client-side to coalesce bursts.

### LLM panel (`apps/frontend/src/components/llm.ts` + `routes/llm.ts`)

A chat panel that talks to an **OpenAI-compatible proxy** (llama.cpp at `:8080`) through the Vite `/llm` proxy (which rewrites `/llm/*` → `/*`). Conversations are independent, persisted in `localStorage`, and listed in a dropdown (New/Delete/switch). The flow is a client-side tool loop:

1. `sendLlmMessage` posts messages + `llmToolDefinitions` to `/llm/v1/chat/completions`.
2. If the reply contains `tool_calls`, the panel calls `executeLlmTool` for each → `POST /api/llm/tool` on the **backend**.
3. The backend runs the tool (`routes/llm.ts`), returns a text result, and the loop feeds it back as a `tool` message until the model produces plain text (capped at the active profile's `maxToolTurns` — default 100 — in `llm.ts`; see the tool-turn budget below).

**Tools** (defined in `llm/tools.ts`, handled in `routes/llm.ts`, named in `packages/shared`'s `LLM_TOOL_NAMES`): `list_directory`, `find_files` (regex on base name via `git ls-files --cached --others --exclude-standard`, so it's git-ignore-aware; capped at 500 matches), `search_files` (regex on file _content_, line by line, over the same git-ignore-aware file listing as `find_files` — the two share a `listWorkspaceFiles` helper; skips binary files and files over the 1MB cap; capped at 200 matches total and 50 per file so one match-heavy file can't crowd out the rest), `read_file` (1-based, `start_line` inclusive/`end_line` exclusive, ≤300 lines/call), `edit_file` (replace a ≤300-line range in an existing file; `end_line === start_line` inserts, an empty `content` deletes the range), `create_directory`, `create_file`, `delete_file`, `delete_directory` (both permanent, root itself is rejected), `run_command` (spawns a **PowerShell** command in the workspace root; 30s timeout, 1MB combined output cap, at most one command in flight at a time, and on timeout kills the whole process tree via `taskkill /T /F` since plain `child.kill()` only signals the top-level process on Windows), `create_subagent`, `ask_questions`, and `use_skill` (all three client-executed — see below). All tools are root-scoped through `fs.ts`'s resolvers. Tool results are always plain strings; backend errors resolve to `200` + an `Error: …` string so the model can read and adapt rather than the loop crashing.

**`create_subagent`, `ask_questions`, and `use_skill` are the three tools the backend never executes.** Every other tool call is forwarded to `POST /api/llm/tool`; all three are intercepted client-side in `llm.ts` (`resolveToolCall`) because each needs something only the browser panel has:

- **`create_subagent`** (`runSubagent`) needs to run its own nested chat-completion loop (the panel alone talks to the LLM proxy). `runSubagent` gives the helper a fresh message history (just the task text, not the parent conversation) and runs it under the named Profile passed as the call's required `profile` argument: its own system prompt, allowed-tools, and hooks, all fully applied (see Profiles below). Nesting stops at one level because `subagentToolDefs` excludes `create_subagent` unconditionally. A missing or unrecognized `profile` is a model-readable error (listing the available profile names) rather than a fallback — there is no built-in default helper anymore. Nothing about a subagent's run is persisted: the parent conversation's store only gets the `tool_calls`/`tool` message pair like any other tool, with the subagent's final text as the result. For the live session, `MessageView.appendSubagentResult` renders the run as a collapsed `<details>` block (task, its own tool-call/tool-result/end-hook trace, then its result) so it's inspectable without cluttering the main transcript; after a reload only the plain result survives (it's an ordinary tool message), same as any other tool.
- **`ask_questions`** (`askQuestions`) needs to render an interactive card and _pause the turn_ until the user answers — a UI concern only the panel can own. Its `questions` argument is an array of `{question, options?, multi_select?}`; the panel renders one block per question (`askQuestionsCard.ts`) into the transcript with optional predefined options (radio, or checkbox when `multi_select`) plus a free-text input, and an Answer button enabled once anything is filled in. Answers come back as one model-readable line per question (`Q1: answer1\nQ2: answer2`). The card is **ephemeral** — it is appended directly to the transcript scroll container (`MessageView.scrollElement`), _not_ as a `VisualItem`, so it is not part of the persisted conversation; only the resulting `tool` message is. A pending question is abandoned if the user starts a new turn, switches conversation, or creates/deletes one (`resolvePendingAsk`), resolving with a `(not answered)` result so the model can adapt. Subagents cannot call `ask_questions` (`subagentToolDefs` excludes it alongside `create_subagent`), since their collapsed trace has no room for an interactive card.
- **`use_skill`** needs to look up a named skill's full content in the browser's `SkillStore` — a panel concern the headless subagent loop doesn't own. Its `name` argument is the exact skill name; the panel returns the skill's `content` verbatim as the tool result. A missing or unrecognized name is a model-readable error listing the available skill names. The model sees each skill's `name` and one-line `summary` in the system prompt's available-skills list (appended by `systemPrompt` when any skill has a non-empty summary) and calls `use_skill` with the skill's `name`. Skills are global (not per-profile); the `Default` profile allows `use_skill` by default.

The backend still carries a throwing stub for each (`create_subagent`, `ask_questions`, `use_skill`) in `routes/llm.ts`'s `tools` record purely to satisfy the `Record<LlmToolName, LlmToolHandler>` exhaustiveness check — either throws if actually reached, which would mean the client-side interception was bypassed.

**Live `edit_file` diff preview.** `streamLlmMessage` (`api/client.ts`) takes an optional `onToolCallChunk(index, name, args)` callback fired on every tool-call delta with that call's accumulated `name`/raw-JSON `arguments` text so far. `runTurn`'s `handleEditAnimChunk` (`llm.ts`) watches for an `edit_file` call: once `path`/`start_line` (and `end_line`, or proof it was genuinely omitted — see `llm/tools.ts`'s parameter order, which the model is **not** guaranteed to follow; verified live) are resolvable via `llm/partialJson.ts`, it calls the `FileViewerHandle`'s `beginEditDiff(path, startLine, endLine)`, which opens that file in the **file viewer panel** (flushing any pending manual edit first, exactly like clicking the file) and renders it as an inline unified diff — the replaced lines fade in red, the surrounding file renders normally, both with a shared old/new line-number gutter (`diff.ts`'s `buildDiffRows`). Every subsequent chunk streams the model's `content` argument so far into the green added rows (`updateEditDiffNew`), ending in a blinking cursor. This live-streamed range is only a best-effort guess, though — a model can order `end_line` _after_ `content` too (verified live, distinct from the `start_line`-ordering case above), which fools the omission check into locking in the wrong range mid-stream — so once the call is fully known (its JSON is valid and complete), `resyncEditDiff` re-parses the real `path`/`start_line`/`end_line`/`content` and re-opens the diff against them _before_ the tool actually runs, guaranteeing the settled preview the user reads is always correct even if the live portion briefly showed the wrong shape. Once the call actually executes on the backend, `endEditDiff(ok)` stops the cursor and shows the outcome ("Edited"/"Edit failed") next to an **OK** button in the viewer's actions bar — the diff (colors and all) stays up until the user dismisses it, at which point the file reloads from disk into the normal, non-diff editable view: the edit's real result stays, only the red/green goes away. A turn abandoned before the call ran (Stop, or a switch/rollback) calls `cancelEditDiff()` instead, reloading immediately with no dismiss step, since there is no real outcome to show. If `beginEditDiff` can't take over (an unsaved manual edit failed to flush, or the file can't be read), the call silently falls back to the ordinary plain-text tool-call/tool-result rendering, same as any other tool. The chat transcript shows no separate label for an animated call — the live preview _is_ the visible trace.

### Profiles (`apps/frontend/src/components/profiles.ts`)

A **profile** is a named, reusable bundle of everything that shapes how the model behaves: its system prompt, an **allowlist** of tool names it may call, and its three hook commands (startup/turn/end — see below). Profiles are the sole source of truth for a conversation's (or a delegated subagent's) tools and hooks — a conversation carries no tool/hook settings of its own, only a `profileId`. `createProfileStore()` persists the profile list to `vise:llm:profiles`, mirroring `ConversationStore`'s shape (DOM-free, unit-tested). The always-present `Default` profile (`DEFAULT_PROFILE_ID = "default"`) is seeded with the app's original system prompt and every known tool allowed, so a conversation that never touches a profile behaves exactly as it did before profiles existed; it cannot be deleted, and `ProfileStore.deleteProfile` refuses to remove it. Deleting any other profile is coordinated by `llm.ts` (not by either store alone, keeping them decoupled): `ConversationStore.reassignProfile(fromId, toId)` repoints every conversation that pointed at the deleted profile back to `Default`.

The panel renders two things for profiles: a `<select id="llm-profile">` next to the model picker (assigns the _active conversation's_ profile) and a "Profiles" button that opens a modal (`#llm-profiles-overlay` / `.llm-profiles-modal`, closed via its own Close button, Escape, or a backdrop click — same pattern as `createDialog.ts`'s file/dir-creation overlay) with its own `<select id="llm-profile-editor">` (which profile's fields are shown) plus inputs for name/system-prompt/hooks and a tools checklist (`renderProfileToolList`, allowlist semantics: checked = allowed, reusing the same `.llm-tool*` CSS as the old per-conversation checklist it replaced). These are two independent selections — editing a profile in the modal never reassigns the active conversation, and switching a conversation's profile never changes what the modal is editing. The editor lives in a modal rather than inline in the panel specifically to avoid nested scrollbars: its content (a long system prompt, the full tool list, three hook inputs) is unbounded and has no "shrink to fit" behavior, so keeping it in the panel's normal flow meant either the panel or the tool checklist (or both) needed their own `overflow: auto` — nested inside each other, or inside `#llm-response`'s own scroll, whenever everything didn't fit. The modal has exactly one scroll region (itself), independent of the panel underneath it.

**Tool allowlisting**: a profile's `allowedTools` replaces the old per-conversation `disabledTools` denylist, but the mechanism is unchanged and still KV-cache-preserving for the _main_ conversation loop: `llmToolDefinitions` is always sent to the model unfiltered, `disabledFromAllowed(profile.allowedTools)` derives the complement once per turn, the system prompt gets a note listing what's unavailable, and a call to one is short-circuited client-side to a fixed result rather than reaching the backend. A **subagent's** offered tool list, by contrast, _is_ filtered to `profile.allowedTools` (via `subagentToolDefs`) — it already deviated from the "send everything" invariant before profiles existed (create_subagent was always excluded), so this is an extension of that existing deviation, not a new one.

**Startup hook**: a profile's optional `hookCommand` runs once — the first time a message/task is sent under that profile — via the same `run_command` tool the model uses (`executeLlmTool` with a synthetic call). Its output is cached as `hookOutput` **on the conversation** (not the profile: two conversations sharing a profile at different times shouldn't share one cached run) and appended to that conversation's system prompt on every turn from then on. Switching a conversation's profile clears its cached `hookOutput` (`ConversationStore.setActiveProfile`), since a stale cache belongs to the old profile's command, not the new one's.

**Turn hook**: a profile's optional `turnCommand` runs fresh before _every_ turn/iteration (same `run_command` mechanism) and is never cached — its latest output is resent each turn, never reused on the next one.

**End hook**: a profile's optional `endCommand` runs after every reply — the model's plain-text answer, once it stops requesting tools — rather than before. Unlike the other two hooks, its output _is_ meant to reach the model, and it's a gate, not context: the panel calls `POST /api/llm/hook-command` (not the `run_command` tool) to get the command's stdout and stderr back **separately** (the tool's `executeLlmTool` only returns one combined, model-formatted string, which can't answer "is stderr empty?" reliably), truncates the combined output to `END_HOOK_OUTPUT_CHARS` (500) for both display and model consumption, and always shows it in the transcript via `MessageView.appendEndHookResult` (ephemeral — like a subagent's trace, it isn't part of `ChatMessage[]` and won't survive `setMessages`/reload on its own unless it blocked). If stderr came back empty, the reply stands and the turn ends normally. If stderr is non-empty, the reply is **not** accepted: the turn loop (`runTurn`'s `for` loop, same `MAX_TOOL_TURNS` budget as tool calls) appends a synthetic `role: "user"` message flagged `endHook: true` — a protocol-valid turn, since a floating `role: "tool"` message with no matching `tool_calls` would not be — carrying the truncated output and an instruction to fix the issue, and loops back into the model. `expandMessage` renders an `endHook`-flagged message as a distinct "end-of-turn check" block (like `compaction`) rather than a plain "You" bubble, so a later reload still explains why the model's answer changed mid-turn. A thrown failure from the check itself (spawn error, or the backend's single-flight guard colliding with another in-flight command) is treated the same as a blocking check — shown and fed back for a retry — rather than propagating to the turn's rollback path, which would otherwise discard the whole turn's history including any file mutations the model's tool calls already made. The backend side: `runCommand` (the LLM tool) and `POST /api/llm/hook-command` both call a shared `runShellCommand` core in `routes/llm.ts` — same spawn/timeout/tree-kill/single-flight guard, one returns a formatted string for the model, the other structured `{stdout, stderr, truncated, timedOut}` JSON for the panel. `checkEndHook` in `llm.ts` is the one shared helper both `runTurn` and `runSubagent` call, so a subagent's own end hook (when running under a named profile) gates its candidate answers identically.

**A subagent under a named profile runs the profile's hooks too** — the startup hook once before its loop, the turn hook fresh each iteration, the end hook gating each candidate final answer — mirroring `runTurn`'s orchestration exactly (via the same `checkEndHook`/`runHookCommand` helpers), not just its system prompt and tools.

**Tool-turn budget**: a profile's `maxToolTurns` (default 100, editable in the Profiles modal) is the maximum number of model-call rounds a single turn may run before it must produce a final answer. It replaced the old hardcoded `MAX_TOOL_TURNS = 5`, which was far too few — a local model doing file exploration (one tool call per round) would exhaust it and the turn would end on a dead-end "I stopped after several directory lookups without a final answer." string. When the budget is hit, `runTurn` pauses and asks the user, via a Yes/No card in the transcript (`requestMoreRounds`, reusing `askQuestionsCard.ts`), whether to allow more rounds; a "yes" extends the budget by another `maxToolTurns` rounds, a "no" (or an abandoned card — `resolvePendingApproval`, called wherever `resolvePendingAsk` is) ends the turn. A subagent runs under the same per-profile budget but headless — it has no user to ask, so it simply stops at the cap.

**Follow (auto-scroll)**: `MessageView` (`messageView.ts`) keeps a `follow` flag and a floating "Follow" pill sticky in the transcript's bottom-right corner. While `follow` is on, every appended block scrolls the view to the bottom; scrolling away from the bottom turns it off automatically (so new messages don't yank the view while reading back), and scrolling back to the bottom — or clicking the pill — turns it back on. `setMessages` (conversation switch/load) always resets it on. `VirtualList.scrollToBottom()` re-measures and re-targets in a loop (bounded, mirroring `layout()`'s own convergence) because landing near the bottom brings previously off-screen (estimated-height) blocks into view, which can grow the measured total height past the first jump's target.

**Context compaction**: `llm.ts` tracks prompt tokens per conversation against the model's context window (from `/llm/v1/models`). Once the last call used ≥80% of the window (`COMPACT_THRESHOLD`), the _next_ turn first asks the model to summarize the conversation, appends the summary as a `compaction`-flagged message, and from then on `buildMessages` sends only that summary plus everything after it — the underlying message array stays append-only (nothing is ever deleted), only the outgoing prompt is truncated.

**Adding a tool** requires the shared `LLM_TOOL_NAMES` entry, a definition in `llm/tools.ts`, and a handler in the `tools` record in `routes/llm.ts` (see [Shared contract](#shared-contract-packagesshared)). Neither side hardcodes tool names beyond that shared list.

A bearer token (`LLM_API_KEY`) is hardcoded in `api/client.ts` — a local-use key, since the proxy only forwards to `127.0.0.1`.

### Shared contract (`packages/shared`)

`packages/shared` is the single source of truth for cross-app shapes. It exports the `LLM_TOOL_NAMES` const array and the derived `LlmToolName` type. The **backend** consumes it type-only (`import type`), so its zero-runtime-deps invariant holds (the type import erases the runtime const). The **frontend** imports the `LLM_TOOL_NAMES` value directly where it needs the runtime array (e.g. `profiles.ts` seeds the default profile's `allowedTools`) — fine for the bundled SPA, which has no runtime-deps constraint. It has **no build step** — `main`/`types` point straight at `./src/index.ts`.

**Adding an LLM tool touches three files:** the `LLM_TOOL_NAMES` const here, a definition in `llm/tools.ts`, and a handler in the `tools` record in `routes/llm.ts`. A misspelled tool name is a compile error on both sides.

## Conventions

- **TypeScript strict** everywhere (`strict: true`, ES2022, ESM). Backend uses `.js` extensions in relative imports (ESM); frontend likewise.
- **No dependencies by design** — backend has zero runtime deps; frontend only Vite + TypeScript (plus Jest/ts-jest as dev deps for the two DOM-free store test suites). Do not add a framework or HTTP library without asking.
- **Formatting is owned by Biome** (repo root `biome.json`): 2-space indent, double quotes, semicolons, 80-col lines, LF endings. Don't fight it; run `pnpm format`.
- **Path safety is non-negotiable**: every filesystem access in a route or LLM tool must go through `resolveWithinRoot` (or `resolveForCreate` for creates). Never join `rootPath` with user/model input directly — this is the core invariant of the app.
- **Binary / size guards**: file preview and writes are capped at 1 MB (`MAX_BYTES`) and reject files with a NUL byte in the first 8 KB (`looksBinary` in `fs.ts`). Keep these guards when touching file routes or the `read_file`/`edit_file` LLM tools.
- **Error mapping**: raw `fs` errors are mapped via `mapFsError` (in `fs.ts`) so ENOENT/ENOTDIR→404, EACCES/EPERM→403, EISDIR→400. Re-throw existing `AppError`s unchanged.
- **DOM-free stores are unit-tested; DOM controllers are not.** `conversations.ts`, `profiles.ts`, and `fileState.ts` take their side effects (persist/network) as injected callbacks specifically so they can run under Jest in Node. If you add similar stateful logic, prefer the same split rather than burying it in a DOM controller like `fileTree.ts`/`llm.ts`.

## Pitfalls

- **No CI** — there is no `.github` workflow. `pnpm typecheck`, `pnpm lint`, and `pnpm test` are run manually/by the agent, not automatically.
- **Tests cover the DOM-free stores and pure helpers** (`fileState.ts`, `conversations.ts`, `profiles.ts`, `skills.ts`, `diff.ts`, `partialJson.ts`) via Jest/ts-jest in the frontend (`apps/frontend/jest.config.js`). There are no DOM/e2e tests and the backend has no test script at all.
- Backend `dev` runs via `tsx watch`; it does **not** rebuild `dist/`. Production runs `node dist/index.js` after `pnpm build` (frontend build is `tsc --noEmit` + `vite build`).
- `ROOT_DIR` defaults to a hardcoded Windows path in `index.ts` — it must be set explicitly for anything other than the author's machine. `PORT` (default 3001) is the only other env var read.
- `LLM_API_KEY` is hardcoded in `api/client.ts` and baked into the bundle — fine for the single-user local tool, but it is a committed secret; move it to a gitignored `.env` + `import.meta.env.VITE_*` before sharing the repo.
- The `run_command` LLM tool runs **arbitrary PowerShell in the workspace root with no allowlist**, gated only by a 30s timeout and single in-flight execution. This is by design for a trusted single local user talking to their own local model — treat it as a real risk surface if the LLM proxy, the backend port, or the model's tool access is ever exposed beyond `127.0.0.1`. It's also Windows-specific (spawns `powershell.exe`, kills via `taskkill`).
- The `/llm` proxy exists only in `vite.config.ts` (dev server) — the built SPA has no production path to the LLM.
- The router only matches under `/api/`; anything else gets a 404 before route matching (see `app.ts`).
- Recursive `fs.watch` isn't available on all platforms (notably Linux); `watch.ts` falls back to a non-recursive root watch there, so nested changes on Linux may not trigger a live refresh the way they do on Windows/macOS.
- Biome ignores `dist/`, `node_modules/`, and `pnpm-lock.yaml` via `biome.json`/`.gitignore` — don't expect lint coverage on build output.
