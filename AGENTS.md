# Vise — Agent Instructions

Vise is an interactive LLM chat REPL written in TypeScript on the Bun runtime.
Full design rationale, invariants, and target layout live in [ARCHITECTURE.md](ARCHITECTURE.md) — read it before making structural changes.

## Commands

| Task       | Command             | Notes                                                                                               |
| ---------- | ------------------- | --------------------------------------------------------------------------------------------------- |
| Run        | `bun run index.ts`  | Entry point. No build step — Bun transpiles TS on the fly.                                          |
| Web UI     | `bun run web`       | Starts the Bun HTTP/WebSocket server at `http://localhost:3000` by default. Set `PORT` to override. |
| Install    | `bun install`       | Only dev deps are `@types/bun` and `typescript`; zero runtime deps.                                 |
| Type-check | `bunx tsc --noEmit` | `typescript` is a dev dep (peer). No `typecheck` script in `package.json`.                          |
| Lint       | `bun run lint`      | ESLint with typescript-eslint. Config in `eslint.config.js`.                                        |
| Test       | `bun test`          | Bun's built-in `bun:test` runner; suites live in `test/`.                                           |

## Surface (product features an agent touches)

Two surfaces an agent commonly edits. The list below is a quick reference — the
authoritative definitions live in the source files linked.

**User-facing slash commands** — dispatched in `Session.handleLine`
(`src/repl/session.ts`); help text is rendered by `formatHelp` in
`src/output/format.ts`. To add one, handle it in `handleLine` and add it to
`formatHelp`.

- `/exit`, `/help`, `/context`, `/compact`
- `/model` (list) / `/model <name>` (switch) — via `ModelController`
- `/tool` (list) / `/tool <name> enable|disable` — via `ToolController`
- `/profile` (list) / `/profile <name>` (set) / `/profile init <name>` (create) — via `ProfileSource`
- `/note` (list) / `/note init <name>` (create) — via `NoteSource`
- `/workflow` (list) / `/workflow <name> [input]` (run) / `/workflow init [--global] <name>` (create) — via `WorkflowSource`; JSON files live under `.vise/workflows/` or `~/.vise/workflows/`
- `/save` (list) / `/save <name>` (persist), `/resume` (list) / `/resume <name>` (restore), `/delete <name>` (delete) — via `SessionSource`

**Model-facing tools** — defined in `src/tools.ts` (`tools: Tool[]`) with their
implementations in `src/tools/files.ts`, `src/tools/shell.ts`,
`src/tools/notes-tool.ts`, `src/tools/subagent.ts`, `src/tools/ask-user.ts`,
and `src/tools/self.ts`; dispatched by name by
the core in `src/core/engine.ts`. To add one, append a definition to `tools`
in `src/tools.ts`, add a handler function in the matching domain module, and
register it in the `baseHandlers` map in `src/tools.ts` (or pass it as an
`extra` handler to `createToolRunner` in `index.ts` when the handler depends
on edge services constructed later, such as the subagent handler's `Client`
or the `ask_user` handler's `RlUserPrompter`).

- Files: `list_directory`, `read_file`, `create_file`, `edit_file`,
  `delete_file`, `delete_directory`, `find_files` (recursive regex name match),
  `search_files` (recursive regex content search, file or directory)
- Shell: `run_powershell` (Windows-only, foreground 60s SIGTERM timeout; `background: true` spawns a background process and returns a numeric process id), `wait_for_process` (block on a background process up to a timeout, in ms), `kill_process` (SIGTERM a background process)
- Notes: `list_notes`, `read_note`, `save_note`, `delete_note`
- Subagents: `run_subagent` (runs a subagent — a fresh, isolated conversation with its own profile — to perform a task and return its final result; the subagent can use all the same tools, including `run_subagent`)
- User interaction: `ask_user` (pauses the turn, prompts the user with a question and optional predefined choices, and returns the user's answer as the tool result; the user may pick a choice or type a free-form reply; `multi_select: true` lets the user select multiple choices, separated by commas)
- Self: `self` (reports the agent's own live state — backend, active model, working directory, context-window fill, active profile, and pre/post-turn hook commands — so the model can confirm which model and profile it is acting as or how full its context is)

## Hard rules (from the architecture invariants)

- **No `process.exit()` anywhere.** Termination happens when the event loop drains; set `process.exitCode` instead. `process.exit()` truncates buffered stdout through pipes.
- **The core (`src/core/`) is pure.** No `node:` imports, no `console`, no `process`, no globals. Same input → same output.
- **No `throw` in core paths.** Errors are the structured `Result<T>` / `ViseError` union from `src/core/errors.ts`. All display formatting belongs in `src/output/format.ts`.
- **Dependency arrows point edge → core only.** `client/llm.ts` is the sole module that performs network I/O; `src/tools.ts` (definitions + registry) and the handler modules under `src/tools/` are the edge implementation of the core's `Tool`/`ToolRunner` types.
- **Explicit `.ts` extensions on all imports** (`allowImportingTsExtensions`), ESM throughout.
- **Size limits:** files < 500 code lines, functions < 100 lines. Split at a natural seam when approaching the limit.

## Current-state notes (code lags the architecture doc)

- `src/wiring.ts` exports `createEdgeSession`, the shared factory for the LLM client, edge data sources, tool runner, and `Session`. Both `index.ts` (`TerminalDriver`) and `src/web/server.ts` use it, supplying frontend-specific streaming callbacks and user prompting. Keep transport-specific behavior in the respective driver, not in shared wiring or the core.
- `index.ts` is thin terminal wiring: it constructs a `StreamDisplay`, readline prompter, and shared edge session, then calls `TerminalDriver.run()`. The interactive terminal surface lives in `src/driver/terminal.ts`. The web frontend is served by `src/web/server.ts` with its entry point in `src/web/main.ts`; static HTML, CSS, and browser JavaScript live in `web/`. It creates an independent `Session` per WebSocket connection and streams turn events over the socket. Start it with `bun run web` (default port 3000; `PORT` overrides). There is no `src/cli.ts` yet; the TTY/pipe split remains outstanding. Don't add TTY/pipe special-casing into `index.ts`.
- **Web UI sessions panel:** The web frontend has a toggleable sessions panel (alongside the tools panel) that lists saved sessions, lets the user resume one (clicking a row sends `/resume <name>` and clears the chat log), and save the current conversation (freeform name input sends `/save <name>` and refreshes the list). The panel is populated by the same `/resume` list command that powers the terminal surface; the initial-load chain in `web/app.js` fetches the session list on connect (after model/profile/tool) so the panel is populated before the user opens it. No server changes were needed — the browser sends `/save` and `/resume` as regular lines through the existing `handleLine` path. No new core or edge code.
- `src/core/engine.ts` mutates the `messages` array in place by design; it's a documented side channel, not a bug.
- `RECENT_TURNS_TO_KEEP` in `src/repl/compaction.ts` and `MAX_TOOL_ROUNDS` in `src/core/engine.ts` are the compaction/tool-loop bounds. `COMPACTION_THRESHOLD = 0.9` in `src/repl/session.ts` drives `maybeAutoCompact()` — the auto-compact-before-every-turn guard that compares the live `context.lastPromptTokensUsed()` against `contextMax()`. The `ContextSource` interface (`lastPromptTokensUsed` + `contextMax`) is core-owned (`src/repl/session.ts`); `lastPromptTokensUsed` comes from the server's `usage.prompt_tokens` and is `undefined` until the first successful chat, so `maybeAutoCompact()` no-ops on cold start.
- `API_KEY`, `URL`, `MODEL` are hardcoded constants in `src/client/llm.ts` (no env config by design — local-only tool).
- `src/data-dir.ts` exports `dataDir = join(process.cwd(), ".vise")` — the single source of truth for the per-project data directory. Shared by all edge sources in `src/edge-sources.ts` and by `src/tools/notes-tool.ts` (which reads it directly rather than receiving it as a parameter). Any new per-project store should import `dataDir` rather than recomputing `join(cwd, ".vise")`.
- **Profiles:** `/profile <name>` loads a `.md` file from the `.vise/profiles/` directory and appends its text as a user message to the conversation (an empty profile file appends a clearing instruction instead); `/profile init <name>` creates a new profile with a placeholder body. The system message is never modified (invariant #6). The `ProfileSource` interface is owned by the core (`src/repl/session.ts`); the edge (`src/edge-sources.ts` `FileProfileSource`) does the `node:fs` I/O, which is shared with the subagent handler through `src/profiles.ts`. Same edge-owns-I/O pattern as `ModelController`.
- **Notes:** A per-project store of short facts and how-to procedures, kept in a flat `.vise/notes/` directory. Each note is one `.md` file; the filename (minus extension) is the note name, and the first non-empty line is its one-line summary (shown by listing); the rest is the body. Note names are unique. The note _listing_ (names + summaries) is auto-injected into context at startup (via the `initialMessage`); full note _bodies_ are on-demand — the model reads them via `read_note` when it needs more detail. The model also reads/writes notes through the `list_notes`/`read_note`/`save_note`/`delete_note` tools, and the user sees the same store via `/note` (list) and can create new notes via `/note init <name>`. The shared file I/O lives in `src/notes.ts` (edge). The `NoteSource` interface is core-owned (`src/repl/session.ts`); the edge (`src/edge-sources.ts` `FileNoteSource`) implements it. Same edge-owns-I/O pattern.
- **Workflows:** JSON files under `.vise/workflows/` (project) and `~/.vise/workflows/` (global). `/workflow` lists both scopes; project definitions take precedence over same-named global ones. `/workflow <name> [input]` runs steps in order; instruction steps run a normal model/tool loop to completion, while tool steps use llama.cpp's JSON-schema constrained output to generate arguments and Vise executes the named tool directly, stopping on the first error. `/workflow init <name>` and `/workflow init --global <name>` create starter files. The `WorkflowSource` interface is core-owned (`src/repl/session.ts`); filesystem parsing and scope resolution live in edge module `src/workflows.ts`, adapted by `FileWorkflowSource` in `src/edge-sources.ts`; pure orchestration is in `src/core/workflow.ts`.
- **Initial file structure:** At startup, `src/edge-sources.ts` (`buildInitialMessage`) builds an indented text tree of the working directory via `src/fs-tree.ts` (capped at 5 levels below root or 25 entries, whichever hits first; dotfiles and `.git` excluded), loads the project's `AGENTS.md` agent-instructions file (best-effort: silently omitted when absent or unreadable). Additionally, the available profiles (names only, from `.vise/profiles/`) and available notes (name + summary, from `.vise/notes/`) are listed when present. All sections are concatenated into a single `initialMessage` string, passed to the `Session` constructor, and injected as the first user message after the system message. The system message is never modified (invariant #6). Because this is a one-shot value built at construction, no core-owned `Source` interface is needed — the session takes an opaque string, not a queryable edge service.
- **Pre-turn hooks:** One or more shell commands (configured in `.viserc.json` as `preTurnCommand`) run in parallel before every turn; each hook's output is injected as a user message before the user's input, in config order. **Post-turn hooks:** One or more shell commands (configured in `.viserc.json` as `postTurnCommand`) run in parallel after every successful turn; each hook's output is injected as a user message after the assistant's reply, in config order. Each hook key accepts either a single command string or an array of command strings. The `PreTurnHook`/`PostTurnHook` interfaces are core-owned (`src/repl/session.ts`); the edge (`src/edge-sources.ts` `ShellHook`) spawns `powershell.exe`. Same edge-owns-I/O pattern.
- **Tools:** `/tool` lists the model-facing tools with their enabled state; `/tool <name> enable|disable` toggles one. The full set of tool definitions is always sent to the model regardless of enabled state — disabling a tool does not change the definitions; it only makes the runner report `error: tool <name> is disabled` if the model calls it. Enabling or disabling also injects a user message into the conversation informing the model of the state change. State is in-memory per process only (not persisted). The `ToolController` interface is core-owned (`src/core/engine.ts`); the edge (`src/tools.ts` `ToolSet`) implements it. Same edge-owns-I/O pattern. The controller/slash-command handlers that depend only on immutable session fields (`reportContext`, `handleModelCommand`, `handleToolCommand`, `handleNotesCommand`) live in `src/repl/commands.ts`; the handlers that need mutable conversation state (`handleProfileCommand`, `handleResumeCommand`, `handleSaveCommand`) live in `src/repl/session-commands.ts`; compaction (`runCompaction`) lives in `src/repl/compaction.ts`; and `/workflow` handling (`handleWorkflowCommand` + `WorkflowCommands` facade) lives in `src/repl/workflow-commands.ts` — all plain module-level functions taking narrow facade interfaces wired by `Session` via closures, keeping `session.ts` under the size limit. `src/repl/session-dispatch.ts` holds a WIP `dispatch()` function and `SessionDispatch` interface that is a structural duplicate of `Session.handleLine`; `handleLine` in `session.ts` is still the live dispatcher. Do not assume `dispatch()` is the active path.
- **Subagents:** `run_subagent` runs a subagent — a fresh, isolated conversation with its own system message and profile — to perform a task and return its final assistant text. The subagent receives the same `ToolRunner` and `Tool[]` as the parent, so it may in turn call `run_subagent` and spawn its own subagents. The `profile` argument is required: `"default"` resolves to a built-in constant profile, any other name is loaded from `profiles/<name>.md` via `ProfileSource` (the same edge I/O as `/profile`). The core `runSubagent` (`src/core/engine.ts`) is pure and delegates to `runTurn`; the edge handler (`src/tools/subagent.ts` `makeSubagentHandler`) does the `ProfileSource` I/O and is registered in `src/wiring.ts` by passing it as the `run_subagent` entry to `createToolRunner` (because its handler depends on the `Client`, `ProfileSource`, `withPreservedSlotCache`, and `currentAbortSignal`, which are constructed there). `makeSubagentHandler` also takes `withPreservedSlotCache` and `currentAbortSignal` callbacks: the subagent's model calls are wrapped in `LlmClient.withPreservedSlotCache` (slot-cache preservation) and forward the parent's live abort signal so Ctrl+C interrupts in-flight subagent model calls. Forgetting the `currentAbortSignal` wiring means a subagent's in-flight model call won't be interrupted by Ctrl+C.
- **self:** The `self` tool reports the agent's live state (backend, model, cwd, context fill, active profile, hook commands). The edge handler (`src/tools/self.ts` `makeSelfHandler`) is registered in `src/wiring.ts` as the `self` entry to `createToolRunner` (because its handler depends on the `Client`, the `Session`, and the hook command list, which are constructed there).
- **ask_user:** Pauses the turn and prompts the user with a question and optional predefined choices. The user picks a choice by number or types a free-form answer; the reply is returned as the tool result string prefixed with `user replied: ` (or an error string when the question is missing/empty or no input is received). With `multi_select: true`, the user may select more than one choice by separating the chosen numbers with commas in their reply; the prompt's trailing line changes to invite comma-separated answers, and the model receives the raw selection string (it already knows the options it provided, so no option text is resolved server-side). The `UserPrompter` interface is edge-owned (`src/tools/ask-user.ts`); the `RlUserPrompter` implementation pauses the main REPL readline, opens a one-shot readline on stdin, and resumes the main readline when the user answers or the stream closes. The handler (`makeAskUserHandler`) is registered in `src/wiring.ts` as the `ask_user` entry to `createToolRunner` (because its handler depends on the `RlUserPrompter`, which is constructed there alongside the readline interface).
- **Sessions:** The conversation can be saved and resumed. One `.json` file per saved session under `.vise/sessions/`; the filename (minus extension) is the session name. The fixed crash-recovery snapshot is written as `auto.json` after every successful turn (`Session.saveSession`, called from `handleLine`; I/O errors are swallowed so a save failure never interrupts the turn). `/save <name>` persists the current conversation under a named file, `/resume <name>` replaces the live conversation with a saved body while keeping the live system message at index 0 (invariant #6) and restoring the saved `activeProfile`. `auto` is a reserved name — users cannot save under it. The shared file I/O lives in `src/sessions.ts` (edge); the `SessionSource` interface is core-owned (`src/repl/session.ts`); the edge (`src/edge-sources.ts` `FileSessionSource`) implements it. Same edge-owns-I/O pattern.
- **Turn interruption (Ctrl+C):** `terminal: false` makes readline emit `SIGINT` on Ctrl+C rather than consuming it, so the edge owns the behavior. While a turn is in flight, the first Ctrl+C calls `Session.interrupt()`, which aborts the per-turn `AbortController` threaded through `runTurn` (`TurnCallbacks.abort`) and `Client.chat` (`signal`); `runTurn` surfaces a `{ kind: "interrupted" }` result (checked pre- and post- each `client.chat` call), and the edge prints `vise: interrupted`. At an idle prompt (no turn in flight) Ctrl+C exits (`exitCode = 130`). The per-turn controller is created at the start of `Session.handleLine` and cleared in a `finally`; `interrupt()` is a safe no-op when no turn is running. Subagents inherit the same `ToolRunner`/`Tool[]`, so their turns are interruptible too.
- **Streaming:** the model reply streams token-by-token, always on for normal user turns. The core (`Client.chat` / `runTurn`) threads optional `onToken`/`onThinking`/`onPromptProgress` callbacks as side channels — the core never does the I/O itself. The edge (`LlmClient`) performs the SSE parsing/accumulation; the driver (`src/driver/terminal.ts`) constructs a `StreamDisplay` (`src/driver/stream.ts`) and passes its bound callbacks. `StreamDisplay` owns all mutable streaming state: `mdLineBuffer` (per-line markdown buffer), `mdInFence` (code fence state), and the progress counters. `LineResult.streamed` tells the driver the reply text was already written, so it emits only the trailing newline instead of re-printing. Compaction/`summarize` calls pass no `onToken`, so they are not streamed. Streaming coverage lives in `test/` (`engine.test.ts` for `runTurn`/`summarize`, `session.command.test.ts` for the `Session` streaming flag, `llm.test.ts` for the `streamChat` SSE parser); `streamChat` is exported from `llm.ts` specifically so it can be unit-tested with a synthetic stream.
- **Tool-call and max-rounds callbacks:** `TurnCallbacks` in `src/core/engine.ts` also includes `onToolCall` (drives the `tool: name` display lines, including indented subagent calls at depth 1) and `onMaxRounds` (user-prompt at `MAX_TOOL_ROUNDS` — the edge wires it via `rlPrompter.ask` to ask "Maximum tool rounds reached. Continue?"; the user's yes/no resets the counter or ends the turn with a `malformed` error). Subagents omit `onMaxRounds`, so their tool loops end silently at `MAX_TOOL_ROUNDS`. `onMaxRounds` is the only user-prompting callback that can extend a turn; if you add a subagent-adjacent flow that needs to prompt, you must thread it (it is optional in `TurnCallbacks`).
- **Markdown rendering:** `src/output/markdown.ts` provides `renderLine(line, inFence): [string, boolean]` — a pure per-line state machine that applies terminal styling to markdown. `StreamDisplay` (`src/driver/stream.ts`) buffers tokens in `mdLineBuffer`, splits on `\n`, and calls `renderLine` for each completed line; `mdInFence` tracks code fence state. When `result.streamed` is true and the buffer is non-empty, the final partial line is flushed through `renderLine` before the trailing newline. Styling: headings → bold, blockquotes → dim, code fences → dim, list items → indented, inline code → cyan, bold spans → bold, links → cyan label + dim url. Pipe mode (no TTY) emits no ANSI codes (handled by `color.ts` `isEnabled()`).

## Environment

- The LLM is a **local llama.cpp server** at `http://localhost:8080` (OpenAI-compatible API).
- Subagent cache preservation uses llama.cpp's `/slots` save/restore endpoints. These are best-effort and require the server to start with `--slot-save-path`; snapshots are retained under fixed process/nesting-depth/slot filenames in that server-side directory.
- **Do not start a second `llama-server` instance if one is already running** — it causes memory issues. Check port 8080 first.
- `run_powershell` in `src/tools/shell.ts` hardcodes `powershell.exe` with a 60-second SIGTERM timeout for foreground commands. This is a Windows-only tool; there is no shell tool for other platforms. Background processes (started with `background: true`) are tracked in an in-process registry and reached by numeric id via `wait_for_process` and `kill_process`; they are not subject to the foreground timeout.

## Pitfalls

- A single large `read_file` tool result can blow the context window — tool output is unbounded (no truncation/pagination yet).
- `LineResult` is structurally duplicated in three files (`session.ts`, `session-dispatch.ts`, `workflow-commands.ts`). They are mutually assignable via structural typing, but an agent adding a field to `LineResult` must update all copies or rely on structural compatibility.
- `session-dispatch.ts` `dispatch()` is currently unused. If you "fix" `Session.handleLine` by delegating to `dispatch()`, you must also reconcile the duplicated `LineResult` types and ensure `workflow-commands.ts`/`session-dispatch.ts` dispatch paths are the live ones. As it stands, only `handleLine` is live.
- Subagent wiring requires three extra callbacks beyond the core `ToolRunner`/`Tool[]`: `withPreservedSlotCache`, `currentAbortSignal`, and display callbacks. These are only available at the `src/wiring.ts` edge. Forgetting the `currentAbortSignal` wiring means a subagent's in-flight model call won't be interrupted by Ctrl+C.
- `run_workflow`-style turns create their own `AbortController`. Both `handleLine` (normal turns) and `handleWorkflowCommand` create per-turn `AbortController`s and call `setCurrentAbort`/`setCurrentAbort(null)` in a `finally`. A new turn-type command must do the same or interrupt support silently breaks.
- `toolRunner.run` returns ` error: unknown tool ${name}` as a plain string, not a `ViseError` variant. Keep it that way until structured tool errors land (see "Future Work" in ARCHITECTURE.md).
- `contextMax()` must be queried live per model, never cached — window sizes differ per model.
- A 200 response with a non-JSON (e.g. plain-text) body now surfaces as a `malformed` error (`stream returned no data`) instead of a `network` error — a deliberate, more accurate classification now that the client always requests `stream: true`.
