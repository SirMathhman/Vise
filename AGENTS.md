# Vise — Agent Instructions

Vise is an interactive LLM chat REPL written in TypeScript on the Bun runtime.
Full design rationale, invariants, and target layout live in [ARCHITECTURE.md](ARCHITECTURE.md) — read it before making structural changes.

## Commands

| Task       | Command             | Notes                                                                                                                                          |
| ---------- | ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Run        | `bun run index.ts`  | Entry point. No build step — Bun transpiles TS on the fly.                                                                                     |
| Web UI     | `bun run web`       | Starts the Bun HTTP/WebSocket server at `http://localhost:3000` by default. Set `PORT` to override.                                            |
| Web dev    | `bun run dev:web`   | Builds the browser bundle, rebuilds it when `web/src/` changes, and watches/restarts the Bun server.                                           |
| Install    | `bun install`       | Server and core have zero runtime deps; the only runtime deps are `marked` and `dompurify`, bundled into the web UI (`web/src/markdown.ts`), and `playwright-core`, used only by the `browser_run_code` runner.   |
| Type-check | `bunx tsc --noEmit` | Server/core/tests (adds the DOM lib for the web tests; excludes `web/`). Browser code: `bun run typecheck:web` (`web/tsconfig.json`, DOM lib). |
| Lint       | `bun run lint`      | ESLint with typescript-eslint. Config in `eslint.config.js`.                                                                                   |
| Test       | `bun test`          | Bun's built-in `bun:test` runner; suites live in `test/`.                                                                                      |

## Surface (product features an agent touches)

Two surfaces an agent commonly edits. The list below is a quick reference — the
authoritative definitions live in the source files linked.

**User-facing slash commands** — dispatched in `Session.handleLine`
(`src/repl/session.ts`); help text is rendered by `formatHelp` in
`src/output/format.ts`. To add one, handle it in `handleLine` and add it to
`formatHelp`.

- `/exit`, `/help`, `/context`, `/hooks` (the configured pre/post-turn hook commands from `.viserc.json`) / `/hooks add pre|post "<command>"` / `/hooks remove pre|post <number>` / `/hooks profile <name> [add|remove pre|post "<command>"|<number>]` (global hooks always run; a profile can also own hooks that run only while it is the active profile, in addition to the global ones — stored as `pre:<command>` / `post:<command>` entries of the `hooks:` JSON-array frontmatter line of the profile `.md`, applied by `SessionHooks` in `src/repl/session-hooks.ts`, re-read before every turn and workflow; the web hooks panel edits the global hooks and the profile editor edits a profile's own) (edits apply to the running session at once and are saved to `.viserc.json` through `HookSource`; the web UI "hooks" panel edits them too, via `hooks_get` and the same `/hooks` lines; one process-wide `HookStore` in `src/edge-sources.ts` holds the live hook arrays shared by every web connection, saves atomically, and its `onChange` makes the server push a `hooks` message to every open panel), `/compact`, `/new` (fresh conversation; the old one stays auto-saved, the active profile is re-applied; web UI "new" button)
- `/goal` (status and current goal) / `/goal on|off` / `/goal clear` — goal checking (on by default in the edge wiring, off for a bare `Session`): when the user speaks, a throwaway call derives the goal (kept across turns until met, so "?" or "ok" continue the task); when the model stops, another asks whether it was accomplished (`yes` with evidence, `no` with the next step, or `blocked` on the user) and a `no` pushes a continue note and runs the turn again, as many times as needed, except that the same step repeating with nothing done in between counts as blocked, and after every 8 automatic continues the user is asked (the same `onMaxRounds` prompt) whether to go on. The continue notes are not the user's words, so they are never saved or summarised (`GoalTracker.isNote`), the conversation is compacted between continues when it is full, and a failed goal derivation falls back to what the user just said, never to the previous goal. Both calls are schema-constrained JSON appended to the conversation for that one request only (never stored) and fail open (unparseable counts as met). `src/core/goal.ts` (pure), `src/repl/goal-loop.ts` (`GoalTracker`, the `/goal` command, `GoalEvent`s shown by the terminal `StreamDisplay.onGoal` and the web `goal`/`goal_state` messages and header toggle). `LlmClient.chat` encodes the conversation as the tool protocol even for schema-constrained requests so these calls share the prompt cache.
- `/image <path>` (attach an image file to your next message; `/image` shows what is attached, `/image clear` drops it) — the terminal's way to show the agent a picture; the web page attaches images by paste, drop or the 📎 button and sends them with the line (`images` on the `line` message, checked by `acceptPictures` in `src/web/pictures.ts`, at most 6 of at most 10 MB, png/jpeg/gif/webp). Refused unless the active model can see images. Via `ImageSource` (`FileImageSource` in `src/tools/images.ts`) and `PendingImages` (`src/repl/image-command.ts`)
- `/model` (list) / `/model <name>` (switch) — via `ModelController`
- `/burst` (status) / `/burst on|off` — burst mode: think once to plan, then tool calls run with a calls-only grammar (no thinking) until the model emits `<done/>`, a tool returns `error:`, or its tool-name probability is below `BURST_MIN_CONFIDENCE`; handled in `runTurn` via `TurnCallbacks.burst`
- `/tool` (list, grouped by category) / `/tool <name|category> enable|disable` (a category toggles its whole group, including tools that start disabled such as `browser_run_code`) — via `ToolController`
- `/profile` (list) / `/profile <name>` (set) / `/profile init <name>` (create) — via `ProfileSource`; `/profile <name> tools [a,b|all]` shows/sets a tool whitelist stored as `tools:` frontmatter in the profile `.md` (applied on switch via `ProfileToolGate`, prior tool states restored on leaving; web UI "profiles" panel edits it)
- `/note` (list, grouped by scope and category) / `/note init [--global] <name> [category]` (create; in the project unless `--global`) — via `NoteSource`. A note has a **scope**: `project` (`.vise/notes/`) or `global` (`~/.vise/notes/`, `globalDataDir`, shared by every project and by no-folder sessions; a project whose data directory is the global one lists those notes once, as global). Notes are the standard memory and skill systems consolidated into one store; suggested categories `user-info`, `memories`, `skills`. Every consumer (note tools, `/note`, web editor, startup message) goes through `NoteStore` (`src/note-store.ts`), which takes a `NoteId` {scope, category, name} so a directory is never paired with a scope by hand, and owns the cross-scope move (copy, then delete; the copy is removed if the delete fails); the file layout is `src/notes.ts`, listing text `src/notes-format.ts`. Global notes appear in every project's startup message and `save_note` can write them without confirmation, so treat their text as data. A note's category is its subdirectory: `<scope's .vise>/notes/<category>/<name>.md`; notes directly in `.vise/notes/` are in the `default` category (nothing else is hardcoded; categories exist once a note uses them; names are unique per category; `src/notes.ts`). The web UI edits notes in the settings panel's "notes" tab (`web/src/notes-panel.ts`; create, edit, move/rename by changing name or category and saving, delete) through the `notes_list`/`note_get`/`note_save`/`note_delete` messages (every note is named by scope, category and name; changing the scope moves it) handled directly in `src/web/notes-api.ts` (never queued behind a turn); emptied category directories are removed
- `/workflow` (list) / `/workflow <name> [input]` (run) / `/workflow init [--global] <name>` (create) — via `WorkflowSource`; JSON files live under `.vise/workflows/` or `~/.vise/workflows/`
- `/save` (list) / `/save <name>` (name the current session and save it), `/resume` (list, shows name and uuid) / `/resume <id>` (restore; a unique id prefix works), `/delete <id>` (delete) — via `SessionSource`. Sessions are stored as `.vise/sessions/<uuid>.json` with the display name inside the file; commands never take the name

**Model-facing tools** — defined in `src/tools.ts` (`tools: Tool[]`) with their
implementations in `src/tools/files.ts`, `src/tools/shell.ts`,
`src/tools/notes-tool.ts`, `src/tools/subagent.ts`, `src/tools/ask-user.ts`,
and `src/tools/self.ts`; dispatched by name by
the core in `src/core/engine.ts`. To add one, append a definition to `tools`
in `src/tools.ts`, add a handler function in the matching domain module, and
register it in the `baseHandlers` map in `src/tools.ts` (or pass it as an
`extra` handler to `createToolRunner` in `index.ts` when the handler depends
on edge services constructed later, such as the subagent handler's `Client`
or the `ask_user` handler's `RlUserPrompter`).

- Large tool results (more than 250 lines or about 20,000 characters, `isTooLarge` in `src/tools/temp-store.ts`) are not shown to the model: `createToolRunner` saves them to the session's temp directory (`TempStore`, under the OS temp folder `vise/<id>`; not persistent: removed by `EdgeSession.cleanup()` when the session ends; a live session refreshes its folder's time hourly and on every use so the sweep of folders older than a day never takes it; a saved file that has vanished, or a failed write, returns a plain error or a truncated inline result instead of throwing; saved files do not survive a restart, so a resumed session's old names are gone) and returns the first lines plus how to read the rest. The temp tools `read_temp` (name, offset, limit; at most 250 lines), `search_temp` (regex over one or all saved files, at most 100 matches) and `list_temp` are core tools (`CORE_TOOLS`), are not file-system tools, and so exist in every session including ones with no working directory; their own output is bounded and never spilled.
- Files (`read_file` takes optional `offset`/`limit` lines; a file over 250 lines or about 20,000 characters comes back as its first 250 lines with a pointer to the rest, a small one whole): `list_directory`, `read_file`, `create_file`, `edit_file`,
  `delete_file`, `delete_directory`, `find_files` (recursive regex name match),
  `search_files` (recursive regex content search, file or directory)
- Images: `view_image` (a png/jpg/gif/webp file, up to 10 MB, shown to the model with the tool result; a file-system tool) and `browser_screenshot` (a PNG of a tab, `full_page` where the engine can: CDP `Page.captureScreenshot`, BiDi `browsingContext.captureScreenshot`, and in the Firefox extension only the visible part, by bringing the tab forward and `tabs.captureVisibleTab`). **How pictures travel:** a `Message` can carry `images` (`Picture`: the SHA-256 `id` of the bytes, the `mime` taken from the bytes themselves, a label, size; never the bytes, so conversations and saved sessions stay small). The bytes live in the shared image store (`ImageStore` in `src/image-store.ts`, `~/.vise/images/<id>.<ext>`, written once, deduplicated; nothing deletes them, and they are plaintext, so a screenshot of a sensitive page stays there until you remove the folder) and are turned into a `data:` URI only when a request is built (`LlmClient.imageResolver`); the web page loads thumbnails from `GET /api/image/<id>` (`serveImage` in `src/web/server.ts`, ids are 64 hex digits only, same-origin only). A tool puts its picture in the session's `ImageOutbox` (`src/tools/images.ts`), `ToolRunner.takeImages()` hands it to the engine, which stores it on the tool-result message and tells `TurnCallbacks.onImage` (the terminal prints a `📷 name · WxH · KB` caption, the web page shows a thumbnail that opens full size on click, `web/src/lightbox.ts`; the `image` WebSocket message). `encodeMessages`/`plainMessages` (`src/client/tool-protocol.ts`) send them as `image_url` parts; they stay in the conversation until compaction summarises them, and count about 4000 tokens each in the size estimates. **Vision gating:** tools flagged `requiresVision` start disabled and are enabled only while the active model can see images (`LlmClient.supportsVision`: the router lists a `--mmproj` for it, or `/props` reports vision), re-checked on every `/model` switch (`controls` in `src/wiring.ts`); they stay in the prompt's tool list but cannot be called (the grammar excludes them).
- Shell: `run_powershell` (Windows-only, foreground 60s SIGTERM timeout; `background: true` spawns a background process and returns a numeric process id), `wait_for_process` (block on a background process up to a timeout, in ms), `kill_process` (SIGTERM a background process)
- Notes: `list_notes` (grouped by scope and category; optional `scope` and `category` filters), `read_note`, `save_note` (optional `category`, default `default`; replaces an existing note of the same name in that scope and category), `delete_note` (`read_note`/`save_note`/`delete_note` **require** `scope`: `project` or `global`; `read_note`/`delete_note` take an optional `category`, needed only when the name exists in several; the startup message lists the notes by scope and category with counts and summaries)
- Subagents: `run_subagent` (runs a subagent — a fresh, isolated conversation with its own profile — to perform a task and return its final result; the subagent can use all the same tools, including `run_subagent`)
- User interaction: `ask_user` (pauses the turn, prompts the user with a question and optional predefined choices, and returns the user's answer as the tool result; the user may pick a choice or type a free-form reply; `multi_select: true` lets the user select multiple choices, separated by commas)
- Browser: `browser_open`, `browser_tabs`, `browser_navigate`, `browser_read` (page text plus an outline of the interactive elements that are clearly in the viewport right now, tagged with refs e1, e2, ... (at least half of the element in view and not hidden behind or clipped by another element), ending with notes on how many more lie above/below/left/right, how far the page is scrolled and which inner panels scroll, each with a ref; `SNAPSHOT_SCRIPT` in `src/browser/page-scripts.ts`; `browser_scroll` brings the rest into view: up/down/left/right by a page-sized step or `amount` pixels, top/bottom, the page or the scrollable panel around a `ref` (or the largest panel in view when the page itself cannot scroll that way), as the page action `scroll`; the outline is always shown in full, while a page's text over 250 lines or ~20,000 characters is saved to a temp file with only its start shown, `src/tools/browser.ts`), `browser_wait_for_text`, `browser_wait_for_text_gone` and `browser_wait_for_idle` (wait for text to appear or disappear, or for the page to stop changing for ~0.6 s, and not before 1.5 s; default 10 s, at most 60 s; they poll `BrowserBackend.pageProbe`, an optional in-page look returning whether the text is there and a fingerprint, so a poll is a few bytes, with `readText` as the fallback, `src/tools/browser-wait.ts`, `src/browser/probe.ts`; case- and whitespace-insensitive; they stop on a dialog or when the turn is interrupted, which is why `ToolRunner.run` takes an `AbortSignal`; for pages that change without loading, where a read right after an action shows the old content), `browser_click`, `browser_hover`, `browser_drag`, `browser_select` (choose an option of a `<select>` by visible text or value, a part of the text is enough; `options` for a multi-select; sets the value and fires `input`/`change` so dependent fields update; the drop-down's own list cannot be driven by clicks or typing in any backend; run through the one generic `BrowserBackend.runPageAction(id, action)`: a `PageAction` (`src/browser/page-scripts.ts`, today only `select`) names an action on a ref, every backend runs its script in the page, and the extension builds the script itself from the named action and never runs script text from the server, so a new widget needs one entry there and a tool, not a method per backend; `browser_read` also shows every field's label and every drop-down's options), `browser_type` (text and/or a key) (after a click, drag or type, a tab the page opened by itself, a `target=_blank` link or `window.open` such as "Apply on company website", is reported in the result as `[a new tab opened: tab N: ...]`: `TabWatcher` in `src/tools/tab-watch.ts` compares the tab list before and ~0.3 s after; the new tab is usable like any other, and in the Firefox extension a tab opened by a tab the agent controls is granted automatically, `extension/src/tabs.ts`), `browser_upload` (attach local files, `paths` relative to the working directory or absolute, to a file input; `ref` may be the input or the upload button/label/wrapper next to a hidden one, found by `fileInputScript` in `src/browser/page-scripts.ts`; a native file picker cannot be driven, so this is the only way; optional `BrowserBackend.uploadFiles`: CDP `DOM.setFileInputFiles`, BiDi `input.setFiles`, and through the Firefox extension the server reads the files and sends them base64 (10 MB total) for the page script to build `File`s with a `DataTransfer`), `browser_handle_dialog`, `browser_run_code` (disabled by default — `RISKY_TOOLS` in `src/wiring.ts`; enable with `/tool browser_run_code enable` — because the snippet runs with the full privileges of the user; a Playwright snippet with `page` in scope; runs in a separate `node` process, `src/browser/playwright-runner.mjs`, because Playwright's CDP transport does not work under Bun — `node` must be on the PATH; `playwright-core` is a runtime dependency used only by that runner) (an integrated headless Edge/Chrome driven over CDP; handlers in `src/tools/browser.ts` depend only on the `BrowserBackend` interface in `src/browser/types.ts`, three implementations: `ExtensionBackend` (below), `ChromiumBackend` (CDP; the terminal default in `src/wiring.ts`) and `FirefoxBackend` (WebDriver BiDi, `src/browser/{bidi,bidi-actions,bidi-view,firefox}.ts`: launches a headless Firefox on a private profile, or attaches by port to a Firefox the user started with `--remote-debugging-port` and then leaves it running; no screencast exists in BiDi so the live view polls screenshots; `browser_run_code` is unsupported there; Firefox allows one BiDi client at a time). The web server shares one `SwitchableBrowser` (`src/browser/switchable.ts`) whose engine is the global setting in `~/.vise/browser.json` (`src/browser/settings.ts`), changed from the settings panel's "browser" tab via the `browser_settings_get`/`browser_settings_set` messages (switching closes the running browser); backends are constructed only in `src/wiring.ts` and `src/browser/switchable.ts`; launched-browser profile/process helpers are shared in `src/browser/processes.ts`; the web server shares one browser across connections and the workspace shows it live via the `browser_*` WebSocket messages in `src/web/browser-bridge.ts`; the frontend must `close()` the browser on shutdown, and the next launch reaps browsers orphaned by a crashed run)
- Tool search: `search_tools` (looks up the full signature of a deferred tool by keyword or exact names). Only the core tools (files, `run_powershell`, `ask_user`, `search_tools`; `CORE_TOOLS` in `src/tools/search-tools.ts`; tool definitions live per domain in `src/tools/defs/`, composed in `src/tools.ts`) are fully described in the system prompt; every other `Tool` is flagged `deferred` and appears there as a name plus a one-line summary, grouped under its `category` (set per definition group in `src/tools.ts`; `search_tools` also accepts a bare category name to return the whole group; `/tool`, the web tools panel and the profile editor list tools grouped by category too). There is deliberately no "call tool" tool: calls are parsed from the model's text and the grammar already allows every enabled tool by name. To add a tool that should always be visible, add it to `CORE_TOOLS`.
- Self: `self` (reports the agent's own live state — backend, active model, working directory, context-window fill, active profile, and pre/post-turn hook commands — so the model can confirm which model and profile it is acting as or how full its context is)

## Hard rules (from the architecture invariants)

- **No `process.exit()` anywhere.** Termination happens when the event loop drains; set `process.exitCode` instead. `process.exit()` truncates buffered stdout through pipes.
- **The core (`src/core/`) is pure.** No `node:` imports, no `console`, no `process`, no globals. Same input → same output.
- **No `throw` in core paths.** Errors are the structured `Result<T>` / `ViseError` union from `src/core/errors.ts`. All display formatting belongs in `src/output/format.ts`.
- **Dependency arrows point edge → core only.** `client/llm.ts` is the sole module that performs network I/O; `src/tools.ts` (definitions + registry) and the handler modules under `src/tools/` are the edge implementation of the core's `Tool`/`ToolRunner` types.
- **Explicit `.ts` extensions on all imports** (`allowImportingTsExtensions`), ESM throughout.
- **Size limits:** files < 500 code lines, functions < 100 lines. Split at a natural seam when approaching the limit.

## Current-state notes (code lags the architecture doc)

For detailed module descriptions and the edge-owns-I/O pattern, see
[ARCHITECTURE.md](ARCHITECTURE.md). The notes below capture only what is
**not** in that document or is non-obvious from reading the code.

- `src/wiring.ts` exports `createEdgeSession`, the shared factory for the LLM client, edge data sources, tool runner, and `Session`. Both `index.ts` (`TerminalDriver`) and `src/web/server.ts` use it. Keep transport-specific behavior in the respective driver, not in shared wiring or the core.
- `index.ts` is thin terminal wiring; the interactive surface lives in `src/driver/terminal.ts`. The web frontend is served by `src/web/server.ts` (entry `src/web/main.ts`); TypeScript sources live in `web/src/` and `bun run web` builds them to `web/dist/` before serving. There is no `src/cli.ts` yet. Don't add TTY/pipe special-casing into `index.ts`.
- **Session root:** a session is rooted at one directory for its whole life. The terminal roots it at the working directory it was started in; a web connection takes it from the page's `?root=<absolute path>` query, and **a page with no `root` starts with no folder** (a `root` that is not an existing directory also falls back to no folder, with a `badRoot` note in the `root` message; the server's own start directory is only where the folder chooser opens). The page remembers the last folder the server confirmed in this browser (`localStorage` `vise-root`, `web/src/restore-root.ts`) and puts it back into the address when it is opened without one, before it connects, so a fresh visit and the Firefox extension's sidebar (whose address is always `/?ui=sidebar`) return to the same project, and a reload keeps it through the address itself and the server never moves it (`src/web/roots.ts` `RootRegistry`; `createEdgeSession({ root })`). Tools resolve relative paths against the root, `run_powershell` and hooks run in it, and notes/profiles/sessions/`.viserc.json` live under it (`dataDirFor(root)` — the module-level `dataDir` is only the terminal default). The web explorer API (`/api/fs`, `/api/file`) takes the page's `root` and serves only roots with an open session. The top bar's ☰ menu ("Start a new session": "Open folder…" or "No folder", above the saved sessions) asks the server to show the OS folder chooser (`POST /api/pick-folder`, a web page cannot learn a folder's absolute path) and opens the choice as a new session in the same tab (page navigation). Roots are not a sandbox: absolute paths still work in tools. **No-folder sessions:** `createEdgeSession({ noFolder: true })` (terminal `--no-folder`, web `?root=none` / the top bar "no folder") have no working directory: the tools flagged `requiresFileSystem` (the `files` and `shell` categories and `browser_run_code`; `isFileSystemTool` in `src/tools.ts`) are removed from the tool list, prompt, grammar and runner, and the system message says there is no file system. Their profiles, notes, sessions, workflows and hooks live in a generated directory (`noFolderRoot`, `~/.vise/no-folder`), shared by all no-folder sessions; the web file tree is hidden. Trust model: any local process can open a session on any directory (loopback + Host/Origin checks only), and a root's `.viserc.json` hooks run commands, so only open folders you trust.
- **Firefox extension (`extension/`):** Vise as UI + hands inside the user's own Firefox. The Bun server stays the brain; the extension (Manifest V2, persistent background page) holds a WebSocket to the server's `/ext` endpoint (accepted only for a `moz-extension://` Origin **and** the pairing token in `?token=`; `src/web/ext-hub.ts` `ExtensionHub`, `src/web/ext-token.ts`) and runs browser operations in real tabs; its sidebar embeds the Vise web UI as `/?ui=sidebar` above a control strip ("Give Vise this tab", release). A `/ws?ui=sidebar` session gets `ExtensionBackend` (`src/browser/extension.ts`, over the `ExtensionLink` interface) instead of the shared headless browser; every other session is unchanged. When the user hands a tab over ("Give Vise this tab") or takes one back ("release"), the extension sends a `shared`/`released` event over `/ext`, `ExtensionHub.onShare` passes it on, `BrowserBackend.onUserShare` turns it into text (`describeShare`: marked as an automatic notice not from the user, with the tab's title and address, which a page controls, flattened to one line, capped, quoted and described as data), and `createEdgeSession` forwards it to `Session.notify`, so the agent is told in the conversation (a user message queued in `NoticeQueue`, `src/repl/round-hooks.ts`, and added at the start of the next turn or between rounds, never between a tool call and its result). The agent may use only tabs it opened or the user handed over: the extension enforces it (`extension/src/tabs.ts`), the server never lists other tabs. Actions are synthetic DOM events (`extension/src/page-actions.ts`; an extension cannot make trusted input, so sites needing it will not respond), page dialogs are auto-answered and reported in the snapshot (`extension/src/dialogs.ts`), and `browser_run_code`, the live view and `browser_handle_dialog` are unavailable. `src/browser/page-scripts.ts` is shared with the other backends. Pairing is automatic: the server keeps a random token in `~/.vise/ext-token` and serves it (`/api/ext-token`) only to the Vise page itself; the sidebar asks the embedded page for it with a `vise-hello` postMessage (answered only to a `moz-extension://` origin, `web/src/pairing.ts`) and stores it for the background page. The sidebar's status widget always shows the state of each link (server, extension build, pairing, link, shared tabs) and whether the current tab is shared; every `bun run build:ext` stamps all scripts with one build id (`__VISE_BUILD__`), and a background page from an older build is reported as "out of date: Reload it" (the sidebar reloads from disk when reopened, the background page only on Reload in `about:debugging`). The model gets explicit tool errors for "extension not connected" (`NOT_CONNECTED`) and "no tab shared yet" (`BrowserBackend.noTabsHint`). Build with `bun run build:ext` (`typecheck:ext` for types), then load `extension/manifest.json` through `about:debugging` (Load Temporary Add-on); set the server port on the extension's options page (default 3000).
- **Web auto-resume:** a web page that connects to a folder restores that folder's most recently saved session (by file time, `latestSessionId` in `src/sessions.ts`) before anything else runs (`queueAutoResume`, `src/web/resume.ts`, queued first on the connection): the model gets it through the normal `/resume`, and the page gets a `history` message (`src/web/history.ts`) that it replays into the chat log (`web/src/history.ts`): what the user typed, the agent's replies, tool lines and pictures, the latest 400 lines. Only messages marked `Message.typed` are shown as the user's (sessions saved before the mark show every user message except the opening context and bracketed notices). A folder with no saved session starts blank; `/new` starts fresh, but a reload before the first turn of the new conversation restores the previous one. The terminal does not auto-resume (`/resume`).
- **Web UI layout:** a top bar holds menu-style items — `files` (toggles the workspace side view), `sessions` and `settings` (dropdown panels); the header below it keeps the model/profile/reasoning selects, `tools`, `burst`, status, stop and new. The settings panel has tabs (`profiles` editor, `hooks`); new global configuration belongs in a settings tab. The dropdown panels (tools, sessions, settings) are registered in one group in `web/src/panel-switch.ts` (`registerHeaderPanels`): at most one is open, buttons get `aria-expanded`/`aria-controls`, Escape closes them, and each panel supplies what to refresh on open. A new dropdown panel must register there instead of toggling its own `hidden` class. The `files` workspace is deliberately outside the group (it is a side view, not a dropdown).
- **Web UI sessions panel:** toggleable panel that lists saved sessions, resumes one (sends `/resume <name>` and clears the chat log), and saves the current conversation (sends `/save <name>`). The browser sends `/save` and `/resume` as regular lines through the existing `handleLine` path — no new core or edge code. See `ui-features.md` for the feature backlog.
- `src/core/engine.ts` mutates the `messages` array in place by design; it's a documented side channel, not a bug.
- **Long turns (hundreds of tool calls are expected):** `MAX_TOOL_ROUNDS` (`src/core/engine.ts`) is 500 rounds, then the user is asked (`onMaxRounds(question)`, the question says what is being asked). Before each round after the first the engine calls `TurnCallbacks.onRound`; the session's hook (`src/repl/round-hooks.ts`) compacts when the last prompt passes `IN_TURN_COMPACTION_THRESHOLD` (0.75) of the window, saves the session every 25 rounds, and every 50 rounds (goal checking on) runs the goal progress check (`checkProgress`: progressing or stuck; stuck ends the turn as "needs you" and keeps the goal). Compaction decides from the last measured prompt plus an estimate of what the last round added (`addedSinceLastCall`), keeps the verbatim tail within a quarter of the window (`TAIL_SHARE`), and a compaction that fails ends the turn with a visible reason instead of overflowing; the same hook runs for workflows (`WorkflowCommands.roundHook`) and, compaction only, for subagents (`compactInPlace`, `subagentCallbacks` in `src/wiring.ts`). A "stuck" progress check asks the user (`onMaxRounds`) rather than ending the turn on its own. Stop reasons are shown through `onToken` (the reply was streamed). Compaction (`src/repl/compaction.ts`) normally splits at user turns (`RECENT_TURNS_TO_KEEP`) but falls back to `splitWithinTurn` (`src/core/engine.ts`), which keeps the turn's opening user message and its last `ROUNDS_TO_KEEP` rounds verbatim and summarizes everything before them, so one giant turn can be compacted too. `COMPACTION_THRESHOLD = 0.9` (`src/repl/session.ts`) drives `maybeAutoCompact()`.
- **Global prompt:** `GLOBAL_PROMPT` (`src/global-prompt.ts`, built in, not configurable) leads every main conversation's system message whatever the profile (`SessionOptions.systemPrompt`, set only in `src/wiring.ts`; `systemMessageFor` in `src/repl/session-options.ts` builds it, so a bare `Session` still has just the working-directory line). It teaches the agent when to save notes (facts about the user, standing preferences, project decisions, hard-won procedures; never secrets or anything that came from a page, file or tool) and treats external text as data. Profiles stay user messages after it (switching never rewrites the system message, which keeps the prompt cache), so the model sees: global prompt, working directory, tool list (appended by the tool protocol), the initial context (tree, notes), then the profile. It is fixed for a conversation: a change applies from `/new` or when a session is resumed (the system message is rebuilt from the current code, so the first resumed turn misses the prompt cache once). Subagents do not get it.
- `API_KEY`, `URL`, `MODEL` are hardcoded constants in `src/client/llm.ts` (no env config by design — local-only tool).
- `src/data-dir.ts`: `dataDirFor(root)` is the per-session data directory (`<root>/.vise`); any per-project store takes the session root and calls it. The module-level `dataDir` (the start directory) is only the terminal default and the shared browser profile location.
- `src/repl/session-dispatch.ts` holds a WIP `dispatch()` that is a structural duplicate of `Session.handleLine`; `handleLine` in `session.ts` is still the live dispatcher. **Do not assume `dispatch()` is the active path.**
- Subagent wiring requires three extra callbacks beyond the core `ToolRunner`/`Tool[]`: `withPreservedSlotCache`, `currentAbortSignal`, and display callbacks. These are only available at the `src/wiring.ts` edge. Forgetting the `currentAbortSignal` wiring means a subagent's in-flight model call won't be interrupted by Ctrl+C.
- **Turn interruption (Ctrl+C):** `terminal: false` makes readline emit `SIGINT` on Ctrl+C rather than consuming it, so the edge owns the behavior. While a turn is in flight, the first Ctrl+C calls `Session.interrupt()`, which aborts the per-turn `AbortController`; at an idle prompt Ctrl+C exits (`exitCode = 130`). Subagents inherit the same `ToolRunner`/`Tool[]`, so their turns are interruptible too.
- **Streaming:** the core threads optional `onToken`/`onThinking`/`onPromptProgress`/`onToolCall`/`onMaxRounds` callbacks as side channels — the core never does I/O. `StreamDisplay` (`src/driver/stream.ts`) owns all mutable streaming state. A tool call is shown as `<icon> <name> · <detail>` (`formatToolCall` in `src/output/tool-line.ts`: an icon per tool and a short detail from the arguments, `onToolCall(name, depth, args)`; the web `tool` message carries the finished `text`). `LineResult.streamed` tells the driver the reply was already written, so it emits only the trailing newline. Compaction/`summarize` calls pass no `onToken`, so they are not streamed.
- **Tool-call protocol:** `src/client/tool-protocol.ts` renders tool definitions into the system prompt as text and the client sends a per-request GBNF `grammar` (free text that cannot contain the call delimiter, then calls to enabled tools only; llama.cpp ignores lazy-grammar triggers on this endpoint; never the `tools` field) restricting callable names to enabled tools, so toggling a tool never changes the prompt/KV cache. Calls are parsed from `<|tool_call|>{json}<|/tool_call|>` in the reply; `TurnCallbacks.isToolEnabled` carries the enabled state to `LlmClient.chat`.
- **Per-session tool state:** `createEdgeSession` builds its own `ToolSet` and passes it to both the `Session` and `createToolRunner`; there is no module-level tool controller, so web connections never share enabled/disabled state.
- **Lazy `/profile`:** switching profile queues its messages (profile text and tool notice) in `Session.pendingProfile`; each switch discards the previous queue and the last one is flushed into the conversation at the start of the next turn, workflow, or `/save`. Tool enabled-states change immediately.
- **Markdown rendering:** `src/output/markdown.ts` provides `renderLine(line, inFence)` — a pure per-line state machine for terminal markdown styling. Pipe mode (no TTY) emits no ANSI codes (handled by `color.ts` `isEnabled()`).

## Environment

- The LLM is a **local llama.cpp server** at `http://localhost:8080` (OpenAI-compatible API).
- Subagent cache preservation uses llama.cpp's `/slots` save/restore endpoints. These are best-effort and require the server to start with `--slot-save-path`; snapshots are retained under fixed process/nesting-depth/slot filenames in that server-side directory.
- **Do not start a second `llama-server` instance if one is already running** — it causes memory issues. Check port 8080 first.
- `run_powershell` in `src/tools/shell.ts` hardcodes `powershell.exe` with a 60-second SIGTERM timeout for foreground commands. This is a Windows-only tool; there is no shell tool for other platforms. Background processes (started with `background: true`) are tracked in an in-process registry and reached by numeric id via `wait_for_process` and `kill_process`; they are not subject to the foreground timeout.

## Pitfalls

- A single large `read_file` tool result can blow the context window — tool output is unbounded (no truncation/pagination yet).
- `LineResult` is structurally duplicated in three files (`session.ts`, `session-dispatch.ts`, `workflow-commands.ts`). They are mutually assignable via structural typing, but an agent adding a field to `LineResult` must update all copies or rely on structural compatibility.
- `session-dispatch.ts` `dispatch()` is currently unused. If you "fix" `Session.handleLine` by delegating to `dispatch()`, you must also reconcile the duplicated `LineResult` types and ensure `workflow-commands.ts`/`session-dispatch.ts` dispatch paths are the live ones. As it stands, only `handleLine` is live.
- Subagent wiring requires three extra callbacks beyond the core `ToolRunner`/`Tool[]`: `withPreservedSlotCache`, `currentAbortSignal`, and display callbacks. These are only available at the `src/wiring.ts` edge. Forgetting the `currentAbortSignal` wiring means a subagent's in-flight model call won't be interrupted by Ctrl+C.
- `run_workflow`-style turns create their own `AbortController`. Both `handleLine` (normal turns) and `handleWorkflowCommand` create per-turn `AbortController`s and call `setCurrentAbort`/`setCurrentAbort(null)` in a `finally`. A new turn-type command must do the same or interrupt support silently breaks.
- `toolRunner.run` returns ` error: unknown tool ${name}` as a plain string, not a `ViseError` variant. Keep it that way until structured tool errors land (see "Future Work" in ARCHITECTURE.md).
- `contextMax()` must be queried live per model, never cached — window sizes differ per model.
- A 200 response with a non-JSON (e.g. plain-text) body now surfaces as a `malformed` error (`stream returned no data`) instead of a `network` error — a deliberate, more accurate classification now that the client always requests `stream: true`.
