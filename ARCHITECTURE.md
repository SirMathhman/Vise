# Architecture

This is the canonical design document for Vise. It describes the architecture the project is working toward, not the current code. Keep it ahead of the implementation: when the code catches up, advance this document. It is not a changelog; completed work lives in the git log.

Vise is a Bun + TypeScript command-line application. The target shape is a small, pure core that interprets lines of input, with a thin terminal frontend that owns all I/O.

## Definitions

- **Core**: the pure logic that turns an input line into a result (line classification and command output, and later the command state). Core code takes data in and returns data out. It never reads stdin, writes stdout, reads the environment, or touches the clock or filesystem without being passed the capability.
- **Frontend**: code that connects the core to a medium. The terminal frontend is the only one today. It owns readline, prompts, and stream handling.
- **Composition root**: the single entry point that wires a frontend to the core and reads the process environment. It is the only place that touches `process`.
- **Session**: one run of the REPL, from start until `/exit` or end of input.
- **Command**: a line whose trimmed text starts with `/`. Commands are interpreted by the core and never sent to the model. The set is `/exit`, `/context`, and `/compact` today; the core classifies any other `/` line as `unknown-command`, and the frontend reports it as an error.
- **Exit command**: a line whose trimmed text is `/exit`. The core's line classifier recognises it; after it, the session accepts no further lines, even if they arrived in the same chunk of input. Bare words such as `exit` or `quit` are ordinary lines.
- **Context command**: a line whose trimmed text is `/context`. It reports the prompt tokens the provider counted for the most recent request that reported usage, out of the model's context window. Both numbers come from the provider, not from an estimate. Before any request has reported usage it reports that no request has been sent. After a compaction it reports that the size is unknown until the next request, because the counted size described the history that was replaced; it never says that no request was sent when one was.
- **Compaction**: replacing the history with a summary of it. The summary is requested from the model by sending the whole history followed by a fixed request. The new history is the summary, kept as a user message, followed by the most recent messages. Compaction runs on `/compact`, and automatically before a message when the last prompt tokens reached 80% of the context window. The rules live in `src/core/compaction.ts`. Building the request and the new history, and the 80% check, are pure. `compact` requests the summary through the `Reply` port, which is its only I/O. The summary is model output, so it is untrusted text, and the user must be able to read it before it replaces the history (see Security Concerns).
- **Tool**: an action the model may request by name, with arguments it writes as JSON. A tool is defined in `src/core/tools.ts` (its spec, its argument parsing, its approval rule, and the line shown for a call) and run by a `ToolRunner` that the composition root passes in. Apart from `run_powershell`, which passes the model's command to PowerShell, a tool never receives the model's text as code. A tool that writes or runs anything must be approved by the user before it runs (see Approval and Security Concerns). Today the tools are `list_files`, `read_file`, and `read_command`, which only read; `edit_file`, which replaces the first exact match of a text in an existing file; `create_file`, which writes a new file and never overwrites one; and `run_powershell`, which runs one PowerShell command in the working directory; a command still running after 30 seconds becomes a background job, which `read_command` reads and `kill_command` (approved by the user) stops. All seven are defined in `src/core/tools.ts` and run in `src/tools/`.
- **Approval**: the user's yes before a tool that writes or runs a command. The question shows the change or command, and the answer is a line the user types after that preview has been printed. Any other answer is a refusal, and so are end of input and a stream error. A refusal is returned to the model as the tool's result, and the turn goes on. End of input, a stream error, or `/exit` during a question ends the session and sends no further request to the model.
- **Tool round**: one request to the model and the tool calls it asked for. A message runs rounds until the model answers without a tool call. Each call is shown as a line, run, and its result appended to the history as a tool message before the next round. The loop has no round limit by the user's choice, so a model that keeps calling tools keeps the session busy.
- **Line**: one unit of input without its terminator. Lines are processed in order and each is handled at most once.

Invariants:

1. Once a session has ended, no line after the exit word produces output or side effects.
2. The core never performs I/O. A frontend is the only code that reads or writes streams.
3. Every line the frontend accepts produces one response, or none when the session has ended. A message line may produce several parts, in this order: the compaction notice (or its error), then for each tool round a line per tool call, then the reply text. A round that fails ends the turn with an error line, and the whole turn is removed from the history.
4. Behaviour depends only on the input stream and the arguments passed in, so the same input always gives the same output. The model adapter, the context-window lookup, and the compaction summary are the exceptions: their replies come from the network, so the adapter must make every reply it returns either complete or an error, never a silently truncated success, and the lookup must do the same. A compaction summary that is incomplete or wrong changes every later request, so a failed or truncated summary must leave the history unchanged.
5. Commands are never sent to the model as text. A `/` line is consumed by the core whether or not it is known. A command may make the core send the history to the model (`/compact` does), but never the command text itself.
6. A session releases its streams before it returns. On every exit path (end of input, `/exit`, a stream error, or a reply that throws), the readline interface is closed and the frontend's error listeners are removed, so the process can end without waiting for more input.
7. A stream error that arrives after a session has returned is reported by the composition root with a readable message and exit code 1. It is never an uncaught exception with a stack trace.
8. The prompt prefix is append-only between compactions. The history changes only by appending a user message, then assistant messages (with any tool calls) and tool messages, or by a compaction. A failed request, or a failed round in a turn, leaves no trace in the history: the whole turn is removed, so the next request begins with the same messages as the last completed one. The cache breakpoint is a marker on the last message of each request, whatever its role, and it never changes which messages are sent, so the provider can reuse the cached prefix on every turn that does not compact.
9. The tool definitions are the same in every request. The set of tools is fixed in code, so the tools part of the prompt never changes and the cache is never invalidated by a tool being added or removed mid-session.
10. A write or a command runs only after an approval given after its preview was printed. A line received before the preview is never an approval, and a question never leads to a request to the model once input has ended. Approval is enforced where the tool runs, not only by the loop that asks, so a second caller of the tool runner cannot skip it.
11. Once input has ended or a stream has failed, no further request is sent to the model, whatever the reply has asked for. The turn stops after the reply that was running when that happened, and no tool call in it runs once the session has ended.

## Structure

Target layout:

```
index.ts            composition root: wires process.stdin/stdout and OPENROUTER_API_KEY to the REPL and the model (entry point, keeps `bun run index.ts`)
src/openrouter.ts   model adapter: streams a chat completion from OpenRouter over HTTPS (performs network I/O, passed to the REPL as a function)
src/core/           pure line classification and command interpretation (no node: imports except types)
src/repl/           terminal frontend: readline, prompt, session lifecycle
src/core/messages.ts  shared data types and ports (ChatMessage, ToolCall, Usage, Reply, ContextWindow)
src/core/tools.ts     tool definitions shared with the model adapter (listFilesSpec, readFileSpec, editFileSpec, createFileSpec, runPowershellSpec, readCommandSpec, killCommandSpec), argument parsing, the approval rule (needsApproval, approvalPreview), the Approve port, and the call line
src/core/result.ts    Result type (ok / err) for failures that are returned, not thrown
src/core/compaction.ts  compaction state (Conversation): the summary request, the compacted history, the 80% check, and compact
src/tools/run-tool.ts  dispatches a call by name, checks the target before asking, and runs a change or command only when approve resolves true
src/tools/run-powershell.ts  the only process spawning: runs one PowerShell command in the working directory; a command still running after 30 seconds becomes a background job
src/tools/jobs.ts            background jobs: keeps each job's last 500 lines per stream, reads them, stops a job's process tree, and stops every job when the session ends (at most 5 running)
src/tools/files/    tool runners that touch the disk, one per tool, with contain.ts (resolveInside for existing paths, resolveNewInside for paths that may not exist yet) shared by them.
scripts/            build checks run by `bun run lint` (file count per directory)
*.test.ts           beside the module each one tests (no separate tests/ folder)
```

Dependency direction is one way only:

```
index.ts  ->  src/repl  ->  src/core
index.ts  ->  src/openrouter.ts  ->  src/core
index.ts  ->  src/tools  ->  src/core
```

`src/core` imports nothing from `src/repl`, `src/tools`, `src/openrouter.ts`, or `index.ts`. `src/repl`, `src/tools`, and `src/openrouter.ts` may import `src/core`, never the reverse, and they do not import each other. Tests may import any module. There are no circular imports.

Each source file has one responsibility. Entry points contain wiring only: they read the environment, construct the functions, and call exported functions. Test files live next to what they test, not inside the entry point.

The composition root supplies the reply function and the context-window lookup explicitly. The frontend has no default model, so a session that forgets to pass one fails instead of silently echoing.

Size and style limits, enforced by `bun run lint` as errors (ESLint for the line, function, and type-literal rules, `scripts/check-files-per-dir.ts` for the file count):

- at most 100 lines per function (`max-lines-per-function`),
- at most 500 code lines per file (`max-lines`),
- at most 10 files per directory,
- no object type literals written inline as `{ ... }` (`no-restricted-syntax` on `TSTypeLiteral`); declare a named interface instead.
- no `throw` statements (`no-restricted-syntax` on `ThrowStatement`); failures are returned as a `Result` from `src/core/result.ts`.

Recursion is avoided in core. When a function would need to call a function that calls it back, pass the callback as a parameter instead of importing across files.

## Potential Problems

- **Stream-level behaviour is easy to get wrong.** Readline delivers every line in a chunk at once, so lines already buffered after `/exit` are still yielded by the loop unless the loop stops at the exit line. A regression test must keep covering lines that arrive together in one chunk, not only one chunk per line.
- **The file-count check ignores untracked files.** `scripts/check-files-per-dir.ts` reads `git ls-files`, so a new file counts only after it is staged. A directory can exceed the limit until someone runs `git add`.
- **The frontend has default model stand-ins.** `runRepl` defaults its reply function to an echo, so a caller that omits it gets fake model behaviour without an error. Its context-window default returns an `err` Result, so `/context` reports that no window is configured instead of showing a real limit. The composition root should pass both explicitly.
- **Stream errors end the session as a failure, but not until the reply finishes.** `runRepl` listens for `error` on input and output, and on the readline interface, where readline re-emits input errors. It aborts the interface and returns `err`, which `index.ts` prints before exiting with code 1. The abort does not reach the reply, so an error that arrives during a model stream is reported only after the stream ends or fails.
- **Partial replies stay on screen.** When a model stream fails (an `{"error": ...}` event, or the connection ending before `data: [DONE]`), `streamChat` yields an `err` result and `runRepl` drops the user line from the history, so no truncated answer is recorded. The text already printed is not marked as incomplete, and nothing tells the user it was discarded.
- **Retired exit words reach the model.** `exit` and `quit` are no longer commands, so a user who types them from habit sends them to OpenRouter as a message, spends a request, and gets a reply. The session stays open until `/exit` or end of input. The frontend should say which command ends the session when it starts.
- **The frontend still owns the conversation state.** The rules are in `src/core/compaction.ts`: `recordUsage`, `compactIfNeeded`, and `compactNow` are transitions over `Conversation`. But `runRepl` holds the `conversation` variable, assigns each step's result to it, appends the user, assistant, and tool messages itself, and decides which line kind reaches which transition. The core does not yet own the sequence of a turn (see Future Work).
- **Tool rounds are unbounded and each one is a paid request.** `runRepl` loops until a reply has no tool call. Nothing limits the number of rounds, the calls per round, or the total output, so one message can run many requests. This is accepted by the user, but the cost and the time it takes must be visible to the user as it happens, and a model that loops should be stoppable with Ctrl+C (see Future Work).
- **`read_file` reads the whole file before the range is cut.** `readFileLines` loads the file into memory, splits it, and only then applies the 500-line cap, so a large file is read in full. The cap counts lines, not bytes, so 500 lines of 1 MB each come back whole and enter the history. The read should stop at a byte cap, and the result should say when it was cut, as the line cap does.
- **`list_files` output has no size limit.** A listing returns every file name up to the depth, with no cap on the count. Hidden entries are skipped, but ordinary large folders such as `node_modules` are not. The whole listing becomes one tool message, is sent in every later request, and counts toward the context window until compaction removes it.
- **Tool lines are not shown as they are received.** A call's line is printed after the reply has ended, because the call is only complete when the stream finishes. A long reply therefore appears before the call that caused it has a line.
- **The stored prompt size is only set by completed requests.** A completed request records its size and clears the compacted flag. A compaction clears the size, so `/context` says the size is unknown since the compaction rather than "no request sent yet". A failed request does not record its size. A failed compaction keeps the conversation unchanged, so the next message tries again and prints an error. The automatic check still uses the size of the previous request, not the size of the request about to be sent, so a message that adds many tokens can overflow the window before the next check.
- **`/context` numbers may not match the last line.** The count is from the last request that reported usage. A later request that failed is removed from the history but leaves the earlier count in place, and the output does not say which request it belongs to.
- **Response schemas can drift from OpenRouter.** The zod schemas in `src/openrouter.ts` are hand-written, and the tests use fixtures written from the same assumptions, so a change on OpenRouter's side passes the tests and fails only at run time. Specific risks: `choices` and `usage` are `optional`, not nullable, so a `null` there fails the whole stream; `ModelListingSchema` requires every entry of `data` to match, so one model with a `null` `context_length` makes `/context` fail for every model; and the error text from zod is printed verbatim, which is the escape-sequence risk under Security Concerns. The schemas and the hand-declared types (`StreamEvent`, `Usage`) are two sources of truth for the same shapes. The error also does not say which request failed.
- **No timeout and no cancellation.** A request that never completes leaves the prompt blocked with no way to abort it. `streamChat` should accept an `AbortSignal`, and the REPL should pass one that Ctrl+C triggers.
- **Compaction keeps roles alternating by merging.** When the first kept message is a user message, the summary is merged into it, so the compacted history starts with one user message. If the first kept message is an assistant message, the summary stands alone as a user message. Either way the roles alternate.
- **The summary is invisible.** Summary chunks are collected without being written, so the user never sees what the model kept, and the "history compacted" line does not say what was dropped. Everything older than the last six messages is gone from the session with no record shown to the user.
- **The summary is a user message with model-written content.** Once a summary is in the history, every later request carries it with user-level authority, so an instruction in a reply that the model summarised is carried forward into every later request. See Security Concerns.
- **History is compacted, not bounded.** Compaction runs on `/compact` and before a message once the last prompt reached 80% of the window. Between compactions the history is resent in full, and no `max_tokens` is set, so a single reply is unbounded. After a compaction, `/context` reports the size as unknown until the next request (see Definitions).
- **A reply that throws is caught at the reply boundary.** `runRepl` turns a thrown reply error into a failure for that turn, the same as an `err` value. The adapters return `err` values and do not throw, so this path is a safety net, not the normal route. The catch assumes the thrown value is an `Error`: a thrown string prints `error: undefined` (verified). A thrown value must be normalised to an `Error` before it becomes a failure. `compact` and the REPL's catch normalise the thrown value, but `src/openrouter.ts` still casts `(error as Error).message` in its three catch blocks, so a thrown string there prints `undefined` in the message. The `ContextWindow` calls in `showContext` and in `compactIfFull` sit outside that boundary, so a throwing context lookup would reject `runRepl` instead of returning an error for `/context` or for the message being sent.
- **A stream error after the session has returned is uncaught.** The `finally` removes the frontend's error listeners on input and output, so an `error` emitted on either stream after `runRepl` returns has no listener. Bun then exits with status 1 and prints a stack trace (verified with a stream that errors after `/exit`, and with output that errors after `/exit`). The process does end, and the failure is not lost, but it is not reported as a session failure and no message is shaped for the user. Invariant 7 is the target.
- **No formatter configured.** The linter enforces size and correctness rules, but not formatting, so style can still drift between files.
- **Approval discards queued input without telling the user.** When the preview is printed, `InputLines.discard()` drops every line queued before it, so an answer must come after the preview, as Invariant 10 requires. The drop is silent. With piped or pasted input every line arrives at once, so an answer sent with the command is discarded and the command is refused with no message (verified: `a` then `y` piped in one chunk refused the call and dropped `y`).
- **The tool loop continues after input has ended while a line is queued.** `finished()` stops the loop on a stream error, on `/exit`, or when input has ended and the queue is empty (`!lines.more`). A queued line keeps it going. Input `a` and `b` piped together, with a reply that asks for `list_files`, ran the tool and sent two more requests after the input had ended, the second answering `b` (verified: three requests in all). Invariant 11 says no request follows the end of input. Decision: the user chose that queued lines still count as input to answer, so a piped message followed by `/exit` keeps its tool result. Queued input therefore keeps a tool loop going, and this case is accepted, not a defect. When a call is skipped, its assistant message stays in the history with no tool message, and nothing tells the user the call did not run.
- **The line queue has one waiter slot.** `InputLines.next()` keeps one pending resolver. A second `next()` while one is pending replaces it, and the first call never resolves. The loop and `approve` never wait at the same time today, so this cannot happen now. A second reader added later would hang without an error.
- **`edit_file` rewrites bytes outside the edit.** `editFile` reads the file as UTF-8 and writes it back as UTF-8, so a byte that is not valid UTF-8 becomes U+FFFD in the whole file (verified: bytes `61 ff 0a 62` edited `b` to `c` gave `61 ef bf bd 0a 63`). A file with any non-UTF-8 byte is silently changed.
- **The preview does not show what will change.** The preview prints `previous` and `replacement`, not the line where the first match is, nor how many matches there are. The write replaces the first match at the time of the write, so a file changed during the question (by an editor or another process) can put the first match somewhere the user did not see, and the user approved without knowing it. The preview also shows the path as the model typed it, not the real location a link resolves to, so an approval can name `link/x.txt` while the write lands at the link's target (inside the working directory, but not the place the user read).
- **`create_file` previews the whole content.** The preview prints every line of the new file, so a large file floods the terminal before the question, and the user answers after scrolling past it. The preview should show a size and a capped excerpt, with the full text kept for the write.
- **`resolveNewInside` reports a misleading error when an ancestor is a file.** For `a.txt/x.txt` where `a.txt` is a regular file, the walk stops at `a.txt`, the folder creation fails with EEXIST, and `createFile` reports "the file already exists" for `x.txt`, which does not exist (verified). The error should name the ancestor that is not a folder.
- **Unpinned development dependency.** `@types/bun` is set to `latest`, so type checks can change without a code change.
- **`typescript` is only a peer dependency.** A fresh install does not provide the compiler the project's checks need unless the user has it installed.
- **Background jobs are not confined.** A command still running after 30 seconds keeps running as a job. Its output is kept as the last 500 lines per stream. `read_command` reads it, and `kill_command` (approved by the user) stops its process tree. `killAllJobs` stops every job when Vise exits, but a job whose stop keeps failing is dropped without a report (see the next bullet). A job's child processes that outlive their parent are not stopped by `kill_command`, for the same reason as gap (b) below.
- **Background job gaps.** (i) `killAllJobs` retries a job whose stop failed up to three times, then clears the registry without reporting the jobs it could not stop, so a process whose stop kept failing can outlive Vise with no message. (ii) A job's status is set by its exit handler and by `killJob` after `taskkill`. The handler writes `exited` only while the job is still `running`, so it never overwrites `killed`. But a stop that completes after the handler has run leaves the status `exited`, and `readJob` then reports an exit the model did not cause. The status should come from one place, not from the order of two callbacks. (iii) `readJob` removes a job at the first read after it has ended, even when its output is still arriving. Verified: a job whose child kept a pipe open returned the output so far, and a second read reported no job. A job that is never read stays in the map for the session, and `MAX_JOBS` counts only running jobs. (iv) `Tail` cuts each line at 8192 characters and marks it. The limit counts UTF-16 code units, so a cut can split a surrogate pair. (v) `index.ts` calls `killAllJobs` only on the return path after `runRepl`. It is skipped if `runRepl` throws, and nothing in `src/` handles interrupts, so what happens to a running job on Ctrl+C depends on the runtime and is not verified.
- **`run_powershell` can keep the process and its pipes after the call returns.** A finished command returns after a one-second grace period even when children hold the output (the test suite covers this). Two gaps remain, both verified. (a) When PowerShell exits normally with a child still holding its output, no stop is applied. The call returned at 1.3 s, but the process could not exit until the child ended (a `Start-Process ping -n 40` kept it alive for 39 s), and the child was never stopped. (b) `taskkill /T` cannot reach a child whose parent has already exited, so the fix for (a) needs a Windows Job Object that kills its processes when the job closes. The `taskkill` call itself has no bound. Output is kept as the last 500 lines per stream, each line cut at 8192 characters.

## Security Concerns

Trust boundaries: everything read from stdin is untrusted text, and every line is sent to OpenRouter, a third party. The model's reply is also untrusted text. Vise reads file names and file contents under the working directory for the model's `list_files` and `read_file` tools (hidden entries skipped; paths are checked on their real location, see below). It writes files only through the `edit_file` and `create_file` tools, after the user approves each change on the terminal, and `create_file` never overwrites. It starts PowerShell only through the `run_powershell` tool, after the user approves each command. The command runs in the working directory. A command still running after 30 seconds becomes a background job that runs until the user approves `kill_command` for it or Vise exits, and its output is kept as its last 500 lines per stream. A child that outlives PowerShell is not stopped by `kill_command` and can keep running after the call returns (see Potential Problems). The API key comes from `.env` and must never be echoed or logged.

- **Terminal escape injection.** In a terminal, readline echoes what the user types, and model replies are written verbatim. A line or reply containing ANSI or other control sequences can change the terminal's state (title, colours, cursor, clipboard on some terminals). Tool lines and approval previews are passed through `sanitize`, which replaces control characters other than tab and newline, so the call's name, path, and the preview's text cannot carry them. Model replies (`streamRound` writes each chunk), the context-window error text, and the `error:` lines are not sanitized yet. This control is **partial**.
- **Prompt injection.** Model replies and earlier replies resent in history can contain instructions that the model then follows, and text from a pasted file or web page can carry them too. The model has `list_files`, which returns file names, and `read_file`, which returns file contents; both are model input. A file the model reads can carry an instruction into the next request, and an injected instruction can make the model call `read_file` on a file the user did not mean it to read. The two read tools neither write nor run anything, but text read from a file is sent to OpenRouter and cannot be taken back. The output of `run_powershell` is model input as well. The risk to design for before any tool can act: any action taken from model output must be confirmed by the user, and must not be reachable from text the model produced alone. Compaction is a second persistence path: a summary written by the model becomes a user-role message in every later request, so an injected instruction survives compaction with more authority than the reply it came from. The ideal is that a summary is shown to the user and confirmed before it replaces the history, and that it is marked in the request as model-written context rather than as the user's words. These controls are **missing**.
- **Unbounded input.** A very long line or an unending stream is read into memory without a limit. The ideal control is a maximum line length, with a defined response when it is exceeded. This control is **partial**: job output lines are cut at 8192 characters and marked, but user input, model replies, and file reads are not limited yet.
- **Containment and hidden paths.** A path is resolved against the working directory and refused when it lands outside it. The real locations of the working directory and the target are compared (`realpath`), so a junction or symbolic link inside the working directory cannot lead outside it. The hidden rule (a path component starting with `.`) is applied to the typed path and to the real path relative to the real root, so a non-hidden junction to a hidden folder such as `.git` is refused. Both checks are in place in `resolveInside` (reads, lists, edits) and `resolveNewInside` (creates). For a path that does not exist yet, the existing ancestor is checked through its real location, and the part below it is checked as typed (it cannot be a link, since it does not exist). A dangling link in that part fails with ENOENT when the folders are made, rather than being refused by the check (verified with a junction to a hidden folder, a junction to a folder outside the working directory, and a dangling junction). `createFile` runs the check again after the approval, but the folders are made after that check, so a link created in the gap between the check and `mkdir` is followed. The `wx` flag protects only the final file. This gap is **partial**: it needs a local process to race the tool, which the model cannot do alone.
- **Tool results are model input from the disk.** File names from `list_files` and file contents from `read_file` are sent to OpenRouter and become model context. Either can contain instructions, which is a prompt-injection path that reads from the disk rather than from the user. The ideal control treats tool output as data, with the escape and length controls above. Data framing is **missing**, and the length control is **missing** for `read_file` (see Potential Problems).
- **Model output is untrusted.** Model replies are written to the terminal as they stream, so they can carry the same escape sequences as input. The same control applies: strip or escape control characters other than tab and newline before writing. This control is **missing**.
- **Server error text is untrusted.** Error bodies from OpenRouter are printed verbatim in `error:` lines, with the same escape-sequence risk. They should be truncated and sanitized the same way. This control is **missing**.
- **Data exposure to a third party.** Every line and every earlier reply is sent to OpenRouter, and the history is resent in full each turn. Since `list_files` and `read_file`, the names and contents of files in the working directory are sent as well, on every turn that uses a tool, not only what the user typed. `run_powershell` output is sent as well, and its command can read files outside the working directory. Users must be told this. Sessions must not send content the user has not typed in this session. `read_file` breaks that rule today: it sends file contents the model asked for, and the user sees only the path and line range in the tool line. The ideal control confirms a content read before it is sent, or caps and announces it; this control is **missing**. A per-session cap on history, compaction that the user can see, a cap on listing size, a cap on content size, and a `max_tokens` limit are the controls. All are **missing** or partial: compaction exists, but its summary is not shown, no `max_tokens` is set, and neither the listing nor the content has a cap.
- **Approval integrity.** The approval question is the only control on writes, and it shows model-written text. The preview is passed through `sanitize`, so terminal control sequences in `previous`, `replacement`, `content`, or the path cannot move the output. The preview still shows the path as typed rather than the real target (see Potential Problems), does not show the line of the first match, and `edit_file` writes whatever bytes it finds at the time of the write. The ideal control shows the real target path and the line of the first match, and writes only the bytes the preview showed. This control is **partial**. A write or a command is approved only by a line typed after the preview (Invariant 10): the question reads the next line of input, so a line typed earlier that is still queued is taken as the answer (Potential Problems). The preview of `run_powershell` shows the command text only, not the working directory's real location or what the command can reach. That control is **missing**.
- **Writes change the file they were approved for, not the text.** An approved edit is applied to whatever file is at the path at write time, after a read that is not compared with the one shown. The ideal control records the matched line or a hash of the file with the approval and refuses the write when it differs. This control is **missing**.
- **Unauthenticated spending.** Any process that can write to the REPL's stdin spends the user's OpenRouter credit. No rate or spend limit exists. This is acceptable for a local terminal tool but must be revisited if the REPL is ever exposed on a socket.
- **Command execution.** `run_powershell` runs a command the model wrote with the user's own permissions. It runs in the working directory, which does not confine it, so it can read, write, delete, or send any file the user can reach, including over the network. The approval preview shows the command line only. The ideal control is an approval that states the working directory and the permissions, a sandbox or a restricted account, a stop that ends the whole process tree, including children that outlive PowerShell, and output framed as data for the model. The per-command approval and the approved stop of a background job are in place; a stop that reaches children that outlive PowerShell, a sandbox, and the output framing are **missing**. Any further command-running tool must be explicit, reviewed on its own, and reachable only through an approval given after its preview.
- **Secrets.** Vise must never log input lines to a file by default, since users may paste secrets. No logging exists yet.

## Future Work

- Move command interpretation into `src/core` as pure functions over `(state, line) -> (state, output)`, so the REPL is a thin driver. The line classifier is done (`src/core/commands.ts`); the REPL acts on its result. Next is moving the command state into the core.
- Move the context state into the core as well: the core keeps the last reported prompt tokens, receives usage through the same state transition as text, and formats the context line from `(used, total)`. The context window becomes a value the core asks for through a port, cached for the session, so `/context` does not fetch the full model listing on every call. The core, not the frontend, decides what `/context` prints when the lookup fails, and it prints the used count in that case.
- Remove the `echoReply` default from the frontend. The ports already live in `src/core/messages.ts`, so the frontend and the model adapter both depend on the core only. The composition root should pass `Reply` and `ContextWindow` explicitly.
- Parse the model listing per entry and keep only the entries that match, so one malformed model cannot fail `/context`. Derive `StreamEvent` and `Usage` from the schemas with `z.infer`, and record real OpenRouter responses as test fixtures so the schemas are checked against the service, not against the tests' own assumptions.
- Make `scripts/check-files-per-dir.ts` count untracked files too (for example, from a directory walk that skips `node_modules` and `.git`).
- Add a formatter, and naming rules to the linter.

Only the queue-empty case stops the loop. When a call is skipped, answer it with a tool message that says it did not run.

- Stop a job's whole process tree on kill and when the session ends, including children that outlive PowerShell. That needs a Windows Job Object set to kill its processes on close, because `taskkill /T` cannot reach an orphan. Release the pipes when the call returns (see Potential Problems).
- Give `resolveNewInside` a structured error that names the ancestor that is not a folder.
- Escape or sanitize model replies and the `error:` lines the same way as tool lines.
- Move the turn itself into the core: a transition `(conversation, line, reply, tools, contextWindow) -> (conversation, parts to show)` that runs the tool rounds and returns what to print, so `runRepl` only reads a line, writes the parts it is given, and holds no conversation of its own. The frontend shows the notice and the summary and decides nothing about history. The turn runner must take the tool runner and the reply as values, so the core stays free of I/O.

- Add a test with a junction to a `.`-prefixed folder, since a symbolic link needs a privilege on Windows, and one for a dangling junction, so the link cases stay covered.

## Performance

These are the obvious concerns only. Measure with a profiler before optimizing.

- Each streamed text delta is written with a separate `write` call. Fine at interactive speed; large replies would benefit from buffering output per chunk.
- Long lines from user input, model replies, and file reads are held whole in memory and in the history. Job output lines are cut at 8192 characters (see Potential Problems).
- Each job stream keeps its last 500 lines, each cut at 8192 characters, so its memory is bounded. A job keeps reading until its process ends, so a command that prints gigabytes runs for its full time. Finished jobs stay in the registry until they are read (see Potential Problems).
- `/context` fetches the full model listing on every call, which is a large response for one number. Cache the context window for the session. The same lookup runs before every message once a size is stored, so the cost is paid on the message path too.
- Compaction resends the whole history once more, plus the summary request, so it roughly doubles the tokens for that turn. It is rare, but a long session can hit it repeatedly.
- **Prompt cache.** The guiding principle is to hit the provider's prompt cache as often as possible. The marker belongs on the last message of every request, whatever its role. `src/openrouter.ts` (`wireMessages` and `toWire`) does this only for a user or assistant message without tool calls. A tool message, or an assistant message that carries tool calls, is sent without a marker, and each round of a tool loop ends with a tool message, so the requests made during a tool loop have no breakpoint and write no cache entry. The next turn then reuses only the prefix written by the last text reply. The fix is to attach the marker to the last message whatever its shape, for example by sending a tool message's content as a text part with `cache_control`, and to confirm the provider accepts a marker on that shape with a probe. A probe against OpenRouter with `anthropic/claude-haiku-5.5` showed 7,204 cached tokens on the second identical prefix with the marker, and 0 without it. The app does not report cache numbers yet. Appending to the history keeps the prefix stable; compaction is the only intended break (Invariant 8). The probe covered two identical requests. It has not covered the turn after a completed one, where the previous last message is sent as plain text rather than with the marker, so the cross-turn case should be probed with two real turns. Provider caches are short-lived (about five minutes on Anthropic models), so a pause longer than that loses the prefix. Each compaction writes one cache entry for the whole history plus the summary request, which is a write cost once per compaction. Reading `cache_read` and `cache_write` from `usage` would make the hit rate measured rather than assumed.
- `list_files` reads every directory down to the depth before it returns, and holds every name in memory. A large tree at depth 5 is read in full even when the result is capped (see Future Work), so the cap limits the output, not the walk.
- `read_file` holds the whole file in memory to return a range of it, so a large file costs its full size even when the range is short (see Potential Problems).
- Startup cost of `bun run` is dominated by the runtime, not by this code.
